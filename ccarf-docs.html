CCAR-F Documentation

Five domains, thirty task statements, end to end

This is an architect exam, so the material is judgement under evidence rather than syntax recall. You are handed a system that already works badly and asked which change fixes the cause. Read the four primers first — they establish the mechanisms all five domains assume — then work the domains in weight order. Every task statement gives you the mechanism, the code or configuration, the decision rule the exam grades on, the distractor it plants, and a Q&A drill. Every domain opens with a worked scenario: one team, one thing measurably wrong in production, and what the credited fix actually was.

Where your study time goes Domain 1 is 27% of the exam and carries seven task statements — more than any other domain, and the only one where a single section (1.2) reliably generates multiple items. Domains 3 and 4 are 20% each. That is two-thirds of the paper in three domains. Domain 2 at 18% and Domain 5 at 15% are smaller, but Domain 5 is not skippable: it supplies the second half of the reasoning in a large fraction of Domain 1 and Domain 2 items, because context handling and error propagation are what decide whether an orchestration answer is right.
How to read the decision tables This exam almost never asks “what is X”. It asks “given this system, this measured symptom and this constraint, what do you change”. Wherever a table below has a Symptom, Situation or Evidence column, that table is the answerable unit — memorise the rows, not the prose around them. And wherever you see version-sensitive, check the live documentation close to your exam date: flag spellings, frontmatter keys and hook event names move between releases.

Primer 1 · The agentic loop, exactly

Every agent on this exam — the support agent, the research coordinator, the developer productivity agent, Claude Code itself — is the same loop. Understand it once mechanically and a large fraction of Domain 1 becomes bookkeeping. The loop is not a feature of the API. It is code you write around a stateless endpoint, and every architectural decision in Domain 1 is a decision about what that code does between calls.

messages = [{"role": "user", "content": user_request}]

while True:
    response = client.messages.create(
        model="claude-opus-5",
        max_tokens=4096,
        system=SYSTEM_PROMPT,
        tools=TOOLS,
        messages=messages,
    )

    # 1. The assistant turn ALWAYS goes back into history, verbatim.
    messages.append({"role": "assistant", "content": response.content})

    # 2. Branch on stop_reason BEFORE you read any content.
    if response.stop_reason != "tool_use":
        break                      # end_turn | max_tokens | refusal | pause_turn

    # 3. Execute every tool_use block in the turn — there may be several.
    results = []
    for block in response.content:
        if block.type == "tool_use":
            try:
                out = dispatch(block.name, block.input)
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": json.dumps(out),
                })
            except ToolError as e:
                results.append({
                    "type": "tool_result",
                    "tool_use_id": block.id,
                    "content": json.dumps(e.structured()),
                    "is_error": True,        # the model sees this and adapts
                })

    # 4. Tool results are a USER message. Then loop.
    messages.append({"role": "user", "content": results})
Seven facts about that loop that generate exam items
  • The API is stateless. There is no server-side agent. Everything the agent “knows” on turn 12 is what you resent in messages. “It forgot the customer ID” is nearly always “you dropped it” or “it is buried in the middle” — see 5.1.
  • Every tool result must come back. A tool_use block with no matching tool_result in the next user message is a 400. You cannot silently drop a call you did not like.
  • Tool results are user messages. The call lives in an assistant message; the result lives in a user message. Reversing them is a hard error, and it is a favourite distractor detail.
  • One turn can contain several tool_use blocks. That is how parallel subagent spawning works (1.3) — several Task calls in one assistant response, executed concurrently, results returned together.
  • The loop needs a stop condition you own. Max iterations, a wall-clock budget, a token budget. Absent one, a model that keeps choosing tools runs until your bill notices.
  • is_error: true is a signal, not a crash. The model reads the error text and adapts — retries with a fixed argument, tries an alternative tool, or reports the failure. That is why the text of the error matters so much (2.2).
  • Where the decision is made is the architectural question. If your code chooses which tool runs next, you built a workflow. If stop_reason and the model's choice drive it, you built an agent. The exam cares about which one the requirement actually needs.

The agentic bias trap Because the exam is about agents, candidates over-select agentic answers. The guide's own framing is the opposite: use the simplest thing that meets the requirement. When a stem describes a fixed, auditable, three-step sequence with a compliance requirement, the credited answer is usually the deterministic workflow with the model doing one bounded job inside it — not an autonomous agent with four tools and a prompt asking it to be careful.
A support agent occasionally calls process_refund without ever having called get_customer. Where in the loop is the fix?
In dispatch() — not in SYSTEM_PROMPT. The loop hands you the tool name and input before the side effect happens, so the dispatcher can check whether get_customer has already returned for this conversation and, if not, return a tool_result with is_error: true and text saying verification required: call get_customer first. The model reads that and complies on the next iteration. This is the single most important structural idea in Domain 1: the loop gives you a programmatic interception point, and a guarantee belongs there rather than in a sentence. See 1.4 and Primer 3.
Why is it wrong to break out of the loop when a tool raises?
Because a tool failure is usually recoverable and the model is the cheapest recovery mechanism you have. Returning the failure as a tool_result with is_error: true lets the model retry with a corrected argument, fall back to a different tool, or tell the user precisely what could not be done. Breaking out converts a recoverable local failure into a total failure — the “kill the whole run” distractor from 5.3. Break out only for failures the model cannot act on: an exhausted iteration budget, an auth failure, or a policy block.

Primer 2 · Coordinator and subagent: the context contract

Multi-agent items are the densest part of this exam, and nearly all of them turn on one fact: a subagent starts with an empty context window. It does not inherit the coordinator's conversation, the user's original question, the other subagents' findings, or anything discovered so far. It receives exactly one thing — the prompt the coordinator writes for it — and it returns exactly one thing: a final message. That is the entire interface.

Coordinator context                     Subagent context (fresh)
┌────────────────────────────┐          ┌────────────────────────────┐
│ user question              │          │ ONLY the task prompt the   │
│ plan / decomposition       │  spawn   │ coordinator wrote:         │
│ subagent A summary  ───────┼─────────▶│  • the goal                │
│ subagent B summary         │          │  • the constraints         │
│ subagent C summary         │          │  • the output shape        │

        ▲ NOT with raw work                     ▲ raw work never surfaces
Both directions of that arrow are exam material Outbound, the coordinator must write a self-contained prompt: everything the subagent needs and nothing it does not. Omit the constraint and the subagent cannot honour it; paste the whole conversation and you have thrown away the isolation you were buying. Inbound, only the final message crosses back, which is exactly why delegation saves context — the subagent can read forty files and return four hundred tokens. Design the return shape deliberately: an unstructured paragraph forces the coordinator to re-derive facts it should have been handed.

Hub-and-spoke, and why not a mesh

Subagents do not talk to each other. Every result flows back to the coordinator, which decides what happens next. This is deliberate: the coordinator is the only component with the whole picture, so it is the only component that can notice a coverage gap, resolve a conflict between two sources, or decide that a fourth subagent is needed. A mesh in which the search agent hands directly to the synthesis agent has no such vantage point, and it is a standard wrong answer.

ConcernOwned by
Decomposing the request into subtasksCoordinator. Its decomposition is the ceiling on the whole system's coverage — a subagent cannot research a facet it was never assigned

The single most reliable tell in multi-agent items When a stem quotes what the coordinator assigned — a list of three subtasks, a set of search queries, a scope description — and the reported failure is a missing dimension in the output, the answer is about the coordinator's decomposition, not about the subagents. Options that give the synthesis agent better instructions, or the search agent more tools, are treating a symptom. The subagents did exactly what they were told; the telling was wrong.

When multi-agent is the wrong architecture

Delegation costs tokens (each subagent re-establishes context), latency (a round trip per hop) and reliability (more moving parts). It pays for itself when the subtasks are genuinely parallel, each needs deep exploration whose raw material should not pollute the main context, and the results compress well. It does not pay when the task is sequential and each step needs the previous step's full detail — then you have added hops and lost information. Expect at least one item where the credited answer is “do this in a single agent”.

A coordinator passes each subagent the full conversation history “so they have context”. What breaks?
The economics and the focus. You are paying to re-send a large history per subagent while getting none of the isolation benefit, and each subagent now has to work out which part of a long history is relevant to its narrow task — which is precisely the attention problem delegation exists to avoid. The correct pattern is a purpose-written, self-contained prompt per subagent: the goal, the constraints that apply to it, any facts it cannot derive on its own, and the required output shape. Nothing else.

Primer 3 · The four enforcement surfaces

If you internalise one thing before the exam, make it this. The recurring question is where does the guarantee live? A system prompt is guidance: it shifts probabilities and it fails occasionally. Four other surfaces are enforcement: they cannot fail in the same way, because the undesired action is not reachable. Whenever a stem describes something that must always hold — money never moves without verification, this agent can never write files, this field is never fabricated — the credited answer moves the rule onto one of these four.

SurfaceMechanismUse it when
1. Tool availabilityDo not put the tool in this agent's tools array / allowedToolsA whole capability must be impossible for a role. A subagent with no Write cannot write, whatever it is asked. Strongest and cheapest surface there is
2. Dispatcher preconditionYour tool executor checks state before performing the side effect and returns is_error if the prerequisite is unmetAn ordering guarantee — verify before refund, lock before write, approve before deploy. The model is told why and self-corrects
3. HooksAgent SDK / Claude Code hooks: PreToolUse can deny a call outright; PostToolUse can normalise or reject its resultA cross-cutting policy that must apply to every call regardless of which agent makes it — secret redaction, blocked paths, currency normalisation, audit logging
4. SchemaJSON Schema on a tool's input_schema (or a structured-output schema): enums, types, required, nullabilityAn output must be machine-consumable and cannot express an invalid value. An enum with four members cannot return a fifth
The rule, stated as a test you can apply in ten seconds Ask: if the model ignored this instruction entirely, would the bad thing happen? If yes, the option is guidance and the exam wants enforcement. If no — because the tool is absent, the dispatcher blocks it, a hook denies it or the schema cannot represent it — that is the credited answer.
Guidance is not worthless — and the exam knows the difference Prompts remain the right surface for things that are matters of judgement rather than permission: tone, when to ask a clarifying question, how to phrase an escalation summary, which of two valid approaches to prefer. The mistake the exam punishes is using a prompt where a hard constraint was required. It also punishes the reverse, less often but it does happen: proposing a rigid programmatic gate for something that genuinely needs case-by-case judgement, which shows up as an option that would block legitimate work.
“Add to the system prompt: never include customer PII in the summary.” Rank the four surfaces for this requirement.
A PostToolUse hook (or an output filter) that redacts PII patterns is strongest — it runs on every call and cannot be talked out of it. A schema helps if the summary is a structured field set that simply has no PII fields. Tool availability helps if the PII source is a tool the summarising agent does not need. The prompt sentence is the weakest of the four and should be kept as a belt-and-braces addition, not as the control. On the exam, an option offering the prompt sentence alone against a compliance requirement is nearly always the distractor.

Primer 4 · Structured output as a contract

Domain 4 is 20% of the exam and half of it is the same insight: when a downstream system consumes the output, prose is a bug. Asking for JSON in the prompt and parsing what comes back gives you a format that is usually right. Defining a tool whose input_schema is your target shape, and forcing the model to call it, gives you a format that is structurally right, because the schema is enforced at generation time rather than checked afterwards.

extract_invoice = {
  "name": "extract_invoice",
  "description": "Record the fields extracted from a single supplier invoice.",
  "input_schema": {
    "type": "object",
    "properties": {
      "invoice_number": {"type": "string"},
      "issue_date":     {"type": "string", "description": "ISO 8601 date, YYYY-MM-DD"},
      "total_amount":   {"type": "number", "description": "Grand total including tax"},
      "currency":       {"type": "string", "enum": ["USD", "EUR", "GBP", "JPY"]},
      "payment_terms":  {"type": ["string", "null"],
                         "description": "Verbatim terms, or null if the document does not state them"},
      "line_items": {
        "type": "array",
        "items": {"type": "object",
                  "properties": {"description": {"type": "string"},
                                 "quantity":    {"type": "number"},
                                 "unit_price":  {"type": "number"}},
                  "required": ["description", "quantity", "unit_price"]}
      }
    },
    "required": ["invoice_number", "issue_date", "total_amount", "currency", "line_items"]
  }
}

resp = client.messages.create(
    model="claude-opus-5", max_tokens=2048,
    tools=[extract_invoice],
    tool_choice={"type": "tool", "name": "extract_invoice"},   # forced: it MUST call this
    messages=[{"role": "user", "content": [{"type": "document", ...}, {"type": "text", "text": PROMPT}]}],
)
data = next(b.input for b in resp.content if b.type == "tool_use")
Four schema decisions the exam grades
  • Force the call. tool_choice={"type":"tool","name":...} when the response must be that structure. {"type":"any"} when it must call some tool. {"type":"auto"} (the default) when text is a legitimate answer.
  • Make genuinely-optional fields nullable — "type": ["string","null"] — or leave them out of required. A required field the source document does not contain is a standing instruction to invent one.
  • Give every closed enum an escape hatch when reality is open: an other member plus a free-text detail field, or an unclear member. Otherwise the model must mis-classify rather than admit the case is novel — and you lose the signal that a new category exists.
  • Put the semantics in description. The schema constrains type and shape; it cannot express “the grand total including tax, not the subtotal”. That distinction lives in the field description, and it is where semantic accuracy comes from.

Syntax errors versus semantic errors

FailureExampleFixed by
Syntactic / structuralMalformed JSON, a missing required key, a string where a number belongs, a value outside an enumThe schema itself. Forced tool use makes most of these unreachable. What remains is caught by validation and usually fixed by one retry
SemanticThe subtotal captured as total_amount; the wrong date of three on the page; a plausible invoice number that is actually the PO numberNot the schema. Field descriptions, few-shot examples of the confusing layout, and human review of low-confidence fields. This is 4.2 and 5.5 territory
AbsenceThe field genuinely is not in the documentNullability. Neither schema strictness nor retry can conjure it — retrying an absent value just produces a more confident hallucination
The distinction the exam tests hardest “Accuracy is 94% but 6% of records have the wrong total” is a semantic problem, and options offering a stricter schema, more required fields, or a validation-and-retry loop do not touch it. Retry re-runs the same reasoning on the same input and gets the same answer. Read the failure description carefully: if the output parsed cleanly and was simply wrong, the schema is not the lever.
version-sensitive Native structured outputs Newer API versions expose a first-class structured-output path — a response-format / JSON-schema parameter that constrains the model's output directly, without the tool-use indirection. Where it is available it is the cleaner answer for “the response must match this schema”. The exam guide's own vocabulary is tool use with JSON schemas, so that is the framing to expect on the paper, but do not be thrown if an option references a native structured-output setting: the underlying decision — schema-enforced rather than prompt-requested — is identical.
A team marks every schema field required so no downstream record is ever incomplete. What actually happens?
Hallucination rate goes up, and the failures get harder to detect. The model must emit something for a field the document does not contain, so it emits something plausible — a date near the other dates, a term that appears on similar invoices. You have converted a visible gap (a null you could route to a human) into an invisible error (a confident wrong value that flows straight into the ledger). Correct design: required for fields that must exist for the record to be meaningful; nullable for the rest; and a downstream rule that routes nulls in important fields to review.

Domain 1 · Agentic Architecture & Orchestration 27%

The largest domain, with seven task statements. It is about who decides: the model, your code, or a coordinator. Almost every item hands you a system that already runs and a measurement that shows it running wrong, and asks which layer to change. Get comfortable with two moves — reading the evidence back to the component that produced it, and preferring enforcement over instruction — and the domain becomes tractable.

Worked scenario
Harbourline Retail: the refund that skipped verification

Harbourline runs an Agent SDK support agent with four MCP tools: get_customer, lookup_order, process_refund and escalate_to_human. Policy says a refund may only be issued after the customer's identity has been verified. The system prompt says so, in bold, twice. Over 12,000 conversations, audit finds 47 refunds issued without a preceding get_customer call — 0.4%. Engineering proposes strengthening the prompt wording and adding a reminder in every turn.

Option on the tableVerdict
Strengthen the system-prompt wording; repeat the rule each turnNo. It reduces a rate that must be zero. 0.4% of 12,000 is 47 unverified refunds; a “better” prompt might make it 12. Twelve is still a compliance finding
Remove process_refund from the agent and route all refunds to a humanNo. It works, but it destroys the 80% first-contact-resolution target the scenario is built around. Over-correcting past the requirement is its own wrong answer
Add a PostToolUse hook that logs every refund for later auditNo. Detection, not prevention. The money has already moved
Enforce the prerequisite in the tool layer: process_refund checks that get_customer has returned for this conversation, and returns an is_error result naming the missing step if notYes. The failure rate becomes structurally zero, the model is told exactly what to do and self-corrects on the next iteration, and legitimate refunds are unaffected
The takeaway When a stem gives you a non-zero rate of a thing that must never happen, it is telling you the control is probabilistic. The credited answer moves the control to a surface where the failure mode does not exist. Every “improve the prompt” option in that situation is a distractor, no matter how well written.

1.1 · Design and implement agentic loops

Covered mechanically in Primer 1. What this task statement adds is the architecture layer: choosing the loop's boundaries, its termination, and how much of the control flow belongs to the model.

What the loop owner is responsible for

ResponsibilityConcretely
Branching on stop_reasontool_use → execute and continue. end_turn → done. max_tokens → the output was cut by your ceiling; do not parse it as complete. refusal → HTTP 200 with near-empty content; check it before reading text. pause_turn → a long-running server tool paused; send the content back unchanged to resume
Maintaining historyAppend the assistant turn verbatim, then a user message carrying one tool_result per tool_use block. Never drop or reorder
TerminationA maximum iteration count, a token budget, or a wall-clock deadline — plus a graceful message when it trips. Without one, a looping model is unbounded spend
Error surfacingFailures return as tool_result with is_error: true and actionable text, not as exceptions that unwind the loop
ObservabilityLog the tool name, arguments, latency and outcome per iteration. Almost every diagnostic item on this exam presupposes someone has this log — it is what makes “the coordinator assigned three subtasks” knowable

Model-driven versus pre-configured decisions

Within one system, some decisions should be the model's and some should be yours. The exam tests the boundary. A useful split: the model decides what is true and what to do next; your code decides what is permitted and when to stop.

Give to the model
  • Which tool answers the question in front of it
  • How to phrase a query, a summary, an escalation note
  • Whether the evidence gathered so far is sufficient
  • How to classify an ambiguous case, given explicit criteria
Keep in your code
  • Whether a prerequisite has been satisfied
  • Whether this agent may touch this resource at all
  • How many iterations, tokens or seconds remain
  • Whether the final output matches the required shape
  • What gets logged, redacted and audited
Two loop bugs that show up as “model quality” problems Truncation read as completion — stop_reason: "max_tokens" ignored, so half-written JSON is parsed and blamed on the model. Unbounded retry — a tool that keeps failing, an error result the model keeps reacting to, and no iteration cap, producing a conversation that spirals. Both are integration defects. When a stem describes intermittent malformed output or runaway cost, look at the loop before you look at the prompt.
An agent sometimes stops mid-task and returns a partial answer that reads as if it were finished. What do you check first?
stop_reason on the final response. max_tokens means your ceiling cut it; refusal means a safety classifier declined and returned 200 with near-empty content, which an integration that reads content[0].text blindly will render as a short, confident, wrong answer. Both are invisible unless you branch on the stop reason before consuming content.
When is a pre-configured sequence the better architecture even though the task “feels” agentic?
When the steps do not vary with the data, and when auditability matters. A three-stage document pipeline — extract, validate, persist — that runs identically every time gains nothing from letting a model choose the order, and loses testability, determinism and cost predictability. Reserve the agentic loop for the part that genuinely varies: inside that pipeline, the extraction step may well be one bounded model call with a forced tool.

1.2 · Orchestrate multi-agent systems with coordinator–subagent patterns high yield

The mechanics are in Primer 2. This section is about the failures the exam actually presents, which are almost always failures of decomposition or scope rather than of the subagents themselves.

2. Spawn A, B, C in parallel;   each returns {findings, sources, confidence, gaps_noted}

Step 3 is the one candidates skip The coordinator's evaluation between rounds is what separates a multi-agent system from a fan-out. An option that adds a second round unconditionally is worse than one that adds a gap analysis and then a targeted round: the first burns budget uniformly, the second spends it where coverage is missing. When a stem says the coordinator “spawns subagents and assembles the results”, the missing piece is nearly always the evaluation step.

Scope partitioning that actually works

Do
  • Name each subagent's dimension explicitly: “economic effects only”, “peer-reviewed sources published 2023 or later”
  • State the boundary: “do not cover regulatory questions; another agent owns those”
  • Fix the return shape so the coordinator can compare like with like
  • Ask each subagent to report what it could not find, not just what it found
Don't
  • Give three subagents the same question and hope for diversity
  • Let subagents talk to each other — you lose the only global vantage point
  • Pass the whole conversation as “context”
  • Let a subagent silently return nothing when its source failed — see 5.3
A research coordinator's log shows it assigned: “economic impact of AI on employment”, “AI and job displacement statistics”, “automation effects on labour markets”. The report is criticised for ignoring social, educational and regulatory dimensions. Which component do you fix?
The coordinator. All three subtasks are the same facet in three phrasings, so the system's maximum possible coverage was one dimension wide before a single subagent ran. The fix is in the decomposition prompt: require the coordinator to enumerate distinct dimensions of the question and to justify that they are disjoint. Options that improve the synthesis agent, add a fourth search subagent on the same facet, or give the search agents better tools are all treating a component that behaved correctly.
When does adding a coordinator make a system worse?
When the work is inherently sequential and each step needs the previous step's full output. Delegation compresses — that is the point — so a chain of subagents each handed the previous one's summary loses detail at every hop, plus latency and tokens. Single agent with good context management beats a coordinator here. Also when there is exactly one subtask: a coordinator that spawns one subagent is pure overhead.

1.3 · Configure subagent invocation, context passing and spawning high yield

Where 1.2 is the strategy, 1.3 is the API surface: the Task tool, the tool allow-list, agent definitions, and what a good subagent prompt contains.

Spawning with the Task tool

In the Agent SDK and in Claude Code, a coordinator delegates by calling the Task tool. The call carries a prompt, a short description, and the subagent type. Crucially, several Task calls in a single assistant turn run concurrently — that is the mechanism for parallel subagents, and it is a favourite detail. Sequential spawning across turns gives you no concurrency at all.

// Agent SDK — defining the roles a coordinator may delegate to
const agents: Record<string, AgentDefinition> = {
  "web-research": {
    description: "Searches the public web for a NAMED, NARROW facet of a question. "
               + "Use when the facet requires external sources.",
    prompt: "You research one assigned facet. Return findings with a source URL and a "
          + "publication date for every claim. Report explicitly what you could not find.",
    tools: ["WebSearch", "WebFetch"],        // enforcement surface 1: nothing else is reachable
    model: "sonnet",
  },
  "doc-analysis": {
    description: "Analyses documents already present in the workspace. No web access.",
    prompt: "Extract the requested facts from the supplied documents. Quote the source line "
          + "for each fact. If a fact is absent, say so; never infer it.",
    tools: ["Read", "Grep", "Glob"],
    model: "sonnet",
  },
};
Three fields, three different jobs description is read by the coordinator and is how it decides which subagent type to use — it is a routing signal, exactly like a tool description (2.1), and vague descriptions cause mis-delegation. prompt is the subagent's system prompt, defining how it behaves and what it returns. tools (or allowedTools) is enforcement: a capability left out of this list is unreachable for that role, full stop.

A developer-productivity agent gives its exploration subagent the full built-in tool set including Write, Edit and Bash, on the grounds that it “might need them”. What is wrong?
Two things. First, safety: an exploration role that can write and execute is one misinterpretation away from mutating the repository, and no prompt reliably prevents that. Restricting tools to Read, Grep and Glob makes it impossible. Second, selection quality: every extra tool dilutes tool choice, so an agent with nine tools picks worse than one with three (2.3). Scope the allow-list to the role's actual job.
Why does a subagent's description matter as much as its prompt?
Because the coordinator routes on it. Two subagent types described as “researches topics” and “investigates subjects” are indistinguishable to the delegating model, so it picks arbitrarily — the same failure as two confusable tool descriptions. Descriptions should state when to use this one and when not to: “public web sources only; use doc-analysis for files already in the workspace”.

1.4 · Multi-step workflows: enforcement and handoff high yield

This task statement is Primer 3 applied to sequences. Two ideas: programmatic prerequisites for ordering guarantees, and structured handoffs for the moment work leaves the agent.

Programmatic prerequisites

REQUIRES = {
    "process_refund":   ["get_customer"],           # identity verified first
    "close_account":    ["get_customer", "lookup_open_orders"],
    "apply_credit":     ["get_customer"],
}

def dispatch(name, args, state):
    for prereq in REQUIRES.get(name, []):
        if prereq not in state.completed_tools:
            return {
                "isError": True,
                "error": {
                    "category": "precondition_failed",
                    "isRetryable": True,
                    "message": f"'{name}' requires '{prereq}' to be called first for this "
                               f"conversation. Call '{prereq}', then retry.",
                    "missing_prerequisite": prereq,
                },
            }
    result = TOOLS[name](**args)
    state.completed_tools.add(name)
    return result
Why this beats the prompt on every axis the exam cares about The bad outcome is unreachable, not merely unlikely. The error text is actionable, so the model fixes itself in one iteration rather than failing the customer. The rule is auditable — it is code with a test, not a paragraph someone may have edited. And it is per-conversation stateful, which no prompt can be.

Decomposing multi-concern requests

A frequent stem shape: a customer message contains three separate issues (a damaged item, a duplicate charge, and a delivery-address change) and the agent handles one and drops the others. The fix is neither a bigger model nor a longer prompt — it is an explicit decomposition step: enumerate the distinct requests first, then resolve each, then confirm each in the reply. The same shape appears in code review (per-file findings plus a cross-file pass, 1.6) and in extraction (per-section, then reconcile).

“Transfer the conversation to a human agent” is not a handoff An option that escalates without a structured summary is incomplete even when escalating was correct. The exam consistently credits the option that carries context across the boundary; simply moving the customer to a queue re-imposes the whole conversation on them and on the human.
A stem reports that an agent “occasionally” performs a destructive operation the policy forbids, and the options are: (a) stronger prompt, (b) remove the tool, (c) prerequisite check in the dispatcher, (d) log and alert. How do you choose between (b) and (c)?
Ask whether the operation is ever legitimate for this agent. If never — the role should not have that capability at all — (b) is the strongest and simplest answer. If it is legitimate under conditions (verified customer, order found, amount under a threshold), (b) over-corrects and destroys the capability the scenario needs, so (c) is right: it permits the legitimate case and blocks the rest. The stem's stated business target — first-contact resolution, throughput — is usually the tie-breaker, because it tells you whether removing the capability is affordable.

1.5 · Agent SDK hooks for interception and normalisation

Hooks are enforcement surface 3. They are shell commands or callbacks the runtime invokes at fixed points in the agent's lifecycle, and they run every time, deterministically, regardless of what the model decided. That property — determinism — is the whole reason they appear on this exam.

The canonical normalisation case

Three MCP servers return dates as 2026-03-14, 14/03/2026 and March 14, 2026, and amounts as 1250.00, "$1,250.00" and 125000 (minor units). The agent reasons over all three and occasionally compares them wrongly. The instinct is to tell the model about the formats in the system prompt. The architecture answer is a PostToolUse hook that rewrites every tool result into one canonical representation before the model ever sees it — because then there is nothing to reason about, no per-server special case in the prompt, and no new failure when a fourth server is added.

Hook or prompt? One question Must this happen on every single call, identically, with no judgement? Yes → hook. If it requires weighing context — is this the right moment to ask a clarifying question, is this refund reasonable — a hook is the wrong shape and the prompt (or a tool the model can choose) is right.
Would you enforce “never write outside the project directory” with a hook or a prompt?
A PreToolUse hook that inspects the path argument and denies anything outside the root. It is a hard boundary with no judgement in it, it applies to every write regardless of which agent or subagent attempted it, and the denial reason goes back to the model so it can retry inside the tree. A prompt sentence is a probability, and this is a security boundary.
A team adds a PostToolUse hook that rejects any tool result over 10,000 tokens. Good idea?
Truncating or summarising, yes — rejecting outright, usually not. Verbose tool results are a real context problem (5.1), and a hook is exactly the right place to trim them to the fields the agent needs. But rejecting means the model gets nothing and will simply call the tool again. Normalise and reduce in the hook; reject only when the result violates an invariant that makes it unusable.

1.6 · Task decomposition strategies

Two axes: fixed versus adaptive, and within-unit versus across-unit.

Fixed chaining versus adaptive decomposition

StrategyUse whenCost of getting it wrong
Prompt chaining — a fixed sequence of model calls, each consuming the lastThe stages are known and stable, and each benefits from a focused prompt: summarise → classify → draftApplied to a variable task, it forces every input down one path and silently mishandles the cases that do not fit
Adaptive decomposition — the model plans the subtasks for this specific inputThe number and nature of the subtasks depend on the input: a research question, a bug of unknown origin, a multi-issue support ticketApplied to a fixed task, it adds variance, cost and unpredictability to something that should have been deterministic
Hybrid — fixed outer phases, adaptive inside oneMost real systems. “Always: gather → analyse → report”, with the gather phase deciding for itself how many sources it needsRarely wrong; it is often the credited answer when two options offer the pure forms

The per-unit plus cross-unit pattern

This shape recurs across three domains, so learn it once. A pull request touches 14 files; a single review pass over all of them dilutes attention and misses both file-level detail and system-level consequences. The credited architecture is two kinds of pass:

  • Per-file passes — focused, independent, parallelisable, each seeing one file in full and reporting concrete findings.
  • An integration pass — sees the diff summary and the per-file findings, and looks specifically for what no single file reveals: a changed function signature and its unchanged callers, a transaction boundary crossed, a shared assumption broken.

The distractor here is always “use a larger context window so everything fits in one pass”. It misdiagnoses the problem: this is attention dilution across many items, not capacity. A bigger window holds more and still spreads attention thinly — and it does nothing about the fact that a single pass has no moment where the reviewer is asked the cross-file question explicitly.

Decomposition is a coverage ceiling Whatever your decomposition does not name, your system cannot find. This is true of research subtasks (1.2), review passes, extraction sections and support-ticket issues. When a stem reports “X was missed”, ask first whether any step was ever responsible for X.
A 14-file PR review misses a signature change that breaks three callers, but the per-file comments are accurate. What is missing?
The integration pass. Per-file review is structurally incapable of catching a cross-file consequence — the file where the signature changed looks fine in isolation, and the caller files were not modified so they may not even be in the diff. You need a second pass whose explicit job is cross-file consistency, given the per-file findings and the whole diff. Note the shape of the wrong answer: “the per-file prompts should also consider callers” asks a reviewer to reason about files it cannot see.

1.7 · Session state, resumption and forking

Sessions persist a conversation so work can continue later. Three operations matter, and the exam tests when each is appropriate rather than their syntax.

OperationSurfaceUse when
ResumeClaude Code: claude --resume <session> (or --continue for the most recent). Agent SDK: pass the session id as resumeYou are continuing the same line of work and the accumulated context is an asset — a long debugging session, a multi-day refactor
ForkResume with forkSession / fork_session set — continues from the same history but writes to a new session id, leaving the original untouchedYou want to try a second approach from a shared starting point, or run a branch you may throw away, without contaminating the original thread

version-sensitive Flag and option spellings (--resume, --continue, --fork-session, the SDK's forkSession) differ between the CLI and the SDK and have shifted between releases. The concepts — continue, branch, restart-with-summary — are what the exam grades.

The resumption trap A resumed session believes the world is as it left it. If files changed, a deploy happened, or a decision was reversed while it was suspended, it will reason from stale facts and produce confidently wrong work. Tell a resumed session what changed. An option that resumes a two-week-old session and immediately asks for a code change, with no update, is a distractor even though resuming was the right call.
When resuming is worse than restarting Long sessions accumulate abandoned approaches, corrected mistakes and superseded plans. All of it is still in context, all of it still influences the model, and the useful conclusions sit in the middle where attention is weakest (5.1). If the useful state is a paragraph, carry the paragraph — do not carry the archaeology.
Two engineers want to try different migration strategies from the same analysed starting point. Resume, fork, or two fresh sessions?
Fork — twice. Both branches inherit the shared analysis without re-doing it, and neither pollutes the other or the original. Resuming twice into the same session interleaves two incompatible lines of reasoning in one history; two fresh sessions throw away the analysis they both need.

Domain 2 · Tool Design & MCP Integration 18%

Five task statements about the interface between a model and the systems it acts on. The organising idea: the model's only view of a tool is its name, description and schema. Every selection failure, every wrong argument, every misroute is a defect in that surface — not in the model's intelligence, and not usually in the tool's implementation.

Worked scenario
Ravensmoor Logistics: the tool that answered the wrong question

Ravensmoor's support agent exposes two MCP tools:

lookup_order“Look up order information”
get_order_status“Get the status of an order”

Telemetry shows the agent calls lookup_order for pure status questions (“where is my parcel?”) about 40% of the time, then calls get_order_status as well — two round trips, extra latency, and a full order payload pulled into context for no reason. A proposal circulates to merge the two into one order_tool with a mode parameter.

2.1 · Tool interface design high yield

The model sees three things: name, description, input_schema. It does not see your implementation, your docs, or your intentions. Anthropic's own guidance is blunt about the leverage here: improving a tool description is usually a bigger accuracy win than any prompt change.

Anatomy of a description that routes correctly

{
  "name": "process_refund",
  "description":
    "Issue a refund against a specific order line. "
    // 1. WHAT IT DOES — one sentence, unambiguous
    "Use after the customer's identity has been verified with get_customer and the order "
    "has been located with lookup_order. "
    // 2. WHEN TO USE IT — including prerequisites the model must satisfy
    "Do NOT use for billing disputes on subscriptions (use adjust_subscription) or for "
    "goodwill credits (use apply_credit). "
    // 3. WHEN NOT TO USE IT — naming the sibling tools explicitly
    "Returns the refund id and the expected settlement date. Refunds above 500 USD are "
    "rejected with a permission error and must be escalated.",
    // 4. WHAT COMES BACK, and the boundaries of what it will accept
  "input_schema": {
    "type": "object",
    "properties": {
      "order_id":   {"type": "string", "description": "Order id from lookup_order, e.g. ORD-84213"},
      "line_id":    {"type": "string", "description": "Line id within the order; omit to refund the whole order"},
      "amount":     {"type": "number", "description": "Refund amount in the order's currency, ≤ the line total"},
      "reason_code":{"type": "string", "enum": ["damaged","not_received","wrong_item","late","other"]},
      "reason_note":{"type": "string", "description": "Required when reason_code is 'other'"}
    },
    "required": ["order_id", "amount", "reason_code"]
  }
}
Four things every description should carry
  1. What it does — in one unambiguous sentence, in the vocabulary a user would use.
  2. When to use it — the triggering situation, plus any prerequisite tools.
  3. When not to use it — naming the sibling tool by name. This is the line that fixes confusable pairs, and the line teams most often omit.
  4. What it returns and its limits — so the model can plan the next step and knows which requests will be refused.

Diagnosing selection failures

Observed behaviourCauseFix
Picks tool A when B was right, on a recognisable class of requestsOverlapping descriptions; no boundary statementDifferentiate: each description states its scope and names the other
Calls two tools where one would doNeither description says what it returns, so the model hedgesState the return contents explicitly
Calls the right tool with wrong or invented argumentsParameter descriptions missing, or the format is unstatedDescribe every parameter: units, format, provenance (“the id returned by lookup_order”)
Uses one generic tool for everything and gets it wrong at the edgesThe tool is too broad — manage_account(action, ...)Split it into distinct named operations. Distinct tools with distinct schemas route better than one tool with an action enum
Fails to use a tool at all when it obviously appliesVocabulary mismatch — the description says “remuneration record”, users say “payslip”Write descriptions in the users' words, and include the synonyms

The keyword-sensitivity trap A system prompt that says “when the customer mentions refund, call process_refund” produces an agent that fires on “I don't want a refund, I want a replacement”. Keyword rules in prompts are brittle by construction. The exam prefers descriptions that capture the situation (“use when the customer is owed money back for a completed order”) over prompts that capture the string.
When is consolidating two tools the right answer?
When the split is genuinely artificial — the two tools hit the same backend endpoint with a different flag and no user-visible distinction exists — or when the toolset is large enough that reducing count is itself the goal. Even then, a consolidated tool needs a schema whose enum makes the mode obvious and a description that explains each mode. What the exam penalises is reaching for consolidation as the first response to a description defect, when rewriting two paragraphs would fix it without touching a single caller.
How do you write a description for a tool with a genuinely narrow, easily-confused sibling?
Make the boundary the second sentence, and name the sibling. “Returns current shipment status and tracking events only. For order contents, pricing or payment history use lookup_order.” Both descriptions should carry the mirror-image sentence, so whichever one the model reads first it learns the boundary.

2.2 · Structured error responses for MCP tools

An MCP tool reports a failure by returning a normal result with isError: true and content describing what went wrong. That content is read by the model, so it is not a log line — it is an instruction to whoever must recover. Errors that say Error: request failed give the model nothing to act on, and the agent's behaviour degrades to a generic apology.

// A tool result the model can actually act on
{
  "isError": true,
  "content": [{ "type": "text", "text": JSON.stringify({
      "errorCategory": "validation",         // transient | validation | business | permission
      "isRetryable": false,                  // may the SAME call succeed later?
      "message": "order_id 'ORD-8421' is not a valid identifier: expected 5 digits after 'ORD-'.",
      "field": "order_id",
      "suggestedAction": "Re-read the order id from the lookup_order result and retry.",
      "alternatives": ["search_orders_by_email"]
  })}]
}
CategoryExamplesRetryableWhat the model should do
transientTimeout, 503, connection reset, rate limitYesRetry the identical call after a backoff — ideally the server has already retried once locally
validationBad format, out-of-range value, missing required argumentNot as-isFix the argument and retry. The message must say which field and what was expected
businessOrder already refunded; account closed; policy limit exceededNoStop and explain, or take the documented alternative path (escalate, offer a credit). Retrying is pure waste
permissionThis agent, key or role may not perform this actionNoEscalate to a human or a privileged path. Never retry, never work around
Recover locally before you propagate A single transient network blip should be retried inside the tool with a short backoff, not surfaced to the model. Surfacing it wastes a full agent iteration on something the server could have handled in 200 ms, and adds noise to the conversation. Propagate what the caller must decide about; absorb what you can simply handle.
Two errors the exam punishes hardest Swallowing: catching the failure and returning an empty successful result. The agent now believes there were no matching orders — a false negative that propagates into a confident wrong answer to the customer. Crashing: letting the exception unwind the whole run, so one failed source kills a report that four other sources could have carried. Both appear as options in nearly every error-handling item; the credited answer is the structured middle path.
“Empty result” and “could not check” are different facts This distinction generates items in both Domain 2 and Domain 5. No orders match that email is a finding. The order service did not respond is an absence of information. Represent them differently, because the correct downstream behaviour differs completely: one lets the agent tell the customer something true, the other requires a retry, an alternative source, or an honest “I could not check”.
A tool returns {"error": "failed"} with isError unset. What does the agent do, and why is it bad?
Without isError the runtime treats it as a successful result, so the model sees an object whose error field it may or may not interpret — behaviour becomes unpredictable. And "failed" carries no category, no retryability and no field, so even a model that understands it is an error cannot choose between retrying, fixing an argument and escalating. Set isError, and make the payload say what class of failure it is and what to do next.

2.3 · Tool distribution across agents, and tool choice

How many tools is too many

Selection reliability degrades as the toolset grows, and it degrades fastest when tools are similar. There is no published magic number, and the exam will not ask for one — it asks what to do about the symptom. The architectural answer is scope by role: the tools an agent holds should be the tools its job requires, and delegation exists partly so that each role's set stays small.

SituationDesign
A monolithic agent with 20 tools, misrouting between similar onesSplit by role into subagents, each with a scoped set (1.3). Coordinator routes; specialists act
A subagent occasionally needs one capability that belongs to another roleGive it a narrow, constrained version of that capability — not the full toolset. A synthesis agent that sometimes needs one fact can have verify_single_fact, not the whole web toolkit
A read-only role in a system with destructive toolsSimply omit them. Enforcement surface 1 — the cheapest guarantee available
Two roles need the same tool with different limitsTwo tools with different schemas and limits, or one tool plus a PreToolUse hook that enforces the per-role limit
“Give it every tool so it never gets stuck” This is a recurring distractor, and it is wrong twice over: it degrades selection for the common case, and it removes the safety property that made the role restriction valuable. The credited pattern is a scoped addition — the one narrow tool that covers the common cross-role need — with the coordinator handling the rest.

A synthesis subagent occasionally needs to verify one fact against the web, and currently returns to the coordinator to ask. Options: give it the full web toolset, give it one narrow verification tool, or keep the round trip. Choose.
The narrow verification tool, if the round trip is measurably hurting. It covers the common case at minimal cost to selection quality and keeps the role boundary meaningful. The full toolset turns a synthesis agent into a research agent and degrades both jobs. Keeping the round trip is defensible if the case is genuinely rare — the exam usually signals which by quoting a frequency.

The secrets rule, which the exam does test A project .mcp.json is committed, so a literal token in it is a token in your git history. Reference environment variables with ${VAR} (and ${VAR:-default} for optional values) so each developer and each CI runner supplies its own. An option that puts a key directly in a shared config file is always wrong.

Resources, not just tools

MCP servers can expose resources — addressable content the client can list and read — alongside tools. The distinction the exam draws: a tool is an action the model chooses to perform; a resource is content that can be discovered and pulled in. When the requirement is “make this catalogue of documents/schemas/templates available for reference”, resources are the right shape, and wrapping the same content in a search_documents tool is a heavier answer that forces every access through a model decision.

Several servers at once A client can connect to multiple MCP servers simultaneously; their tools are all discovered and presented to the model together. Two consequences: name collisions matter (namespacing keeps search from three servers distinguishable), and tool count adds up fast — three servers with eight tools each is 24 tools in one selection decision, which is exactly the 2.3 problem arriving by the back door.
Your team's agent must reach an internal API. Where does the server config go, and where does the token go?
The server entry goes in the project .mcp.json so everyone gets it on clone, with "API_TOKEN": "${INTERNAL_API_TOKEN}". The token itself lives in each developer's environment and in CI's secret store — never in the committed file, never in CLAUDE.md, never in a slash command. If a token must differ per developer, that is another reason the variable indirection is the only workable design.

And “use Bash with grep -r rather than the Grep tool” — it works, but returns unstructured output, respects no ignore rules, and is the sort of answer the exam marks down in favour of the purpose-built tool.
You must understand how authentication works in an unfamiliar 400-file service. What is the sequence?
Grep for the concept first — authenticate, login, jwt, session — to find the two or three files that matter; Glob for the conventional locations (**/auth/**, **/middleware/**) to confirm the layout; then Read only those files, in full. If the answer needs a broad sweep whose raw material you do not want in your main context, delegate it to an exploration subagent restricted to Read, Grep and Glob, and take back a summary (5.4).

Domain 3 · Claude Code Configuration & Workflows 20%

Six task statements on configuring Claude Code so a team gets consistent results. The organising idea: context should arrive automatically and only when relevant. Every mechanism here — hierarchy, imports, path rules, skills, commands — exists to answer the question “how does the right convention reach the model at the right moment without a human pasting it”.

Worked scenario
Sable Research: the 900-line CLAUDE.md nobody follows

What belongs in CLAUDE.md — and what does not

Do put in

  • Conventions that apply to all work in the repo

Diagnosing what actually loaded /memory shows the memory files in play and lets you edit them. When a stem says a convention “is not being followed”, the first architectural question is whether the file containing it was ever loaded for that task — a directory CLAUDE.md only applies when work reaches that directory, and a rule with a paths: glob only applies when a matching file is touched.
A convention in a package-level CLAUDE.md is ignored when Claude edits that package from a session started at the repo root. Bug or expected?
Expected behaviour to reason about, not a bug to report. Directory-level memory attaches to work in that subtree; if the session's activity has not reached those files, that memory has no reason to load. If the convention must apply whenever files of a certain type are touched — wherever they live — a directory file is the wrong mechanism and a .claude/rules/ entry with a paths: glob is the right one (3.3).

3.2 · Custom slash commands and skills high yield

Slash commands

A command is a prompt template stored as a Markdown file — .claude/commands/name.md for the project, or in the user directory for personal ones. It is invoked explicitly by the human.

---
description: Review the staged diff against our security checklist
argument-hint: [severity-floor]
allowed-tools: Read, Grep, Glob, Bash(git diff:*)
---

Review the staged changes for security defects at severity $1 or above.

Current diff:
!`git diff --cached`

Checklist: @docs/security-checklist.md

For each finding give: file and line, the concrete exploit path, and the fix.
Report nothing that is merely stylistic.
  • $ARGUMENTS is everything the user typed; $1, $2 are positional.
  • !`cmd` runs a shell command and inlines its output at invocation time.
  • @path inlines a file.
  • allowed-tools restricts what the command may do — enforcement, not advice.
  • argument-hint is the completion hint shown to the human in the UI.

Skills

A skill is a folder — .claude/skills/<name>/SKILL.md, plus any supporting files — describing a capability the model invokes when it judges the situation matches. The frontmatter description is therefore a routing signal, exactly like a tool description.

---
name: incident-postmortem
description: >
  Produce a blameless post-mortem from an incident timeline. Use when the user
  mentions an outage, an incident, a sev-1/sev-2, or asks for an RCA document.
  Do not use for routine bug write-ups.
allowed-tools: Read, Grep, Glob, Write
context: fork
---

# Incident post-mortem

1. Gather the timeline: alerts, deploys, mitigations, resolution.
2. Establish contributing factors — never a single "root cause", never a person.
3. Write to `docs/postmortems/YYYY-MM-DD-<slug>.md` using @templates/postmortem.md.
4. Produce action items with an owner and a due date each.
The three frontmatter keys the exam cares about
  • description — how the model decides to invoke it. Must say when to use and when not to. A vague description means the skill never fires, or fires on the wrong task.
  • allowed-tools — the tools available while it runs. Enforcement surface 1, scoped to a workflow.
  • context: fork version-sensitive — runs the skill in an isolated context that does not pollute the main conversation, returning only its result. Use it for verbose work — a long audit, a broad sweep — whose intermediate output the main thread does not need.

Choosing the surface

The classic mis-assignment Putting a long, occasionally-used procedure in CLAUDE.md — it costs context on every unrelated task and dilutes the rules that do apply. And the mirror image: putting an always-applicable convention in a skill, so it only sometimes loads and the team sees inconsistent behaviour. Always → CLAUDE.md. Sometimes, by file type → path rule. Sometimes, by task → skill.
A team's skill never triggers. The body is excellent. Where is the bug?
The description. It is the only part the model reads when deciding whether the skill applies — the body is loaded after. A description like “helps with documentation” gives nothing to match against. Rewrite it to name the triggering situations in the words a user would use, and to name what it is not for so it stops competing with a neighbouring skill.
When is context: fork worth it?
When the skill's intermediate work is voluminous and only its conclusion matters — auditing 200 files, sweeping a dependency tree, running a long analysis. Forking keeps that traffic out of the main conversation, so the thread you are actually working in stays focused. It is the skill-level version of the subagent isolation argument in 5.4. 3.4 · Plan mode versus direct execution

Plan mode explores and proposes without changing anything; you approve before work begins. Direct execution starts editing. The exam wants the judgement, not the keystroke.

There are several defensible approaches and the choice has consequencesThere is one sensible way to do it
You do not yet know the blast radiusYou already know exactly what to change
The work is architectural, or touches shared contractsThe work is mechanical — rename, formatting, a version bump

The under-used third option: delegate the exploration Understanding an unfamiliar area produces a lot of output — file listings, search results, whole files read — that you do not want occupying your main context for the rest of the session. Sending that discovery to an Explore-style subagent and receiving a summary keeps the working thread clean. On the exam, when a stem complains that a session “degrades after exploring the codebase”, this is the shape of the answer, not a bigger context window.
Both over-corrections are wrong answers Planning a two-line fix wastes a round trip and reads as process for its own sake. Going direct on a cross-cutting refactor produces a large diff built on an approach nobody agreed to, which is expensive precisely when it is wrong. The exam signals which by describing scope and reversibility — read those two attributes out of the stem before you look at the options.
A stem describes migrating authentication from sessions to JWTs across a service, and asks for the best workflow. What must the answer contain?
Exploration first (ideally delegated, because it is verbose), then plan mode to surface the approach — token lifetime, refresh strategy, migration path for live sessions, what happens to existing clients — then approval, then execution in stages with tests between them. An option that starts editing files is wrong because the approach has real alternatives with real consequences; an option that only plans, with no staged execution and verification, is incomplete.

Restart with a prompt that encodes what you learned. Three CI-specific design rules
  • Structured output is not optional. A pipeline that greps prose for the word “critical” is a pipeline that fails silently the day the phrasing changes.
  • CLAUDE.md is your CI context. The repository's conventions load in CI just as they do locally, which is what makes automated review aware of the team's actual standards rather than generic ones.
  • Precision over recall in a blocking gate. A reviewer that flags twenty things per PR, fifteen of them noise, gets ignored within a fortnight — and an ignored gate is worse than no gate, because it also blocks. This is exactly 4.1: explicit severity criteria, not “be conservative”.
Do not let the author review itself When the pipeline both generates and reviews, use a separate invocation for the review — a fresh instance with no memory of the generation reasoning. An instance that just justified a design decision is poorly placed to find the flaw in it. See 4.6.
And do not batch a blocking check The Message Batches API is 50% cheaper and takes up to 24 hours. A pre-merge review is blocking a human, so the discount is irrelevant — the option that moves a blocking gate to batch is always wrong (4.5). Nightly full-repo analysis, however, is exactly what batch is for.
Automated PR review is being ignored by the team. Diagnose.
Almost certainly precision, not coverage. Measure the false-positive rate first — the stem usually supplies it. The fix is explicit severity criteria with code examples of what does and does not qualify, and reporting only the top severities in the blocking gate while everything else goes to a non-blocking comment. Adding more checks, a bigger model, or stronger “be careful” language all make the ignoring worse.

Domain 4 · Prompt Engineering & Structured Output 20%

Six task statements. The mechanics are in Primer 4; the domain itself is about precision — getting a specific, reliable, machine-usable result out of a probabilistic system. The recurring judgement: which failures are fixed by schemas, which by examples, which by criteria, and which by none of the three.

Worked scenario
Kestrel Systems: the reviewer nobody reads

Kestrel added an automated code reviewer to its pipeline. The prompt ends “be conservative and only report issues you are confident about”. After six weeks: an average of 23 comments per PR, and engineers report roughly 70% are not worth acting on — style opinions, hypothetical nulls that cannot occur, suggestions to refactor working code. Developers have started approving through the bot without reading it. Leadership asks for a fix, and the proposals are: a stronger model, a confidence score with a threshold, and a second reviewer to filter the first.

Have the model score its confidence 1–10; suppress below 7No. Self-reported confidence is not calibrated. The 70% it was wrong about are exactly the ones it felt sure of

4.1 · Explicit criteria over vague confidence language high yield

“Be conservative” is not an instruction — it is a hope. The model has no shared referent for how conservative, and no test it can apply to a candidate finding. Replace the adjective with a decidable rule.

Report a finding ONLY if it satisfies one of these categories.

BLOCKER — a defect that is exploitable or causes data loss in production.
  Qualifies:      unparameterised SQL built from request data; a secret in
                  committed source; an auth check removed from a route.
  Does NOT:       a theoretical null on a value the caller has already validated;
                  a missing test.

HIGH — a defect that will cause incorrect behaviour under conditions that occur
  in normal operation.
  Qualifies:      an unhandled error path on a network call in a request handler;
                  an off-by-one in pagination; a race on a shared counter.
  Does NOT:       inefficient-but-correct code; naming; a TODO comment.

MEDIUM — correctness risk only under unusual conditions. Report, do not block.

Do NOT report: formatting, naming, subjective structure preferences, or anything
the linter already enforces.

For each finding give: file, line, the concrete failure scenario (inputs → wrong
result), and the minimal fix. If you cannot state the failure scenario in one
sentence, it is not a finding.
Four properties of criteria that work
  1. Categorical, not scalar. Named severities with definitions beat a 1–10 score, because a category has a test and a number has a vibe.
  2. Illustrated both ways. What qualifies and what does not. The negative examples do most of the precision work.
  3. Anchored in observable consequences. “Causes incorrect behaviour under conditions that occur in normal operation” is checkable; “important” is not.
  4. Carrying a self-check. “If you cannot state the failure scenario in one sentence, it is not a finding” converts the criterion into an action the model performs per candidate.
Why self-reported confidence keeps appearing — and keeps being wrong It is intuitive and it is easy to implement, which is why it is written as a plausible option in item after item. It fails because a model's stated confidence is not calibrated against its accuracy: the cases it gets wrong are disproportionately cases it feels sure about. Confidence can be used — but only after being calibrated against labelled data, per field, as in 5.5. Raw introspective confidence as a routing threshold is a distractor.
The precision/recall framing the exam expects In a workflow a human must trust, false positives cost more than false negatives, because they destroy the trust that makes any of the output useful. A reviewer that catches 70% of real issues and is right nearly every time it speaks gets read; one that catches 95% and is wrong two-thirds of the time gets muted. When a stem describes people ignoring or bypassing an automated check, precision is the objective.
“Only flag issues you are highly confident about” and “only flag issues where you can state a concrete failing input”. Why is the second so much better?
The second is a test the model can actually run. It must produce an artefact — the failing input — and if it cannot, the finding is dropped by construction. The first asks for an introspective judgement with no external referent, which the model will answer, unreliably. Prefer criteria that force a checkable artefact over criteria that ask for a feeling.

4.2 · Few-shot prompting

Two to four examples, chosen for the cases that are actually hard. Their job is to demonstrate the decision boundary, not to pad the prompt with easy cases the model already handles.

Use few-shot whenBecause
The classification boundary is genuinely ambiguousA worked case draws the line more precisely than a paragraph describing it
The output format is specific and hard to describeOne demonstration beats three sentences of specification
Inputs vary in structure — invoices from forty suppliersExamples across the variation teach that the fields are the target, not the layout
Domain conventions are non-obvious“Net 30 from invoice date unless a delivery date is stated” is easier shown than argued
Choosing the examples Pick the cases that are hard, representative and diverse. Two examples of the same easy pattern teach nothing and cost tokens. One example of each confusable pair — the case that looks like A but is B, and the reverse — is worth ten easy ones. Include at least one negative or edge case: the document where the field is genuinely absent and the correct output is null, so the model learns that absence is representable.
Few-shot does not generalise to unseen structure A recurring stem: extraction works on the four supplier formats in the examples and fails on a fifth. The distractor is “add an example for every supplier format”, which does not scale and merely postpones the problem. The credited direction is examples that are deliberately structurally varied, plus field descriptions that define the field semantically (“the grand total including tax, wherever it appears”) rather than positionally (“the number in the bottom right”).
How many examples, and does more always help?
Two to four is the working range for most tasks on this exam. More is not monotonically better: examples consume context, they can over-anchor the model on their specific surface features, and a long example block pushes the actual input toward the low-attention middle. If four well-chosen examples do not fix it, the problem is usually the criteria or the schema, not the example count.

4.4 · Validation, retry and feedback loops

Validate the extraction, and when it fails, retry with enough information for the second attempt to differ.

def extract_with_retry(document, max_attempts=2):
    messages = [{"role": "user", "content": build_prompt(document)}]

    for attempt in range(max_attempts + 1):
        data = call_with_forced_tool(messages)
        errors = validate(data)                 # schema + business rules
        if not errors:
            return data, None

        if attempt == max_attempts:
            break

        # The retry must carry ALL THREE, or it is just a re-roll:
        messages += [
            {"role": "assistant", "content": json.dumps(data)},          # 1. what it produced
            {"role": "user", "content":                                  # 2. the specific error
                f"That output failed validation: {errors}. "
                f"Correct only those fields and return the tool call again. "
                f"The source document is above."},                       # 3. the document, still in context
        ]

    return None, {"status": "needs_human_review", "errors": errors, "last_attempt": data}
FailureRetry helps?Because
Malformed JSON / missing key / wrong typeYesA structural mistake the model can see and correct once it is named
Enum violationYesNaming the permitted values usually resolves it in one attempt
Business-rule violation — line items do not sum to the totalSometimesIf it was an arithmetic slip, yes. If the document itself is inconsistent, no — and that is a finding, not an error
Wrong value, correctly shapedNoThe same reasoning on the same input yields the same answer. You need better field descriptions or examples
The value is not in the documentNoRetrying an absent fact produces a more confident invention. Route to human review or supply the missing source
Bound it, and make the give-up path useful Two attempts, occasionally three. Beyond that you are paying for the same failure repeatedly. The exit path matters as much as the retry: a record that goes to human review should carry the document reference, the best attempt, and which specific validation failed, so the human starts at the problem. Silently dropping the record, or writing a partially-invalid one, are both distractors.
Instrument the failures, do not just handle them Add a field that records why the model made the call it did — for example a detected_pattern or evidence_span alongside a classification. When 8% of records need review, that field turns an opaque failure pile into a distribution you can act on: “61% of failures are the same three supplier layouts” is a fixable finding. This is the same instinct as annotating gaps in 5.6.
An extraction pipeline retries five times with the same prompt and logs the final failure. What is wrong on both counts?
The retries carry no new information, so attempts two through five are the same computation at the same price — a re-roll, not a correction. A retry must include the failed output and the specific validation error, and the source document must still be in context. And the log is a dead end: the failure should route into a review queue with the document reference and the failing field, so a human can resolve it and so the failure distribution is analysable.

4.5 · Batch processing strategies

The Message Batches API takes a set of independent requests and processes them asynchronously at roughly half the cost, returning results within up to 24 hours (usually much sooner). Each request carries a custom_id you use to match results back — results are not guaranteed to come back in submission order.

Batch is right whenBatch is wrong when
Nobody is waiting — nightly reprocessing, backfills, periodic auditsA human or a pipeline stage is blocked on the result
The requests are independent single-shot callsThe work is a multi-turn agent loop with tool calls — batch processes each request as a unit, so an interactive tool-use loop does not fit
The volume is large enough that 50% is real moneyThe volume is small and the latency cost outweighs the saving
The deadline is comfortably beyond 24 hoursThe SLA is hours, or the arithmetic leaves no slack for a resubmission
Do the SLA arithmetic the exam is asking for A stem that says “12,000 documents, results needed within 24 hours” is not a batch question with a comfortable answer — it is a trap. Batch's own window is up to 24 hours, so a run that lands late leaves zero room to resubmit the failures, and there will be failures. Either the deadline needs real slack (48 h+), or you split: batch the bulk, process the tail synchronously.
Partial failure is normal, and the plan for it is part of the answer Individual requests inside a batch can fail while the batch succeeds. A design that assumes all-or-nothing will silently drop records. Correlate by custom_id, identify the failures, and resubmit them — synchronously if the deadline no longer permits another batch window.
Which parts of a document pipeline can be batched: nightly reprocessing of 50,000 archived files, the live upload path, and a weekly quality audit sampling 500 records?
Nightly reprocessing and the weekly audit — both are unattended, independent and deadline-tolerant. The live upload path cannot be batched: a user is waiting. The credited answers on this exam are usually hybrid ones that route by urgency rather than moving everything to batch for the discount or leaving everything synchronous for the latency.

4.6 · Multi-instance and multi-pass review

Two independent ideas that the exam often combines: who reviews (a fresh instance, not the author) and how the work is divided (per-unit passes plus an integration pass).

Why self-review is weak

An instance that just produced a design has, in its own context, the reasoning that justified it. Asking it to critique that work invites it to re-derive the same justification — the failure it is least likely to find is the one baked into its own premises. An independent instance sees the artefact without the argument, which is precisely the position a human reviewer occupies. On the exam, when generation and review happen in the same session, that is the defect.

ArchitectureShapeUse when
Independent review instanceFresh session; sees the artefact and the criteria, not the generation transcriptAlways, when the output is going to be trusted. The single highest-value change in most review pipelines
Per-unit + integration passesOne focused pass per file/section, then one pass over the findings and the whole diffMany units where both local detail and cross-unit consistency matter (1.6)
Specialised reviewersSeparate passes for security, performance, correctness, each with its own criteriaThe criteria genuinely differ and a single prompt would be an unfocused list of everything
Consensus across runsN independent runs; keep what the majority flagsRarely the exam's answer — it multiplies cost to paper over criteria that were never made explicit. Fix the criteria first
Two review distractors that look sophisticated “Have the model critically review its own output before returning” — some benefit, but it does not address the structural problem, and it is offered as an alternative to the fix rather than an addition. “Run three instances and take the majority” — triples cost, and if the criteria are vague all three are vague in the same direction. Reach for consensus only when the stem says explicit criteria are already in place and precision is still short.
A CI pipeline generates code and then reviews it in the same Claude Code session, and the review approves everything. Fix?
A second, independent invocation for the review, given the diff and explicit severity criteria but not the generation session. If the diff spans many files, add the two-pass structure: per-file review, then an integration pass over the findings. Note that both fixes are structural — neither is “tell the reviewer to be stricter”.

Domain 5 · Context Management & Reliability 15%

The smallest domain by weight and the one that decides the most items elsewhere. Six task statements about what an agent knows, what it does when it does not know, and what it tells the next component. The organising idea: an agent's context is a designed artefact, and honest reporting of gaps is a feature, not a failure.

Worked scenario
Ironvale Insurance: the agent that forgot the claim number

Ironvale's claims agent handles conversations that routinely run 40–60 turns, each turn pulling policy documents, claim histories and adjuster notes through MCP tools. Around turn 30, quality collapses: the agent re-asks for the claim number it was given at turn 3, contradicts a coverage decision it communicated at turn 12, and starts summarising the policy incorrectly. The context window is not full — usage sits around 60%. Proposals: a bigger context window, aggressive summarisation every ten turns, and a larger model.

Option on the tableVerdict
Move to a larger context windowNo. At 60% usage capacity is not the constraint. The problem is where the facts are, not whether they fit
Summarise progressively every ten turnsRisky on its own. Repeated summarisation of summaries erodes exactly the specific details — numbers, dates, decisions — that matter most
Use a larger modelNo. Attention dilution across a long conversation is not a capability gap
Maintain a structured “case facts” block — claim number, policy, decisions taken, amounts — kept current and re-anchored near the end of the context; trim verbose tool payloads to the fields actually usedYes. The critical facts stop living in the low-attention middle, and the window stops filling with document dumps nobody re-reads
The takeaway “It forgot” in a long conversation is a placement problem before it is a capacity problem. Facts that must persist should be maintained explicitly, not left to survive by luck in the middle of a transcript.

The progressive-summarisation trap Summarising summaries loses specifics first: the claim number becomes “the customer's claim”, the agreed figure becomes “the amount discussed”. After three rounds the context reads fluently and has quietly stopped containing the facts the conversation depends on. Structure what comes back from subagents A subagent that returns three paragraphs forces the coordinator to re-derive facts from prose. A subagent that returns {findings[], sources[], confidence, gaps_noted[]} lets the coordinator compare results, spot gaps mechanically, and cite accurately. Designing the return shape is a context-management decision as much as an orchestration one.
Context usage is 55% and the agent is contradicting itself. What does that tell you?
That capacity is not the problem, so every capacity-shaped option — bigger window, bigger model, more aggressive compaction — is a distractor. The facts are present but poorly placed or buried under bulk. Extract them into a maintained facts block near the end of the context, and reduce the tool payloads that are consuming the middle.

5.2 · Escalation and ambiguity resolution

An agent must know when to stop being an agent. The exam is unusually precise about what counts as a trigger.

Real escalation triggerWhy it is decidable
The customer explicitly asks for a humanUnambiguous, and it must be honoured immediately — not after one more attempt to help, which is the behaviour that generates complaints
Policy does not cover the case, or an exception is requiredThe agent is being asked to make a decision nobody authorised it to make. Inventing policy is the worst available outcome
The agent cannot make progress — tools failing, information unobtainable, repeated attempts not convergingObservable from the loop's own history, not from a feeling
Two triggers that look right and are not Sentiment. An angry customer with a simple, in-policy problem should be helped, not transferred; a calm customer asking for an unauthorised exception must be escalated. Sentiment is uncorrelated with whether the agent is competent to act. Self-reported confidence. Same objection as 4.1 — uncalibrated introspection, and the cases it is wrong about are the ones it feels sure of. Both appear repeatedly as plausible distractors.

Ambiguity: ask, do not guess

When a lookup returns three matching orders, or a request could mean two different things, the correct behaviour is to present the options and ask — concretely, with enough detail to choose (“the 3 March order for the headphones, or the 19 March order for the cable?”). Picking the most recent, or the highest-value, or the first, is a silent guess that will sometimes act on the wrong object; and a bare “which order do you mean?” puts the work back on the customer. The same rule holds between agents: a subagent facing an ambiguity its brief does not resolve should report it rather than choose.

A customer writes: “This is unacceptable. I want to speak to a person. My order arrived damaged.” What should the agent do?
Escalate immediately, with a structured handoff (1.4) that includes the damage report and everything already established. The temptation — offering to resolve the damaged order first, since it is a simple in-policy case — is precisely the behaviour customers experience as being trapped with a bot. An explicit request for a human is honoured on the turn it is made.

5.3 · Error propagation across multi-agent systems

Extends 2.2 from tools to agents. When a subagent cannot complete its assignment, what crosses back to the coordinator determines whether the system degrades gracefully or lies.

// What a failing subagent should return
{
  "status": "partial",
  "completed": ["academic sources (11 papers)", "government statistics (3 datasets)"],
  "failed": [{
      "source": "industry-reports-api",
      "failure": "timeout after 3 attempts",
      "attempted_query": "manufacturing automation employment 2023-2025",
      "impact": "no industry-side employment figures; the economic section rests on
                 academic estimates only",
      "alternatives": ["public filings of the top 5 manufacturers",
                       "the 2024 trade-association summary already in the workspace"]
  }],
  "findings": [ ... ],           // everything it DID establish
  "confidence": "medium — one of three source classes is missing"
}
The three-step discipline
  1. Recover locally. Retry the transient failure, try the alternative source, degrade to a narrower query. Most failures should never reach the coordinator.
  2. Propagate structure, not an exception. What failed, what was attempted, what impact it has, what alternatives exist, and everything that did succeed.
  3. Annotate the output. The final report states its coverage limits. A conclusion drawn from two of three source classes says so.
The two failure modes, restated because they are worth full marks Swallowing: returning an empty successful result, so the coordinator believes the topic has no material and synthesises a confident report with a silent hole in it. This is the more dangerous of the two and the exam treats it as such. Crashing: propagating an exception that terminates the whole run, so one flaky API costs you four subagents' completed work.
Coverage annotation is the mark of a correct answer Options that produce a clean-looking report from incomplete data are wrong even when the data gap was unavoidable. The credited answer nearly always includes telling the reader — or the coordinator — what is missing and what that does to the conclusion.
One of four research subagents fails entirely. What does the coordinator do?
First decide whether the missing facet is essential. If it is, retry it — possibly with a different source or a narrower query — before synthesising. If it cannot be recovered, synthesise from the three that succeeded and annotate the report with the gap and its effect on the conclusions. Aborting the run discards three subagents' work; synthesising silently produces a document that reads as complete and is not.

5.4 · Context in large codebase exploration

The developer-productivity scenario in concrete form: understanding a large unfamiliar system without the understanding itself consuming the window.

TechniqueMechanics
Delegate the sweepAn exploration subagent with Read, Grep, Glob reads forty files and returns a structured map. Forty files' content never enters your context

Whenever a stem describes long-running work that loses its place — or a session that degrades after exploration — the answer involves moving state out of the conversation.
A migration across 200 files is repeatedly interrupted and each resumption re-does work. Design the fix.
A manifest file listing every file with a status — pending, done, failed with reason. The agent reads the manifest at the start of each run, works the pending entries, and updates it after each one. Resumption becomes trivial and idempotent, progress is visible to humans, and no context needs to survive between runs. Compare the wrong answers: a bigger context window does not survive an interruption, and “keep the session open” is not a design.

5.5 · Human review workflows and confidence calibration

You cannot review everything, so review the right things. Two ideas: aggregate metrics hide segment failures, and confidence is only useful once calibrated.

The aggregate-accuracy trap “94% accuracy” across 10,000 documents is compatible with 99% on the nine common formats and 40% on the tenth — and if that tenth is your highest-value customer, the aggregate is actively misleading. Random sampling reproduces the same blindness, because it draws proportionally from the segments and never gathers enough of the rare one to notice. Stratify: sample by document type, by source, by value band, by extracted-field confidence, so each segment gets its own measured accuracy.
Routing ruleWhy it beats reviewing a flat sample
Field-level confidence, calibratedA record can be certain in nine fields and doubtful in one. Route the field, not the whole record — far less human time for the same risk reduction
Value or risk thresholdsA $2,000,000 contract deserves review at a confidence a $40 invoice does not. Expected cost of an error, not probability alone
Novelty routingFirst N documents from a new supplier or a new layout go to review regardless of confidence — that is where unknown failure modes live
Validation-failure routingAnything the retry loop could not resolve (4.4), with the specific failure attached
What “calibrated” means, precisely That when the system reports 0.8 confidence, it is right about 80% of the time — established by comparing confidence against a labelled set, per field, and adjusting the mapping. Raw self-reported confidence has no such property. This is the distinction between the credited answer and the 4.1 distractor: confidence is usable after calibration against ground truth, never straight out of the model.
Review is a feedback loop, not a filter Corrections humans make are labelled data. Feed them back: they improve field descriptions, supply the next few-shot examples, recalibrate the confidence mapping, and tell you which segments need routing rules. A review queue that only fixes records and never changes the system is a permanent cost centre.
Aggregate accuracy is 94% and the business is satisfied, but one client complains constantly. Where do you look?
At that client's segment specifically. Stratify the evaluation by source and document type and you will very likely find a format-specific failure that the aggregate averages away. The remedies follow the diagnosis — few-shot examples of that layout, sharper field descriptions, and a routing rule sending that segment to review until its measured accuracy recovers.

5.6 · Provenance and uncertainty in multi-source synthesis

The research scenario's reliability half. A synthesised report is only usable if a reader can trace a claim to a source and can see where the sources disagreed.

RequirementMechanism
Claim–source mappingEvery subagent returns findings with their source attached, and the mapping survives synthesis. Citations reconstructed after the fact are how misattribution happens
Conflict annotationTwo sources disagree → report both, with their dates and their basis, and say why they may differ. Silently choosing one destroys information the reader needs
RecencyCarry publication dates. In a fast-moving area a 2021 figure and a 2025 figure are not a contradiction — they are a trend, but only if the dates survived
Coverage limitsState what could not be established and why (5.3)
Confidence that reflects evidence“Three independent sources agree” and “one blog post” are different epistemic states and should read differently
Appropriate renderingComparisons as tables, sequences as timelines, disagreements as side-by-side. Content shape should follow content type
The most tempting wrong answer in this task statement “Have the synthesis agent resolve conflicts by selecting the most authoritative source.” It produces a cleaner document and destroys the signal. Authority is not truth, the reader cannot see what was discarded, and a genuine disagreement between two credible sources is itself a finding. Annotate; do not adjudicate silently.
Two subagents return contradictory figures for the same statistic. What does the coordinator do?
Report both, with source, date and methodology where known, and note the likely reason for the divergence — different populations, different years, different definitions. If resolving it matters to the conclusion, spawn a targeted subagent to investigate the discrepancy (iterative refinement, 1.2). What it must not do is pick one and present it as settled.

Exam-day playbook

Pacing

Sixty items in 120 minutes is two minutes each, but the time is not evenly distributed: four scenario texts need reading, and the items that hang off them are then quicker. Budget roughly 3–4 minutes to read each scenario properly the first time it appears, then 90 seconds to two minutes per item. Flag-and-return anything that takes more than three minutes — leaving a hard item to come back to costs you nothing, and burning eight minutes on it costs you three easier items.

A five-step routine for a scenario item

  1. Find the evidence sentence. The stem always contains one sentence with the measurement or the observation: “47 of 12,000”, “70% of comments are not actionable”, “the coordinator assigned these three subtasks”, “context usage is 60%”. Everything else is setting.
  2. Name the component that produced it. Read the evidence back to its cause. Narrow coverage → the decomposition. Misrouted tool → the descriptions. A rate of a forbidden action → the enforcement surface. Contradiction late in a conversation → context placement.
  3. Read the scope word in the question. “First step”, “most effective”, “highest impact” → the cheapest change with the largest effect. “Design”, “architecture”, “how should the system” → a structural answer is permitted. “Select two” → two independent contributions, not one answer split in half.
  4. Eliminate on the distractor patterns. Usually two options fall immediately: one is guidance where enforcement is required, one blames a component the evidence exonerates.
  5. Break the tie on the scenario's stated goal. First-contact resolution, false-positive rate, latency SLA, coverage. The option that protects the named metric while fixing the cause is the credited one.
Three sentence-level tells Options containing “instruct”, “remind”, “emphasise”, “encourage” against a hard requirement are usually distractors. Options containing “also”, “in addition”, “as well as” often bundle a correct idea with an incorrect one — check both halves, because a half-wrong option is wholly wrong. Options that require machinery the guide declares out of scope — fine-tuning, vector-store internals, cloud-specific deployment, streaming — are almost never credited.
Multiple-response items The item tells you how many to select, and there is no partial credit. Pick your certain answer first, then test each remaining option independently against the stem — do not pick the one that “goes with” your first choice. Two correct answers on this exam are usually from different layers: one structural change and one process change, or one preventive and one diagnostic.
The last ten minutes Review flagged items only, and change an answer only if you can name the specific fact you had wrong. A vague sense that another option “feels better” is not evidence, and on a well-constructed paper second-guessing without a reason costs more marks than it gains.

One-page cheat sheet

Where the guarantee lives

  • Tool not granted → capability impossible
  • Dispatcher precondition → ordering enforced
  • PreToolUse hook → call denied
  • PostToolUse hook → result normalised
  • Schema → invalid value inexpressible
  • Prompt → guidance only, non-zero failure rate

The loop

  • Branch on stop_reason before reading content
  • Assistant turn back in history verbatim
  • One tool_result per tool_use, in a user message
  • Errors return with is_error, do not throw
  • Own the termination condition

Coordinator / subagent

  • Subagent context is empty — brief it fully
  • Only the final message returns
  • Decomposition is the coverage ceiling
  • Scopes disjoint and named
  • Evaluate between rounds → targeted refinement
  • Several Task calls in one turn = parallel

Tool descriptions

  • What it does · when to use · when not to, naming the sibling · what it returns
  • Describe every parameter: units, format, provenance
  • Split over-generic tools; scope sets per role
  • tool_choice: auto / any / forced / none

Errors

  • transient → retry · validation → fix and retry
  • business → stop and explain · permission → escalate
  • Recover locally, propagate structure, annotate coverage
  • Empty result ≠ could not check
