How to read the decision tables Most of this exam is not "do you know what Projects are" but "given this situation, what do you do first". Wherever there is a table with a Situation column, that table is the answerable unit. Memorise the rows, not the prose around them.

Primer 1 · What Claude is, and what a turn actually is

Every question on this exam ultimately rests on one fact about how the technology works, so it is worth being precise about it. Claude is a large language model: given the text so far, it produces the text that most plausibly comes next. It is extremely good at that. What it is not is a database lookup, a calculator, or a search engine. Those distinctions generate most of the exam's correct answers.

What follows from "generates plausible text"

  • A fact Claude was given in the conversation can be quoted accurately.
  • A fact it was not given is reconstructed from training — and reconstruction of a specific-looking detail (a subsection number, a date, a figure, a citation) is exactly where fabrication happens.
  • Fluency and accuracy are independent. A wrong answer reads exactly as confidently as a right one.
  • The same prompt can produce different answers on different runs. Output is not deterministic.

The turn, and what is in it

  • The model sees the whole conversation each turn — your messages, its messages, attached files, Project instructions, Project knowledge, and any memory or connector content brought in.
  • It does not remember anything outside that. A new chat starts blank unless memory or a Project carries something in.
  • Everything in the window competes for attention. Adding irrelevant material makes answers worse, not merely more expensive.
  • Training data has a cutoff. Anything after it must arrive via web search, Research, a connector, or your own upload.
The trap this primer exists to prevent The single most-tested wrong answer on this exam is asking the model to assess itself — "ask Claude how confident it is", "ask Claude to check its own work and send it if it says it is fine". A confidence rating is generated text produced by the same process that produced the error. It is not a measurement. Self-review can surface candidates worth checking; it can never substitute for checking them.

What is in scope for an Associate, and what is not

The exam guide is explicit that this credential is for professionals who use Claude as a productivity tool, and that architecture and API work belongs to the Architect and Developer credentials. Several items turn on you knowing which side of that line something falls on.

Yours as an AssociateEscalate to an Architect or Developer

Configuring a Project: instructions, knowledge, connectors Building against the Claude API, SDK, or Claude Code
Evaluating outputs; setting up a human review step Automated evaluation harnesses and CI gates
Choosing a model tier and product feature for a task Programmatic model routing, batch pipelines, cost engineering at scale
Redesigning a team workflow around Claude Systems integration, custom MCP servers, authentication
Applying your organisation's AI policy to a task Writing the policy's technical controls, DPIAs, tenancy design
Escalation is a two-way test Candidates over-learn "escalate when unsure" and then pick escalation for things an Associate plainly owns — adding a file to Project knowledge, rewriting a weak prompt, deciding an output needs a second reader. Both directions are scored. Ask: does this require writing code or changing a system? If no, it is yours.
Real scenario
Meridian Mutual: “it knew the date of birth yesterday”

A claims handler pastes a 40-page medical report into a conversation and gets a good summary. Twenty minutes later, in a new conversation, they ask “what was the claimant’s date of birth?” and get a confident, completely invented date. They raise it as a bug: the system has forgotten something it knew.

Nothing was forgotten, because nothing was ever stored. A turn consists of everything sent in that request — the instructions, the conversation so far, and any attached material — and the model produces a continuation of it. The new conversation contained a question about a report that was not in it, and a fluent answer is what the model produces when the material is absent. A colleague who asked the same question in the original conversation got the right answer, because there the report was still part of the input.

The exam leans on this constantly. “It forgot”, “it made up a figure” and “it gave a different answer to my colleague” usually all reduce to the same cause: what was in the request differed.

Takeaway · A turn is everything you send, every time. The model keeps nothing of its own between conversations, so anything that must be available every time has to be put there deliberately — by attaching it, or by configuring it.

Claude produces a summary of an internal policy with a heading and a clause number that do not exist in the document you attached. What is the most precise description of what happened?
It generated the shape of a policy document rather than reading yours closely — clause numbers and headings are highly predictable text, so they are among the first things fabricated. Note the important detail for the exam: the source was attached and it still happened. Attaching a source reduces fabrication, it does not eliminate it, which is why verification of specific citations against the source remains a required step rather than an optional one.
You run the same prompt twice and get two different summaries. Which one is right, and what should you conclude?
Neither is authoritative because it is a second run — output is not deterministic, so difference between runs tells you nothing about which is correct. What it does tell you is useful: variation on the points that matter means your prompt underspecified them. Comparing two runs is a good technique for finding unstable claims to check, and a bad technique for deciding which claim is true.
A colleague says "Claude has all our policies in it, it was trained on the internet". Correct them in one sentence.
Training data does not include your internal documents, and even for public material the model reconstructs rather than retrieves — so anything you need it to be accurate about must be supplied in the conversation, in Project knowledge, or through a connector.

Primer 2 · The product surface, feature by feature

Domain 3 asks you to select product features by name, and Domain 5 asks you to configure two of them. This is the table to know cold. Availability by plan is version-sensitive — verify close to your exam date — but the purpose of each surface is what items turn on.

SurfaceWhat it isReach for it when
Chat A single conversation. Nothing carried in except memory, if enabled. The task is one-off and self-contained, and no durable context is needed.
Projects A workspace with its own instructions, its own knowledge (uploaded files and other sources), its own chat history, and — where memory is on — its own separate memory. The same context is needed repeatedly: brand guidelines, a style guide, product docs, a client's background. Anything you would otherwise paste into every chat.
Artifacts Substantial, self-contained content rendered in its own panel beside the chat — documents, code, diagrams, small apps. Persistent, editable in place, and shareable. The output is a deliverable you will revise, reuse or send onward, rather than an answer you read once.
Research An agentic multi-step investigation: Claude decomposes the question, searches repeatedly across the web and any connected internal sources, and returns a synthesis with citations. Takes minutes, not seconds. The question needs many sources reconciled, or spans internal and external material. On paid plans.
Connectors Live links to systems — Google Drive, Gmail, Calendar, and others — so Claude can search and use your existing content without you uploading it. The source of truth changes and lives in a connected system, so an upload would go stale.
Memory Entries Claude generates from your chats so later conversations build on earlier ones. Toggled in Settings. Projects get their own separate memory, which keeps unrelated work from mixing. You want continuity across sessions. Turn it off, or use an incognito chat, when you do not.
Incognito chat A chat that is not saved to history and does not write to memory. Available outside Projects. A one-off sensitive or exploratory conversation you do not want retained or influencing later answers.
Skills Packaged, reusable instructions (and optional files) for a procedure you repeat, invoked when relevant rather than pasted every time. A repeatable multi-step procedure with a known house format — a monthly report, a specific document style — that is too long to live in Project instructions.
Code execution / file creation Claude runs code in a sandbox to analyse data and produce real files — spreadsheets, documents, decks. The task involves arithmetic over a real dataset, or the deliverable must be an actual file.
Claude Code An agentic coding tool for engineers, driven from the terminal or IDE. Out of scope for this credential. If an item's real answer is "use Claude Code", the Associate answer is to involve a Developer.
Rule — Projects for recurring context, chat for one-offs, Research for many sources Three near-miss pairs the exam likes:
  • Project vs re-pasting. If context is needed more than once, it belongs in a Project. Re-pasting is the wrong answer even when it works.
  • Project knowledge vs a connector. A static reference document → upload it. A source that changes underneath you → connect it, so it cannot go stale.
  • Research vs a normal chat with search. Research is for questions needing many sources reconciled. Using it for a quick lookup wastes minutes; using a quick lookup for a genuine research question produces a thin answer from one source.

Artifact, inline, or structured file?

Objective 2.6 asks this directly, and it recurs across Domains 2 and 4.

FormatChoose it whenSignal in the stem
InlineShort, conversational, read once and discarded — an answer, a recommendation, a quick comparison."tell me", "which should we", "quick"
ArtifactSubstantial and self-contained; will be edited, iterated, reused or shared."draft the", "we will revise", "send to the team", "template"
Structured data / fileThe output feeds another system or person's tool — a spreadsheet, a table with fixed columns, CSV, JSON."import into", "upload to the tracker", "one row per", "the finance system expects"
Trap — format is chosen by destination, not by length A three-line answer that has to be pasted into a ticketing system as fixed fields is structured. A long, discursive explanation the reader will consume once and never touch again is inline. The wrong answer reasons from size; the right answer reasons from what happens to the output next.
Real scenario
Beckford & Hale: four requests in one week, four different features

A consultancy’s partners asked for four things. The whole of Domain 3 is the ability to hear which feature each one is asking for:

What they asked forThe feature
“Every draft should come out in the firm’s house style, with our citation rule, without anyone having to remember to ask.” Project instructions — standing rules that apply to every conversation in the Project.
“Last quarter’s benchmarking pack should be available to everyone on the engagement.” Project knowledge — uploaded files the conversations can draw on, with a named owner who keeps them current.
“I want to pull the ticket data straight from the client’s tracker instead of exporting a CSV every Monday.” A connector to that system — live data, no copy-paste, and access governed by the client contract.
“Turning interview notes into our standard finding template is the same six steps every time.” A Skill — a packaged, repeatable procedure invoked when it is needed rather than applied to everything.

Choosing the wrong one is usually the whole question: house style in a Skill applies only when someone remembers to invoke it, and a rate card in the instructions instead of in knowledge means editing configuration every time a price changes.

Takeaway · Instructions are for what must be true every time; knowledge is for the material to draw on; connectors are for live data in another system; Skills are for a repeatable procedure. The exam gives you the sentence and wants the feature.

Your team asks Claude the same twelve questions about a product every week, pasting the spec sheet in each time. What is the fix, and what is the wrong version of the fix?
Create a Project, put the spec sheet in Project knowledge and the standing rules in Project instructions, and have the team work in it. The wrong version of the fix is to write a longer, better prompt that everyone copies — it addresses the symptom (bad prompts) and not the cause (durable context living in nobody's configuration). A second wrong version: putting the spec sheet in the instructions. Instructions are for how to behave; knowledge is for reference material.
The spec sheet is revised every fortnight by another team, in a shared Drive folder. Does that change your answer?
Yes — that is the connector case. An upload is a snapshot and will silently go stale between revisions, which produces confidently wrong answers with no visible failure. Connect the Drive source so the current document is read at query time. If a connector is not available to you, the compensating control is an explicit owner and cadence for re-uploading, plus a version and date noted in the Project instructions.
You need a competitor landscape covering eight vendors, using public sources and your own internal win/loss notes in Google Drive. Which surface?
Research, with the Drive connector enabled — it is the one surface designed to work across internal context and the web in a single multi-step investigation, and it returns citations you can check. Note the two near-misses: a plain chat with web search gives you a thinner answer from fewer sources, and uploading the win/loss notes manually into a normal chat throws away the connector and the citations.

Primer 3 · Model tiers — Haiku, Sonnet, Opus

Objective 3.2 names the three tiers explicitly. What the exam tests is not version numbers but the trade-off each tier represents, and your willingness to actually choose.

TierPositionFitsPoor fit
Haiku Fastest, lowest cost, least capable at hard reasoning High-volume, well-specified, shallow work: classification, tagging, routing, short replies from a template, simple extraction, first-pass triage Multi-step reasoning, nuanced judgement, long documents needing synthesis, anything consequential without review
Sonnet The balanced default — strong reasoning at moderate cost and latency Most day-to-day professional work: drafting, analysis, summarising, editing, moderate-complexity reasoning. Start here unless you have a reason not to Being used as the answer to everything without a moment's thought about whether the task is trivially easy or genuinely hard
Opus Most capable at complex reasoning; highest cost and latency Genuinely hard work: ambiguous multi-constraint problems, deep synthesis across many sources, high-stakes analysis where an error is expensive, novel strategy Bulk simple tasks, latency-sensitive interactive work, anything where the marginal quality is not worth the marginal cost
The decision rule the exam grades on Match the tier to the hardest part of the task, not to its importance and not to its length. An important task that is mechanically simple does not need the top tier; a low-profile task that requires reconciling contradictory sources might. Where volume is high and the work is easy, a cheaper, faster tier is the correct professional choice — and the exam's own sample question makes exactly that point.
Sound reasoning
  • "Two thousand short replies a day from a known template — the fast tier, with sampling review."
  • "One board memo reconciling four conflicting forecasts — the top tier, once."
  • "Split it: cheap tier triages the queue, top tier handles the 6% it flags as complex."
  • "Interactive tool where users wait — bias to the faster tier and accept slightly less depth."
Scored wrong
  • "Use the most capable model for everything, to be safe." Failure to select is not caution.
  • "Use the cheapest model everywhere and review more." You have moved cost onto people, usually at a worse rate.
  • "Switch platforms." Never the answer to a cost/quality trade-off on this exam.
  • "Disable features to save money." Features are not the cost driver, and this breaks the task.

Extended thinking

Where available, extended thinking lets the model reason at greater length before answering. Treat it as a dial on the same axis as tier selection: it buys accuracy on hard, multi-step problems at the price of time and cost. It is the wrong lever for a task that is failing because it lacks information — no amount of thinking recovers a document you did not attach.

Version-sensitive Specific model names, versions, context sizes and prices change frequently. The exam is written to the tier semantics above, which are stable. Do not spend study time memorising model version strings; do spend five minutes checking the current line-up before exam day.
Real scenario
Northwind Retail: 30,000 descriptions and one budget

The task: rewrite 30,000 product descriptions, of which 500 are flagship items that carry the brand. The first plan was the strongest tier for all 30,000, which came back at several times the available budget. The second was the fastest tier for all 30,000, which produced acceptable copy for the long tail and flat, forgettable copy for the flagship items — the ones the money was for.

The plan that worked splits the decision per step: the fast tier for the 29,500 routine descriptions, where a small quality difference is genuinely invisible on a category page; the strongest tier for the 500 flagship items, and for the prompt-development work itself, where a better draft saves days of iteration; and a mid tier for the QA pass that scores a sample of the output.

Takeaway · Tier is chosen per step, by consequence and volume — not once per project. High volume plus low consequence is the fast tier’s case; low volume plus high consequence is what you pay for.

Fifteen thousand support emails a month need routing into eight categories, and roughly 4% need a nuanced apology drafted. Design the model choice.
Two tiers, split by difficulty. Classification into eight known categories is exactly the fast, cheap tier's job — high volume, well specified, shallow. The 4% needing a written apology with judgement about tone and liability goes to a stronger tier. The wrong answers are the two uniform ones: top tier for all fifteen thousand (paying complex-reasoning prices for a labelling task), or cheap tier for all of it (the 4% is where the reputational damage lives).
A stakeholder insists on the most capable model for a weekly status roll-up because "the exec team reads it". Respond.
Importance of the audience is not the same as difficulty of the task. Summarising structured status inputs into a known format is not hard reasoning; what protects an exec-facing document is a review step and a good template, not a bigger model. The professional answer names the real control: keep the balanced tier, add human review before it goes out, and spend the saved budget where the reasoning is actually hard.
An analysis on the balanced tier keeps missing a subtlety in a 90-page contract. Escalate the tier, or something else?
Diagnose before escalating — this is the Domain 7 habit. If the subtlety lives in a section that was never in the context, or is spread across sections the model was asked about separately, the fix is input and decomposition, not capability: section-by-section passes with an explicit checklist, then a synthesis pass. Escalate the tier when you have confirmed the material was present and the model still failed to reason across it. Paying for the top tier to compensate for a missing attachment is the classic wasted upgrade.

Primer 4 · Context, memory, and the conversation lifecycle

Objective 3.4 is unusually specific — "when to restart, summarize, or persist" — which means there are items where those three are the options and you have to pick correctly. Here is the distinction.

ActionSituationWhy it is right
Restart (new chat) The topic has genuinely changed, or a long thread has accumulated wrong turns, abandoned drafts and contradictory instructions that keep resurfacing in answers. Everything in the window influences the answer, including your own superseded instructions. A clean chat removes the interference rather than arguing with it.
Summarise and carry forward The thread is long but the work is unfinished and its conclusions still matter. Ask for a structured hand-off — decisions made, constraints agreed, open questions, current draft — and paste it into a fresh chat. You keep the conclusions and drop the debris.
Persist (Project / knowledge / instructions) The context will be needed again next week and by other people, not just later in this thread. Configuration outlives conversations. This is the only one of the three that helps a colleague.
Trap — "just keep the conversation going" Long threads fail in two ways the exam likes to describe without naming: answers start drifting back to earlier, superseded versions of the task, and quality degrades even though nothing errored. Neither is fixed by adding another instruction to the same thread. If a stem describes a long conversation whose answers are getting worse or reverting, the answer is almost always restart-with-summary — not a firmer prompt.

Memory, and its boundaries

  • Memory is generated from your chats and applied to later ones, so Claude builds up understanding instead of starting blank every time. It is toggled in Settings.
  • Each Project has its own separate memory. Client work does not bleed into other client work, and confidential threads stay contained. Treat this as a governance feature, because items do.
  • Incognito chats are not saved to history and do not write to memory — the tool for a one-off sensitive conversation. They are available outside Projects.
  • Memory is a convenience layer, not a record system. Something the business must be able to find later belongs in a document or a Project's knowledge, not in memory.

Project knowledge at scale

As a Project's knowledge grows past what fits comfortably in context, retrieval takes over: on paid plans Claude switches to a retrieval mode that expands effective capacity substantially while holding response quality. Two practical consequences the exam cares about:

  • More is not automatically better. Twelve curated documents beat sixty overlapping ones, because retrieval has less chance of surfacing a superseded version. Curation is part of configuration.
  • Duplicates and stale drafts are actively harmful. If v3 and v7 of a policy are both in knowledge, some answers will cite v3. Removing the old one is the fix; instructing Claude to "use the latest" is not.
Real scenario
Tessellate Software: ninety turns in, the conversation starts arguing with itself

A researcher’s competitor analysis has run to about ninety turns. The pricing table from turn 4 is now being blended with a hypothetical scenario from turn 60, and the answers are getting less reliable, not more. Objective 3.4 asks exactly this: restart, summarise, or persist?

  • Restart — the next competitor is a new task with new material. Nothing from this conversation helps, and carrying it forward is what caused the problem. Start clean.
  • Summarise — the analysis in progress is still one task. Write the conclusions and open questions into a compact summary and carry that into a fresh conversation, not the ninety turns.
  • Persist — the pricing table is needed every week by four people. It does not belong in a conversation at all; it belongs in the Project as a file with an owner.

They did all three, for the three different pieces. The mistake to recognise on the exam is treating a long conversation as a filing system: material that is needed repeatedly should be configuration, and a conversation that has changed topic should be a new conversation.

Takeaway · Restart when the task changed, summarise when the task continues but the history is baggage, persist when the material is needed again next week. Long conversations degrade; that is a lifecycle decision, not a model problem.

Forty turns into a campaign-planning chat, Claude keeps reintroducing a channel you ruled out at turn nine. What do you do?
Ask for a structured summary — decisions, constraints, the ruled-out list with reasons, open questions, current draft — then start a fresh chat with that summary as the opening context. The ruled-out channel is still in the window and still influencing generation; repeating "don't include it" adds another instruction to a thread that already contains the contradiction. If this campaign will run for weeks, also persist the constraints into a Project so turn 40 of the next chat does not repeat the problem.
Your Project knowledge has grown to sixty files, including three versions of the pricing sheet, and answers have become less reliable. First action?
Curate: remove superseded versions so exactly one current pricing sheet remains, and drop documents no longer relevant to the Project's purpose. Reliability fell because retrieval now has several plausible and mutually contradictory sources to choose from. Adding an instruction that says "always use the newest pricing sheet" leaves the contradiction in place and depends on the model resolving it correctly every time.
You need one exploratory conversation about a possible reorganisation, and you do not want it shaping later answers or sitting in your history. What do you use?
An incognito chat — it is not saved to history and does not write to memory. Note the constraint that makes this a real exam item: incognito is available for chats outside Projects, so if you are working inside a Project you will not find it there. The alternatives are to have the conversation outside the Project, or to turn memory generation off in Settings for that period.

Domain 1 · Prompting and Task Execution 14% · ~8 items

Four objectives. The exam does not ask you to recite prompt-engineering vocabulary; it gives you a weak prompt and a bad output and asks what to change. Every answer here is a specific structural change, never "be clearer".

Real scenario
Larkfield Council: “draft a letter refusing this blue-badge application”

The output. The decision was right. Everything else was wrong: no explanation of the appeal route, a tone the ombudsman would have had something to say about, and a citation to “paragraph 4.2 of the mobility policy” that does not exist. The officer’s conclusion was that the tool was not up to the job.

The prompt, rebuilt around the five components.

  • Role and audience — a council officer writing to a resident who has just been refused something they applied for.
  • Context — the application, the decision and the reason, and the relevant policy extract attached. The fabricated paragraph number existed because no policy was ever supplied.
  • Task — one verb: draft the refusal letter.
  • Constraints — plain English, under 400 words, cite only the attached policy, set out the appeal route, and write “not stated” rather than inferring anything that is not in the papers.
  • Output shape — the council’s four-part letter template.

Same model, same document, same officer. Every item in this domain works like this: you are shown a weak prompt and a bad output, and the answer is a specific structural change.

Takeaway · Each missing component produces a characteristic failure — missing context produces fabrication, missing audience produces the wrong register, missing output shape produces something you reformat by hand. Name the missing part; never answer “be clearer”.

1.1 · Create effective prompts for business and technical tasks

A prompt that reliably works carries five things. Missing any one of them produces a characteristic failure, and the exam describes the failure and expects you to name the missing part.

ComponentWhat it suppliesThe failure when it is missing
Role / audienceWho is writing, and who is readingCorrect content pitched at the wrong level — jargon for a customer, or baby-talk for a specialist
ContextThe source material and the situationFabricated specifics. The model fills the gap you left, because that is what it does
TaskOne clear verb and object: summarise, compare, draft, classify, extractAn essay when you wanted a decision, or a decision when you wanted the options
ConstraintsLength, tone, what to exclude, what must be cited, what to do when information is missingOutput that is technically responsive and unusable — too long, off-tone, confidently filling gaps
Output shapeThe format: a table with named columns, five bullets, a memo, JSON, a specific document structureProse you now have to reformat by hand, every single time
The highest-value constraint most people omit Tell the model what to do when the information is not there: "if the document does not state a figure, write not stated — do not estimate". Without that instruction the model's default behaviour is to produce something plausible, because a fluent answer is the objective it was trained on. With it, gaps become visible. On this exam, an option that adds an explicit missing-information rule is very often the right one.

Two prompts, same task

Weak

"Summarise the attached vendor contracts and tell me if there are any risks."

  • No audience — you get a tone at random.
  • "Risks" is undefined, so it invents a taxonomy.
  • No format, so eight contracts come back as eight paragraphs you cannot compare.
  • No missing-data rule, so absent termination clauses get plausible ones.
Strong

"You are preparing a briefing for our procurement lead, who is not a lawyer. From the eight attached contracts, produce one table: vendor, term end date, notice period, auto-renewal (yes/no), liability cap, and any clause that limits our right to terminate for convenience. Quote the clause number for every entry. Where a contract does not address a column, write not stated — do not infer. Then list, in at most five bullets, the contracts you would renegotiate first and why."

  • Comparable output, checkable against sources, gaps visible.
Examples beat adjectives "Professional tone" means little; two paragraphs of our actual house style mean a lot. When an item offers "describe the tone you want in more detail" against "provide two examples of approved output", the examples win. This is the same reason few-shot examples belong in Project instructions for recurring work — see 5.3.
A drafted customer email is accurate but reads as though written for an engineer. Which prompt component was missing, and what is the fix?
Role/audience. The fix is to name the reader and their level explicitly — "a non-technical customer who has already been told their order is delayed" — and, if this is recurring work, to persist an audience definition plus one approved example into Project instructions. Note the distractor shape: "ask Claude to make it friendlier" is a tone adjustment applied after the fact, which will need repeating on every future draft because the underlying prompt still does not say who is reading.
Extractions from 40 invoices are 90% right, but the 10% wrong are all invented values in fields the invoice does not contain. What single line fixes most of it?
An explicit missing-information instruction: "if a field is not present on the invoice, output not stated; never infer or estimate a value." The errors are not a capability problem — the model is doing exactly what an unconstrained generative objective implies. Making absence a legal output is what stops fabrication, and it has the side benefit that the 10% becomes visible instead of silently wrong.
You want the same output shape every week from five different colleagues. Where does the format specification live?
In the Project's instructions, not in five people's individually-written prompts. This is the crossover point between Domain 1 and Domain 5: a prompt component that must be identical across people and weeks is configuration, and configuration belongs in a Project. Leaving it in prompts guarantees drift, and the drift will be blamed on the model.

1.2 · Apply task decomposition techniques to structure complex requests

Decomposition is the answer to a specific, recognisable failure: you asked for several things at once, and the output covers some of them well, some superficially, and quietly drops the rest. The tell in a stem is a request containing the word "and" three times.

Signals that a request needs breaking up

  • Multiple deliverables in one ask — "analyse the data, write the exec summary, and draft the customer note". Effort gets spread; the last item is thinnest.
  • Later steps depend on judgements from earlier ones — you cannot draft recommendations properly in the same breath as discovering what the data says.
  • Volume beyond one pass — sixty documents, forty interviews, a year of tickets. One pass produces a shallow average of everything.
  • You need to check the middle — if an error in step two would invalidate steps three through five, step two needs to be its own reviewable output.
The decomposition rule Break the work at the points where you would want to inspect the intermediate result. That single heuristic produces good decompositions and explains why the exam favours them: each stage becomes separately verifiable, and an error surfaces at the stage that caused it rather than in a final deliverable where you cannot see it.

Worked example — a quarterly business review

#StageWhy it is a separate stage
1Extract the metrics from the four source systems' exports into one tablePurely mechanical and fully checkable. If the numbers are wrong, everything downstream is wrong — so verify here, cheaply
2Identify movements outside normal variation, with the figures attachedAnalytical judgement. You want to see and challenge this list before anything is written about it
3For the top five movements, draft candidate explanations and mark each as evidenced or speculativeThe step where fabrication is most likely, so it is isolated and explicitly labelled
4Write the two-page narrative for the exec audience, using only stage-3 items marked evidencedDrafting is a different task from analysis, with a different audience and tone
5Produce the appendix table of every metric with its sourceMakes the whole thing auditable by whoever reviews it
Trap — decomposition is not the same as "ask again in smaller pieces at random" Two wrong versions appear as distractors. The first is splitting by volume alone — twenty documents at a time with no per-batch structure — which produces twenty inconsistent mini-answers you then have to reconcile by hand. The second is splitting into stages but not carrying the constraints forward, so stage 4 forgets the audience and the exclusions established at stage 1. A decomposition needs a fixed output shape per stage and an explicit hand-off between stages.
"Review these 120 support tickets, find the top themes, quantify each, and write a recommendation memo" produces a memo with three vague themes and no numbers. What went wrong and what do you do?
Four tasks in one request, so the model produced a plausible average of all four rather than doing any of them properly. Decompose: (1) classify all 120 tickets into themes with one row per ticket, (2) aggregate into counts and percentages, (3) review that table yourself — this is where you catch mis-classification cheaply, (4) draft the memo from the reviewed table. Note that the quantification failure is the diagnostic clue: numbers are what get dropped first when a single request is overloaded, because prose about themes is easier to generate than counting.
A stakeholder objects that four prompts is slower than one. What is the honest answer?
It is more steps but usually less total time, because the alternative is one fast bad answer followed by an unbounded number of correction rounds against an output whose errors you cannot localise. Make the real trade-off explicit: decomposition buys you checkpoints, and checkpoints are what let you catch a mis-classification at stage 1 instead of discovering it in a memo that has already gone to the exec team. Where the work recurs, the stages become a documented workflow and the per-run cost falls further.
When is decomposition the wrong answer?
When the task is genuinely one thing and the real problem is elsewhere — a missing source document, the wrong audience, an undefined term, or a model tier that is under-powered for the reasoning involved. Splitting a well-formed single task into stages adds overhead and no checkpoints worth having. The exam does include items where decomposition is the plausible-but-wrong option, and the tell is that the output's problem is accuracy about a fact rather than coverage across several deliverables.

1.4 · Adapt prompting strategies based on task type

The objective names four task types, so expect items that hinge on treating them differently. The core insight: analysis and research want constraint and grounding; brainstorming wants breadth and volume. Applying the wrong posture is the failure mode.

Task typeWhat you wantHow to prompt for it
Analysis Grounded conclusions traceable to the data, with uncertainty visible Attach the data. Ask for the finding and the evidence in adjacent columns. Require it to separate what the data shows from what it suggests, and to state what the data cannot tell you. Ban estimation of absent values
Research Multiple sources reconciled, with disagreements surfaced rather than smoothed over Use Research where the question warrants it. Demand citations. Ask explicitly where sources conflict and which is more authoritative — a synthesis that hides the conflict is the failure
Drafting House voice, right audience, right length, first draft not final copy Name the audience and the purpose; supply an approved example; state length and structure. Iterate on the draft rather than trying to get it perfect in one shot
Brainstorming Range, including options you would not have reached — then a separate, ruthless filter Ask for a specific large number of options and explicitly invite bad and expensive ones. Do not evaluate in the same turn. Filter against your criteria in a second pass
Trap — evaluating while generating Asking for "ten great ideas that fit our budget and brand guidelines" collapses generation and filtering into one turn, and you get six safe ideas you already had. The correct shape is two turns: generate wide with no filter, then apply the criteria as a separate step. Conversely, asking an analysis to "explore possibilities freely" is the mirror error — that is how speculation ends up presented as finding.
Rule — match the posture to the type Analysis and research: constrain, ground, cite, expose uncertainty. Drafting: specify audience and shape, then iterate. Brainstorming: widen first, judge second. An item that applies a research-grade citation demand to a brainstorm, or brainstorm-style openness to a financial analysis, is describing the wrong strategy for the type.
A brainstorm for campaign concepts returns eight predictable ideas. What is wrong with the prompt?
It almost certainly bundled the constraints into the generation ask, so the model pre-filtered to safe options — and it probably asked for a small number, which biases toward the obvious. Ask for twenty-five, explicitly invite ideas that are too expensive, too weird, or off-brand, and forbid evaluation in that turn. Then filter in a second pass against budget and brand. The unusable ideas are not waste; they are what pulls the distribution away from the predictable centre.
An "analysis" of survey data reads persuasively but you cannot tell which claims came from the data. What was misapplied?
A drafting posture was applied to an analysis task — the output was optimised for reading well rather than for being traceable. Re-prompt for the analytical shape: one row per finding with the supporting figure and the question it came from, a separate clearly-labelled section for interpretation, and an explicit statement of what this sample cannot support. The persuasiveness was the warning sign, not the achievement.
Which task type is most exposed to hallucination, and what protects it?
Research, because it reaches for facts the model was not given and produces specific-looking citations. Protection is structural: use the surface designed for it, require citations, and then actually open the cited sources — the citation existing is not the same as the citation supporting the claim. Analysis is next most exposed, but only where values are absent from the data, which is why the "say not stated" rule matters there.

Domain 2 · Output Evaluation and Validation 21% · ~13 items — the largest domain

Six objectives and more items than any other domain. If you learn one thing thoroughly for this exam, learn this: you are the control. The model produces a candidate; deciding whether it is fit to leave your hands is the job the credential certifies.

The four-question gate, applied to every output before it goes anywhere
  1. Is it correct? Are the specific claims — numbers, names, dates, citations, quotes — verifiable against a source, and have you actually checked the ones that matter?
  2. Is it complete? Did it cover everything asked, or does it cover most of it fluently? Completeness failures are quieter than accuracy failures and therefore more dangerous.
  3. Is it right for this reader? Level, tone, length, and what they are supposed to do next.
  4. Who else must see it before it goes? Consequence, regulation, and audience decide this, not your confidence.
Real scenario
Aldgate Bank: the complaint response that passed QA

What went out. A response to a customer complaining about a £340 fee. Accurate on the fee itself. Silent on the customer’s second question, about the effect on their credit file. And it cited an FCA rule number that does not exist. It was not in the 5% QA sample, so nobody read it before it was sent.

The four-question gate, applied.

  1. Correct? No. And note where the fabrication was: the rule number — the most precise-looking, most authoritative-sounding element on the page. That is where invention concentrates, and it is the first thing to check, not the last.
  2. Complete? No — and this is the failure that cost the most. The customer asked two questions and got one answer, fluently. Incompleteness does not look like an error; it looks like a finished document.
  3. Right for this reader? A distressed customer, so tone and clarity matter as much as accuracy.
  4. Who else must see it? A complaint that can be escalated to the Financial Ombudsman is not a 5%-sample document. The sampling rate had been set by review capacity, which is not a control — it is a budget.

Takeaway · You are the control. The model produces a candidate; deciding whether it is fit to leave your hands is the job this credential certifies — and completeness failures are quieter, and therefore more expensive, than accuracy failures.

2.1 · Evaluate Claude-generated outputs for accuracy and completeness

Accuracy and completeness fail differently and are caught differently. Treat them as two passes.

Accuracy — check the specifics

Fabrication concentrates in the most precise-looking elements, because those are the most predictable text. In priority order:

  • Citations, clause and section numbers, case and standard references
  • Figures, percentages, dates, deadlines, monetary amounts
  • Names of people, products, teams, and organisations
  • Quotations presented as verbatim
  • Causal claims — "X happened because Y" is an interpretation wearing a fact's clothes
  • Arithmetic, wherever it was done in prose rather than by executing code

Completeness — check against the ask

Re-read your own request and tick items off. Omission does not announce itself; the output reads finished either way.

  • Every item in the input accounted for — count them: 8 contracts in, 8 rows out
  • Every part of a multi-part question answered
  • Caveats, exceptions and edge cases, not just the main case
  • Disconfirming evidence, not only the evidence that supports the conclusion
  • Explicit gaps: does it say what it could not determine, or is silence doing that job?
Trap — fluency read as quality A well-organised, confident, well-written output is evidence about the writing and no evidence at all about the facts. The exam repeatedly offers "it was clearly written and well structured" as a reason to proceed. It never is. Conversely a hedging, awkward answer is not therefore wrong.
The counting technique For any output derived from a countable input, count. Eight source contracts must yield eight rows; 120 tickets must yield 120 classifications summing to 120. This single habit catches most completeness failures in seconds and needs no domain expertise — which is exactly why it appears in correct answers.
A summary of twelve interviews contains no factual errors you can find, but the recommendation feels unsupported. What are you probably looking at?
A completeness failure, most likely that only some interviews actually shaped the synthesis while all twelve were cited as its basis. Check coverage directly: ask for a table with one row per interview and the specific point taken from each, then look for rows that are empty, vague, or duplicated. Accuracy checks would never have found this, because nothing in the output is false — the defect is what is absent.
Claude reports "revenue grew 23% year over year" from a spreadsheet you attached. What do you check, and how?
The arithmetic, against the figures in the sheet — prose-computed percentages are a classic error, and a wrong one looks identical to a right one. Better: have the calculation done by executing code over the data rather than described in prose, so the computation is reproducible and inspectable. Also check the definition underneath the number: which periods, which revenue line, and whether the comparison is like-for-like. A correctly computed percentage over the wrong two columns is still wrong.
Your reviewer says "I read it twice, it's fine." Is that a validation step?
No — that is a fluency check. A validation step names what was verified and against what: "the four figures in the summary match the finance export; the two cited clause numbers were opened in the contract; all eight vendors appear." Reading for plausibility is exactly the check that a fluent fabrication passes, which is why the exam treats "it read well" as a non-answer.

2.2 · Identify hallucinations, inconsistencies, and biases in responses

Three distinct problems that the exam keeps distinct. Know which one a stem is describing, because the remedy differs.

ProblemWhat it isHow you catch it
Hallucination Content presented as fact that is not supported by any source — a fabricated citation, an invented figure, a clause that does not exist, a quotation nobody said Verify the specific claim against the authoritative source. There is no shortcut: the only reliable detector is the source itself
Inconsistency The output contradicts itself, or contradicts the source, or contradicts an earlier turn — a total that does not match its parts, a date that moves between sections Cross-read the document against itself. Check that totals reconcile and that figures repeated in two places agree. This one you can catch without external sources
Bias Systematic skew: one-sided framing, unstated assumptions about people or groups, evidence selected to support a conclusion, an unrepresentative sample treated as general Ask what is missing. Who is not represented? What would the strongest counter-case be? Whose interests does this framing serve?

Where each one comes from — and what that implies

  • Hallucination is a property of generation under missing information. It is reduced by supplying sources, permitting "not stated", and narrowing scope. It is never eliminated, which is why verification is a step and not a mood.
  • Inconsistency rises with length and with long conversations, because more of the context competes and earlier superseded material is still present. Shorter outputs and fresher threads reduce it.
  • Bias has two sources you must separate: bias in the model (from training) and bias in your input (a leading prompt, a skewed dataset, a sample that only includes the customers who complained). The second is far more common in business use and entirely within your control — and it is the one exam items usually describe.
Trap — asking the model to audit its own bias "Ask Claude whether its answer is biased" produces a fluent, agreeable paragraph about balance and changes nothing structural. Real bias checks are structural: state the counter-position and ask for the strongest case for it; check whether your sample represents the population you are generalising to; have someone with a different stake read it. Where the output concerns people — hiring, performance, credit, discipline, access to services — a human decision-maker is required regardless (see 2.4 and 6.4).
A high-yield inconsistency check Ask for the same conclusion twice, in two different shapes — once as prose and once as a table of figures with sources. Contradictions between the two are the unstable claims, and those are the ones worth the expensive verification. This is a triage instrument, not a validation: agreement between two runs is not evidence of truth, only of stability.
A market summary cites a named analyst report with a plausible title, publisher and year. You cannot find it. What is your conclusion and your action?
Treat it as fabricated until you have opened the actual source. Fabricated citations are the archetypal hallucination precisely because their format is so predictable that the model can generate one indistinguishable from a real one. Action: remove the claim, or replace it with a source you have opened yourself. Asking Claude to "confirm the reference is real" is not a check — it will confirm it.
An employee-engagement analysis concludes morale is high. It was built from exit-interview data. Name the problem precisely.
Input bias — sampling bias specifically, and a compounding one. Exit interviews capture people who left, which is unrepresentative of current staff in a direction that could point either way, and the responses are shaped by the exit context. No prompt change and no model upgrade fixes this. The fix is a representative input, or an explicit and prominent statement of what the sample can and cannot support. This is the most common real-world bias in business use of Claude and it is entirely the analyst's responsibility.
A recommendation memo's total does not match the sum of its line items. Which of the three problems is it, and does it matter which?
Inconsistency — and it matters a lot, because it tells you the check you needed was internal reconciliation rather than external verification, and because it is a signal about the whole document. An arithmetic contradiction on the surface means the underlying figures were assembled unreliably, so the correct response is not to fix the total but to re-derive the numbers from the source — ideally by executing code over the data rather than by prose arithmetic.

The exam expects you to know several techniques and, crucially, to know which are validation and which are only triage. Confusing the two is how candidates lose points here.

When two options look similar, pick the one that consults something external.

Keep a retained random sample even after you add targeted checks If you route only the suspicious cases to review, you learn nothing about the ones you did not suspect — and that is precisely the population where silent errors accumulate. A small continuing random sample is the only instrument that measures your true error rate. This is a favourite of well-constructed items in this domain.
Claude summarises a regulation and cites a specific subsection. The summary is going to your compliance team. What do you do — and why is each alternative wrong?
Open the official regulation text and verify the subsection before sharing. This is the official sample question, and it is worth knowing why the other three fail: sending it because Claude sounded confident treats fluency as evidence; asking Claude to rate its own confidence consults the same process that produced the error; and rewording it more formally polishes a document whose defect is factual. Note also the audience multiplier — a compliance team will act on a subsection reference, so this is a case for full verification rather than sampling.
You must sign off 400 extracted invoices a day and can review 40. Design the check.
Layer three things. First, 100% automated reconciliation of what can be checked mechanically — totals against line items, amounts against the payment system, dates in valid ranges. Second, targeted routing of everything the extraction marked not stated, plus every invoice above a value threshold, to human review. Third — the part most answers drop — a small random sample from the unflagged remainder, reviewed continuously, so you can measure the error rate in the population nobody looked at. Reviewing the first 40 by arrival order is the wrong answer: it measures nothing and protects nothing in particular.
Two runs of the same analysis agree exactly. How much confidence does that buy?
Very little about truth. Agreement means the claim is stable, and stable errors are common — a mis-read column or a mis-remembered fact reproduces reliably. What agreement is genuinely useful for is the inverse: disagreement reliably flags a claim worth verifying. Use re-runs to build your check list, then validate against the source.

2.4 · Determine when human review or additional verification is required

Objective 2.4 is a decision rule, and the exam tests it as one. The trigger for human review is the consequence of being wrong — not the length of the output, not the model used, and above all not how confident anyone feels.

Mandatory human review — memorise these triggers
  • Regulated or professional advice — legal, medical, financial, tax, safety. Qualification is required by law or professional standard, and Claude has none.
  • Decisions about people — hiring, promotion, discipline, credit, benefits, admissions, access to services. A human must own the decision.
  • Money and contractual commitment — payments, pricing, discounts, anything creating a binding obligation.
  • External publication under your organisation's name — press, marketing claims, customer communications, filings.
  • Anything going to a regulator, auditor, or court.
  • Safety-relevant content — clinical, engineering, operational instructions people will follow.
  • Irreversible or hard-to-reverse actions — deletion, disclosure, public statements.

Claude drafts patient-facing guidance about a medication. It is accurate as far as you can tell and reads beautifully. Can it be published after your review?
No. Clinical content requires review by a qualified clinician regardless of how good it looks and regardless of your own diligence — the risk is that a plausible, well-written error about dosing or interactions is exactly what a non-clinician cannot detect. Note what is not the answer: neither "don't use Claude for patient material" (drafting under clinical review is a legitimate and valuable use) nor "add a disclaimer" (a disclaimer does not make unreviewed clinical guidance safe).
Your team lead asks you to skip review on an internal weekly summary to save time. Is that acceptable?
Reasonably, yes — for a genuinely internal, low-consequence, easily-corrected document, an author spot-check of the figures is proportionate, and insisting on formal review is the over-caution error. Two conditions though: check the specifics you are keeping, and confirm nothing in it feeds a downstream decision that raises the stakes. Summaries have a habit of being pasted into things that matter, and the review posture follows the eventual destination.
An output will be used to decide which of forty applicants advance. What is required?
A named human decision-maker who owns the outcome, plus a bias review of the criteria and the inputs, plus records of the basis for each decision. This is a decision about people, so Claude's role is strictly to organise and summarise information for a person to weigh — not to rank, score or shortlist as the operative decision. Check as well whether your organisation's AI policy or local law restricts automated processing in recruitment at all; where it does, policy answers this before your own judgement does.

"Make it more positive for the exec audience" is the distractor — that is not adaptation, it is misrepresentation, and it is a governance failure as much as a communication one (see 6.4).

Comparing candidate outputs

The objective includes "compare", which implies you sometimes generate alternatives and choose. Do it with criteria, not by feel:

  • Fix the criteria before you look — accuracy, completeness against the ask, fit for audience, actionability, tone. Written down, ideally weighted.
  • Compare on the same input, or you are measuring the input, not the output.
  • Judge accuracy separately from style. The more persuasive draft is very often the less accurate one, and reviewing them together lets fluency win.
  • Feel free to combine. The best structure from one and the best evidence from another is usually better than either.
A validated six-page analysis must go to the exec team, the specialist team, and affected customers. How many pieces of work is that, and what is shared?
Three derived outputs from one validated core. Shared and immutable: the facts, figures and material caveats. Different in each: length, structure, vocabulary, and what leads. Exec gets the recommendation and the ask up front; specialists get method, assumptions and limitations; customers get plain language about impact and next steps. The error to avoid is deriving the customer version from the exec summary rather than from the validated analysis — each hop drops caveats, and by the third hop a hedged finding has become a promise.
Two drafts: one crisper and more persuasive, one duller with a caveat about data quality. Which do you send?
Neither as-is — take the crisper structure and put the caveat back in. The caveat is a fact about what the analysis can support, so removing it is not an editorial choice, and the persuasiveness of the other draft is not a reason to drop it. This is why accuracy and style get judged on separate passes: put them in the same pass and the better-written draft reliably wins on the wrong grounds.
A stakeholder asks you to remove the uncertainty range because "the board wants a number". What do you do?
Give them a single headline number and keep the range, in the form the board can act on: "£2.4m, with a plausible range of £1.9–2.9m depending on the two assumptions listed below". The request is reasonable — boards do need a number to decide on — but the range is a fact about the estimate's reliability, and deleting it transfers risk to people who cannot see it. Reframing satisfies the real need without misrepresenting the analysis.

2.6 · Organize and curate information and select appropriate output formats

The objective names the three options explicitly: artifacts, inline, structured data. The decision table is in Primer 2; what follows is the part that gets tested beyond the table.

Format follows destination Ask what happens to this output next. Read once in the conversation → inline. Edited, reused, iterated, or sent onward as a document → artifact. Consumed by a system or a person's tool, or needing consistent fields across many records → structured data or a real file. Length is not the criterion, and neither is effort.

Curation — the half of the objective people skip

"Organize and curate information" is about imposing a usable structure on material, not about picking a renderer. What the exam looks for:

  • One organising principle per output, chosen deliberately: chronology for an incident timeline, severity for a risk register, theme for a research synthesis, owner for an action list, journey stage for customer feedback. Mixed organising principles are the most common reason a well-written document is hard to use.
  • Consistent granularity. One row per ticket, or one row per theme — not both in the same table.
  • Stable fields. If this output recurs, the columns must not drift between runs, or nothing downstream can consume it and nothing can be trended.
  • Provenance carried alongside. A source column or citation per row is what makes verification possible later, which is the whole reason Domain 2 exists.
  • Deliberate exclusion. Curation means leaving things out and being able to say why. An output that includes everything has not been curated.
Trap — the format that is convenient to produce Prose is the cheapest output to generate and the most expensive to consume when the reader needs to compare, sort, or import. If a stem mentions many items being compared, a recurring report, or content going into another system, the correct answer is a structured shape with fixed fields — even when the current output "works" as prose. Conversely, forcing a genuinely narrative explanation into a table destroys the reasoning that made it useful.
Weekly competitor updates go into a shared tracker with fixed columns, but Claude returns three well-written paragraphs each week. What do you change?
Specify the structured shape with the tracker's exact columns and one row per competitor per week, and persist that specification in the Project's instructions so every week matches. The paragraphs are not wrong, they are the wrong shape for the destination — and because the destination is a tracker that will be trended over time, field stability across weeks matters as much as the format itself. Reformatting by hand each week is the distractor: it works and it guarantees drift.
An incident review needs to explain how a failure cascaded across four systems. Table or narrative?
Both, doing different jobs: a chronological table of events with timestamps, systems and sources, plus a short narrative explaining the causal chain. Forcing pure structure loses the causality — the reason a table cannot carry "this is why the retry storm reached the database" — and pure narrative makes the timeline unauditable. Note the organising principle is chronology throughout; switching to system-by-system halfway is what makes most incident write-ups unreadable.
You have 200 pieces of customer feedback. What does "curate" require beyond summarising them?
Choosing an organising principle and applying it consistently — theme, journey stage, or severity, one of them, not a mix — then fixing the granularity (one row per theme, with counts, not a blend of themes and individual quotes), attaching provenance so any theme can be traced back to the feedback behind it, and deliberately excluding what is not decision-relevant while being able to say what you excluded. A summary answers "what did they say"; curation answers "what should we do about it", which is what the requester actually needed.

Domain 3 · Product and Model Selection 12% · ~7 items

Four objectives, and the domain with no prep-course lesson of its own — it is folded into lesson 1, which is why candidates arrive under-prepared. The mechanics are in Primer 2, Primer 3 and Primer 4; the sections below are the decisions the exam actually poses.

Real scenario
Civic Health Trust: three asks, three answers, and one trap

3.2 · Differentiate between Claude model types

The tier table is in Primer 3. What items test here is the discrimination: given a task description, which tier, and can you say why in terms of the task rather than the stakes.

The one question that decides it What is the hardest cognitive step in this task? Labelling into known categories, applying a template, extracting stated values → the fast tier. Drafting, summarising, moderate analysis → the balanced tier. Reconciling contradictory sources, reasoning under genuine ambiguity, multi-constraint judgement where an error is expensive → the top tier. Volume, audience seniority and deadline pressure are all irrelevant to this question, and all three appear in distractors.
Legitimate reasons to change tier
  • The task's hardest step got harder or easier
  • Latency matters to a waiting user, and depth can be traded
  • Volume makes cost per item material, and quality holds at the lower tier — measured, not assumed
  • A measured quality shortfall on genuinely hard reasoning, after confirming the input was complete
Illegitimate reasons
  • The audience is senior
  • The deadline is tight
  • Someone complained once
  • To compensate for a missing document or a vague prompt
  • "To be safe" — with no task-based reason at all
Same document, two tasks: "extract the twelve stated dates" and "tell me whether these terms are more favourable than our standard agreement". Same tier?
No. Extraction of stated values is mechanical — fast tier, with verification against the document. The comparison requires holding two documents' terms against each other and making a judgement about "favourable" that depends on context the document does not state — that is genuine reasoning, so a stronger tier, and it is also a case for human review since it informs a commercial decision. The exam likes this shape precisely because the input is identical and only the cognitive demand differs.
A summarisation workflow on the fast tier is producing acceptable output. Your manager wants it moved to the top tier for quality. What do you propose?
Measure before moving. Take a sample, run both tiers, and score them against the criteria that matter — accuracy of figures, completeness against the source, fit for the reader. If the fast tier holds up, the current setup is correct and the upgrade is pure cost. If it does not, you now have evidence for the change and a baseline to show the improvement. "Acceptable" is a feeling; the professional answer converts it into a comparison, and that is also objective 7.2's habit.

3.3 · Align model selection with task requirements (cost, speed, quality)

Three constraints that trade against each other. The exam wants to see you name which one binds, and it wants you to reject the two uniform answers.

SpeedA person or process is waiting; interactive tool; real-time queueFaster tier, shorter outputs, less thinking. Accept less depth deliberately and say so
CostHigh volume × low individual value; a per-item budget existsCheapest tier that holds quality at a measured level, plus sampling review. Tier the work so only the hard slice is expensive

The tiered-workflow answer Where a stem gives you high volume and a hard minority, the best answer is almost always to split the work: a cheap fast pass over everything that also identifies the hard cases, and a strong pass on just those. It satisfies cost and quality simultaneously instead of sacrificing one, and it is the shape of answer that distinguishes a strong candidate from someone picking a single tier.
Trap — cost answers that are not about the model "Disable features to cut cost" and "switch to another AI platform" both appear as distractors, and neither engages the trade-off. Also treat "review less" with suspicion: moving spend from compute to unreviewed risk is not an optimisation, it is a transfer of the cost onto whoever gets the error.
Thirty thousand product descriptions must be rewritten this quarter within a fixed budget, and roughly 500 are flagship products needing real craft. Design it.
Two tiers by product tier. The 29,500 standard descriptions go to the fast, cheap tier with a strict template, a fixed output shape, and a random sample reviewed continuously to hold quality measurable. The 500 flagship descriptions go to a stronger tier and get human editorial review, because those are the ones with visible brand consequence. Uniform answers lose either the budget or the flagship quality; the split satisfies both constraints, which is the point of the objective.
A customer-facing chat assistant is accurate but users complain it is slow. Which constraint binds, and what do you trade?
Speed. Trade depth deliberately: a faster tier, shorter target responses, and less extended reasoning — then re-measure accuracy to confirm the trade did not cross into unacceptable. Worth noting the alternative lever that is not a model change: much perceived latency in interactive tools comes from long answers, so constraining response length can resolve the complaint without touching the tier at all.

A colleague keeps one enormous chat per client, running for months, and reports it has "got worse". What do you recommend?
Convert the pattern: one Project per client, with the durable client context in instructions and knowledge, and a fresh chat per piece of work. That fixes three things at once — context dilution in the endless thread, the loss of everything when the thread becomes unusable, and cross-client bleed, since each Project gets its own memory. Persist. A convention agreed once and needed indefinitely is configuration, so it belongs in the Project's instructions where every future chat picks it up. Restarting or summarising carries it into this thread and loses it again next week, and relying on memory to have retained it is not a control — memory is a convenience layer, not a specification.

Domain 4 · Workflow Integration and Solution Design 16% · ~10 items

Five objectives and the second-heaviest domain. This is the consulting half of the credential: given a business process, decide what Claude should do inside it, where the checkpoints go, and how to explain the result to people who will either fund it or resist it.

Real scenario
Meridian Mutual: 600 documents a day and capacity to review 60

The situation. 600 claim documents arrive daily. Handlers can properly review about 60. Personal injury claims are a regulated determination about a person.

Two designs the exam will offer you, and why both are wrong. Automate the lot — fails, because a regulated decision needs a named human decision-maker and this removes them. Keep everything manual — fails, because the backlog is the harm: claimants wait, and the 540 documents nobody reads today are not being handled carefully, they are being ignored.

The design that works. Claude processes all 600: extracts to a fixed structure, summarises, flags missing or contradictory information, and ranks by value and by its own confidence. A handler then reviews — always for personal injury, and by exception elsewhere, with the low-confidence and high-value items at the top of the queue. The checkpoint sits where being wrong is expensive, not spread evenly across everything.

The part candidates skip. The success measure was agreed before the pilot: documents per handler per day, and the error rate found in the review sample. Without the second number, a throughput improvement is indistinguishable from a quality collapse.

Takeaway · Decide what Claude does, where the human checkpoint goes, and how you will know it worked — before you start. Checkpoints belong where the consequence of being wrong is highest, not uniformly everywhere.

4.1 · Apply Claude to analyze requirements and use cases

Two things are bundled here: using Claude to help you understand a requirement, and judging whether a requirement is a good Claude use case at all. The exam tests both, and the second is the harder one.

Using Claude on requirements work

  • Extract and structure — turn a 40-page RFP or a folder of stakeholder emails into a table of discrete requirements with source references, so nothing is carried only in someone's memory.
  • Find contradictions and gaps — "which of these requirements conflict, and which specify a goal without specifying how it will be measured?" This is genuinely valuable because it is tedious for humans and mechanical for a model with the documents in front of it.
  • Classify — must-have vs nice-to-have, functional vs non-functional, in-scope vs out-of-scope. Then you confirm the classification, because priority is a stakeholder decision, not a text property.
  • Generate the questions you have not asked — "what would a delivery team need to know that this document does not say?" A strong use, and one candidates under-rate.
Trap — letting the model decide what matters Claude can tell you that two requirements conflict. It cannot tell you which one the business should sacrifice, because that depends on commercial context, politics and risk appetite that are not in the document. An option where Claude resolves a priority conflict or approves a scope decision is wrong however sensibly it is phrased; the correct shape is Claude surfaces, a person decides.

Judging whether a use case fits

Good fitPoor fit
  • Language in, language out
  • High volume of similar judgement calls
  • Synthesis across many documents
  • Drafting where a human edits and owns the result
  • Classification against defined categories
  • Explaining complex material to a specific audience
  • Tedious, error-prone, well-specified transformation
  • Requires a fact no one has supplied and no source contains
  • Requires the output to be provably correct with no review possible
  • The system of record must be updated with no human in the loop and errors are costly
  • Regulated determinations about people, made autonomously
  • Precise arithmetic done in prose rather than by executing code
  • Accountability cannot be assigned to a person
  • The real problem is a broken process, and automation would just make the mess faster
The fit question, in one line Is the work language-shaped, and can a competent person verify the output at a cost worth paying? If yes to both, it is a candidate. If the verification cost exceeds the value of the automation, the use case is a bad one even though the model could do it — and that is a distinction the exam rewards.
A team wants Claude to read incoming purchase requisitions and approve those under £5,000 automatically. Assess it.
Split the request. The language-shaped part — reading the requisition, extracting the fields, checking them against the policy, flagging anything missing or unusual, and drafting a recommendation — is a strong use case. The approval is a financial commitment, so a person must own it. The right design gives the approver a pre-checked, structured summary so the decision takes seconds instead of minutes, which captures nearly all the value without transferring the accountability. Note that "£5,000 is small" is not the deciding factor; the volume of small approvals is exactly how large aggregate losses happen.
Stakeholders ask for a system that "tells us which customers will churn next quarter". Is that a Claude use case?
Not as stated — that is a prediction from structured behavioural data, which is a modelling problem, not a language problem. What Claude does well around it is the language layer: synthesising the qualitative signals in support tickets, call notes and emails into themes and per-account summaries, explaining a churn model's outputs to account managers in plain terms, and drafting the outreach. Answering the literal request would be the wrong recommendation; reframing to the language-shaped part of the same business need is the right one.
Claude reports that two requirements in an RFP contradict each other. What is your next action?
Open both requirements in the source and confirm the contradiction is real — this is a claim about a document, so it is verifiable and must be verified before you raise it with a client. If it is real, take it to the stakeholders who own the requirements for a decision. What you do not do is have Claude pick a resolution: the trade-off depends on commercial context that is nowhere in the RFP.

4.2 · Leverage Claude for research, planning, and process optimization

Three activities with one shared discipline: Claude produces the candidate, you supply the constraints it cannot know and the verification it cannot perform.

Trap — the confidently wrong estimate Ask for a project plan and you will get durations: "discovery, 3 weeks". Those numbers are generated to look like plausible durations, not derived from your team's velocity or availability. They are legitimate as a starting structure and illegitimate as a commitment. Claude's competitive research says a rival "launched a compliance module in Q3 at $40 per seat". You plan to put it in a board pack. What do you do?
Verify both specifics — the launch and the price — against the rival's own site, documentation or a named published source, and cite whatever you find. Competitor pricing is precisely the kind of specific, plausible, high-consequence claim that gets fabricated, and a board pack is external-grade output. If you cannot substantiate it, either remove it or state it explicitly as unverified with the uncertainty attached. A process map produced from staff interviews recommends deleting a second approval step as duplicative. How do you handle the recommendation?
Find out why the step exists before touching it. Second approvals are usually a control — segregation of duties, a fraud response, an audit or regulatory requirement, or the residue of a specific past failure — and none of that is visible in interview transcripts describing what people do day to day. Ask the control owner and the risk or audit function. If it turns out to be genuine duplication, remove it with their agreement; if it is a control, the optimisation is to make it faster, not to delete it.
Research on a fast-moving regulation returns a confident summary with citations. What limitation applies regardless of the citations?
Recency and reach. A web-based synthesis can miss the most recent amendment, cannot see material behind paywalls or inside your organisation, and cannot know which of two conflicting sources your jurisdiction actually follows. For a regulation that drives compliance decisions, the citations tell you where to look, and the authoritative text plus qualified legal review is what you act on — which is objective 2.4 applying to a Domain 4 activity.

4.3 · Use Claude to support solution design, development, and iteration

Note the verb: support. The Associate credential is not about building systems — that is the Architect and Developer scope. This objective is about Claude as a design partner inside work you own.

In scope for an Associate

  • Generating design options and the trade-offs between them
  • Stress-testing your design — "what breaks under 10× volume? what did I not consider?"
  • Writing the specification, user stories, acceptance criteria and test cases
  • Reviewing documents and designs against a checklist or standard
  • Drafting and iterating collateral, docs and communications through artifacts
  • Configuring Projects and Skills so the workflow is repeatable by others

Escalate — and know to whom

  • API integration and application architecture → Architect / Developer
  • Agentic systems, tool use, orchestration → Architect / Developer
  • Enterprise tenancy, SSO, DLP, retention → platform / security
  • Anything touching regulated determinations → compliance / legal
  • Production code deployment → engineering
Iteration, at solution level The loop from 1.3 scales up. Design a small version, run it on real work, measure against criteria you set in advance, change one thing, measure again. The exam's preferred answer to "how should we roll this out" is almost always a bounded pilot with a defined success measure — not a full rollout, and not an indefinite evaluation with no criteria.
Trap — the pilot with no measure "Try it for a month and see how it goes" is a distractor that sounds prudent. Without a defined measure and a baseline, the pilot's outcome will be decided by whoever is loudest afterwards. Define before you start: what you are measuring, against what current performance, and what result would make you stop.
You are asked to design a Claude-assisted contract review workflow. What does your design have to specify beyond the prompts?
The checkpoints and the ownership. Concretely: which contract types are in scope and which are excluded; what goes into the Project as knowledge (the playbook, standard positions, precedent clauses) and what goes into instructions (output format, citation requirement, escalation triggers); what the output shape is; which findings route to a lawyer and which a reviewer can clear; how exceptions are handled; who owns the configuration and reviews it; and what you measure. Prompts are the smallest part of the design, and an answer that only addresses prompting has missed the objective.
Mid-pilot, a stakeholder asks to expand scope to a second, more complex document type. What do you say?
Finish the pilot on the original scope first, because expanding mid-run destroys the comparison you set the pilot up to make — you would no longer be able to attribute the result to anything. Take the new type as a second, separately-measured phase, and note that a more complex document type may need a different tier, different knowledge, and a different review posture, so it is genuinely a new design rather than more of the same. Refusing outright is the over-caution error; agreeing immediately loses the evidence.
Your design would work better if Claude could write directly into the CRM. Who owns that, and what do you do now?
That is an integration — API work and system-of-record writes — so it belongs to engineering with an Architect or Developer designing it, and it needs its own review of failure modes and permissions. Your move as an Associate is to document the requirement and hand it over with the evidence from your pilot, while shipping the version that works today: structured output a person pastes or imports, with the human confirmation step intact. Building the integration yourself is outside the role's scope; abandoning the workflow because the integration is not there yet gives up value you already have.

4.4 · Integrate Claude into existing workflows to augment or redesign them

The objective offers two words, and the exam distinguishes them sharply. Augment keeps the process and makes a step better. Redesign changes the process because the constraint that shaped it no longer applies.

ApproachWhen it is rightWhat it looks like
Augment The process is sound; one or two steps are slow, tedious or inconsistent. Controls and accountability stay where they are Claude drafts the first version; the existing reviewer still reviews; the existing approver still approves. Low risk, fast to adopt, easy to reverse
Redesign The process exists because of a limit that no longer binds — e.g. work was batched weekly because reading everything took a week Change the shape: continuous instead of batched, whole-population instead of sampled, self-service instead of queued. Higher value, needs governance sign-off and new controls
Start by augmenting, and look for the redesign Augmenting proves value with little risk and gives you the evidence to fund the bigger change. But an answer that only ever augments misses the objective's second half: when a stem explicitly describes a constraint that Claude removes — "we only sample 5% because reviewing everything is impossible" — the exam wants you to notice that the 5% was a capacity artefact, and that reviewing 100% is now on the table.

What every integration must specify

  1. Trigger — what starts it, and does a person start it or does the work arrive?
  2. Inputs — where they come from, and whether they are current. Static uploads go stale; connectors do not.
  3. The Claude step — which surface, which tier, what configuration, and where that configuration lives so it is not in one person's head.
  4. Output shape — fixed fields if anything downstream consumes it.
  5. Checkpoint — who reviews what, at what rate, on what criteria. Never "the team will check".
  6. Exception path — what happens to the cases the workflow cannot handle. Its absence is the commonest design flaw, because those cases then silently become nobody's.
  7. Failure mode — what people do when the step is unavailable. A workflow with no manual fallback is a single point of failure.
  8. Ownership and review cadence — a named owner, and a date when the configuration gets re-checked (5.4).
Trap — automating the checkpoint away Under pressure to show efficiency, the review step is the first thing proposed for removal, often dressed as "Claude checks its own output". That is not a checkpoint (2.3). Legitimate ways to make review cheaper: structure the output so it is faster to check, verify mechanically what can be verified mechanically, route by risk, and sample the low-risk remainder. Deleting review is not one of them.
A team samples 5% of support conversations for quality review because that is all they have capacity for. Augment or redesign?
Redesign, and the stem tells you why: the 5% is a capacity artefact, not a methodological choice. Have Claude score 100% against the published quality rubric, then use human reviewers where they add most value — calibrating the rubric, reviewing the flagged tail, and auditing a random sample of the unflagged population so you can measure the scoring's own error rate. Simply speeding up the existing 5% sample would leave the real limitation in place.
A workflow works for 85% of cases. What must the design say about the other 15%?
Exactly how they are identified, where they go, and who owns them — by name or role, with a service expectation. Unhandled exceptions do not stay visible; they accumulate quietly with whoever notices them, and they are the hardest cases, so the people handling them are doing the hardest work with no support. A workflow that handles 85% cleanly and routes 15% explicitly is a good design; one that handles 85% and is silent about the rest is an incident waiting to happen.
Where should the workflow's Claude configuration live, and why does the exam care?
In a shared Project — instructions and knowledge — owned by a named person, not in individual prompts or in a document that people are supposed to copy from. The exam cares because a workflow whose behaviour depends on each person's prompting is not a workflow: it drifts, it cannot be audited, it cannot be improved once for everyone, and it breaks when the person who knew the trick leaves.

4.5 · Communicate Claude's value and limitations to stakeholders

An objective about honesty under commercial pressure. You will face both an over-seller and a sceptic, and the exam's answer to both is the same: specifics, evidence, and named limits.

AudienceWhat they actually want to knowHow to answer
Executive sponsorWhat it costs, what it returns, what could embarrass usA measured result from the pilot, the cost, the review burden, and the two risks with their controls. Never a claim you cannot evidence
Sceptical practitionerWhether this replaces their judgement, and whether it will make more workShow it doing the tedious part while their judgement stays the control. Be concrete about what it gets wrong — credibility comes from naming the failures first
Risk / complianceData flows, retention, review, accountability, auditabilityThe controls and the evidence trail, in their vocabulary. Bring the policy question before they have to find you

The limitations you should always state
  • It produces fluent output whether or not it is correct — review is part of the workflow, not an optional extra.
  • It knows only what it was given: no access to your systems unless connected, and a training cutoff.
  • It is not deterministic — the same input can yield differently-worded output.
  • It cannot be accountable. A person owns every decision it informs.
  • Volume changes the arithmetic: a 2% error rate is invisible at ten items a week and material at ten thousand.
Trap — both directions Over-claiming ("it eliminates manual review") sets up a failure that will be blamed on the technology and will close the door on the next attempt. Under-claiming ("it just saves a bit of typing") loses the funding for work that genuinely pays. Distractors in this objective are usually one of these two, and the correct answer is the specific, measured, limit-bearing middle.
An executive says "so we can cut the review team". How do you respond?
Directly: no, and the review is what makes the value real. Reframe it in terms they care about — reviewers stop retyping and start checking, so throughput rises without the error rate rising, and that is the result you can evidence from the pilot. Then give the number: here is the measured error rate, here is what an escaped error of that type costs us, and here is why removing the check is the one change that turns a saving into an incident. Agreeing to keep quiet about it is not an option — you would be manufacturing the failure that ends the programme.
A senior analyst says "it made things up last time, I don't trust it". What is the productive answer?
Agree with the observation, because it is correct, and then work on the conditions. Fabrication concentrates where the input is missing, so ask what it was given: without the source document, invention is the expected behaviour, not a malfunction. Show the difference with the source attached, an explicit "say not stated" rule, and their own check on the output. Dismissing the experience or promising a newer model fixes it both lose the person whose scepticism is actually the control you want in the workflow.
You are asked to present time savings and you have not measured any. What do you present?
What you can evidence, plus the plan to measure what you cannot. Say plainly that you do not yet have a time saving, describe what you have observed, and propose the measurement: a baseline on the current process, a defined pilot scope, and the specific numbers you will report back. Producing an estimate that sounds like a measurement is the failure here — it will be quoted back as fact in a business case, and when it does not hold, everything else you said loses its credibility too.

Domain 5 · Configuration and Knowledge Management 12% · ~7 items

Four objectives about turning a working prompt into a working system. The single organising idea: anything that must be true every time belongs in configuration, not in a prompt — and configuration that is not maintained becomes a liability.

Real scenario
Beckford & Hale: three versions of the house style in circulation

The symptom. Consultants were pasting the firm’s style guide into the top of every conversation. Three variants were circulating, one of them eighteen months old, and the disclosure line the client contract required was in only two of them.

The reorganisation. The organising rule is that anything that must be true every time belongs in configuration, not in a prompt:

  • Project instructions: the citation rule, the tone, the required AI-disclosure line, the output template. Short, stable, and applies to every conversation whether or not anyone remembers it.
  • Project knowledge: the approved report examples and the current rate card, as files — because they change on a schedule and need to be replaced, not edited into a prompt.
  • Connector: the client’s ticket system, instead of weekly CSV exports that were stale by Tuesday.

The failure they then had to design against is the one this domain really tests: a Project whose knowledge has gone stale is more dangerous than no Project at all, because everyone now trusts it. So each file has a named owner and a refresh date, and the rate card is checked at the start of every week.

Takeaway · Configuration is for what must hold every time; knowledge files are for material that changes on a schedule and needs an owner. Stale knowledge that everyone trusts is the characteristic failure of this domain.

5.1 · Configure Claude Projects with instructions and knowledge sources

Instructions Standing behaviour: role and audience, tone, output format, terminology, what to cite, what to refuse, escalation triggers, and what to do when information is missing Bulk reference content. Pasting a 30-page policy into instructions crowds the behavioural rules out and makes them harder to maintain
Knowledge Reference material to consult: policies, product docs, style guides, precedent examples, glossaries, approved templates Behavioural rules. A document that says "always use British spelling" sitting in knowledge is a fact Claude may mention, not a rule it follows
The test that resolves it Ask: is this a rule about how to behave, or material to consult? Rules → instructions. Material → knowledge. "Cite the policy section in every answer" is a rule. The policy is material. Both are needed, and each is useless in the other slot.

Project scope — one Project or several?

  • Separate Projects when the audience, tone, confidentiality boundary, or knowledge base differs. Client A and Client B must not share a Project — and note that each Project keeps its own separate memory, which is what makes this the structural fix for cross-contamination rather than a convention people have to remember.
  • One Project when several people do the same kind of work and consistency is the point. Sharing is the mechanism that makes behaviour uniform across a team.
  • Too many Projects is its own failure: nobody knows which to use, and they drift apart. Split on a real boundary, not on personal preference.
Free-plan limit Free accounts can create up to five Projects; paid plans get substantially more retrieval capacity over Project knowledge. Limits change — verify against the live documentation close to your exam date, and prefer answers that reason about the boundary rather than quoting a number.
You have a 40-page underwriting manual, a required output format, and a rule about escalating anything involving litigation. Where does each go?
Manual → knowledge. Output format → instructions. Escalation rule → instructions, phrased as a behaviour: "if the case involves active or threatened litigation, do not assess it; state that it must go to the legal team." The common error is putting all three in instructions because they are all "requirements" — that buries the two actual rules inside forty pages of reference text and makes the configuration unmaintainable.
Three consultants each have their own Project for the same client. What is the problem?
Three configurations that have already diverged, three knowledge sets updated at different times, and three different answers to the same client question. Consolidate to one shared Project with a named owner, and let personal experimentation happen in ordinary chats. The point of a Project is shared, versioned behaviour; a per-person Project has the maintenance cost of configuration with none of the consistency benefit.
Answers cite a policy version that was replaced six months ago. Fix it.
Remove the superseded document from Project knowledge and add the current one. The distractor is adding an instruction like "always use the 2025 version" — that leaves the obsolete text in the retrievable set, so it can still surface, and it papers over a maintenance failure with a rule. Then fix the cause: a named owner and a review cadence, which is objective 5.4.

The objective names connectors explicitly — Google Drive, Gmail, Calendar. The decision that matters is upload versus connect, and the criterion is not convenience.

Does the source change underneath you? Changing → connector. Static → upload. That one question answers most items in this objective. And when a stem says answers are correct-but-outdated, the diagnosis is an upload that should have been a connector, or a superseded file nobody removed.

Curating knowledge at scale

  • Remove superseded material. Retrieval does not know which of two contradictory documents is current, and the older one is often the better textual match.
  • One authoritative document per topic. Three overlapping decks about the same product is how inconsistency gets built in.
  • Prefer the source, not the summary of it. A summary in knowledge is someone's interpretation, and errors in it propagate silently into every answer.
  • Do not upload what should not be in the workspace at all. Curation is a privacy control as much as a quality one — see 6.2.
  • Name files so their scope and date are visible. Retrieval and humans both benefit.
Trap — "add more, to be safe" Uploading everything tangentially related degrades answers: more competing material, more chance the wrong document is retrieved, more stale content, and a bigger privacy surface. When a stem offers "upload all related documents" against "upload the current authoritative document and remove the old ones", the second is right.
Connector privacy fact worth knowing Anthropic states that models are not trained on the content retrieved through connectors, and connector access follows the permissions of the account you connect. That does not make a connector a substitute for your organisation's data policy — connecting a corporate mailbox is a decision for IT and compliance, not an individual convenience choice (6.3).
Product pricing changes monthly. Sales answers keep quoting old prices. What is the fix, and what is the fix that only appears to work?
Connect the live pricing source and remove the uploaded price list, so currency stops depending on anyone remembering. The fix that only appears to work is a diarised monthly re-upload: it depends on a human doing a repetitive task forever, it is silently wrong between the price change and the upload, and the failure mode is invisible — sales quote confidently from stale data with no signal that anything is wrong.
Someone proposes connecting a shared mailbox containing customer correspondence to a Project. What is your answer?
Not your decision to make alone. Connecting a mailbox of customer correspondence brings personal data into a workspace with a set of viewers, so it needs IT and compliance sign-off, a clear purpose, and a view on who in the Project can then see that material. Ask what question you are actually trying to answer — often a narrower input (a specific thread, or an anonymised extract) satisfies the need without exposing the whole mailbox. The technical ease of connecting is not the same as the authority to connect.
A Project has 60 documents and answers have got vaguer. Diagnose.
Under-curation. Sixty documents almost certainly contain duplicates, superseded versions and near-topics, so retrieval brings back a blend and answers regress to a vague average. Audit it: one authoritative document per topic, superseded versions deleted, tangential material removed, clear filenames. Adding an instruction to "focus on the most relevant document" does not help, because the model cannot know which of two similar documents you consider current.

5.3 · Create effective system-level instructions

Project instructions are configuration read on every turn. They are written differently from prompts: specific, behavioural, testable, and short enough to stay true.

ElementWrite it like this
Role and audience"You support our UK claims handlers. They are trained but not lawyers."
Scope"Only motor and home claims. If asked about commercial lines, say it is out of scope."
Output formatThe exact structure: named sections, or named columns, and a length.
Grounding rule"Answer only from the documents in this Project. Cite the document and section for every claim."
Missing-information rule"If the documents do not cover it, say so explicitly and do not infer. Suggest who to ask."
Escalation triggers"Any mention of litigation, injury, or a regulator: stop and route to the technical claims lead."
TerminologyOur words for our things, and the ones never to use.
ExamplesOne or two approved outputs. Worth more than any amount of description.
Behavioural, not aspirational "Be accurate and professional" is unenforceable and changes nothing. "Cite the policy section for every claim; where the policy is silent, say not covered" is a behaviour you can check in the output. If you cannot tell from an output whether an instruction was followed, it is not an instruction.
Trap — instructions that grow until they contradict Instructions accumulate as people add rules for individual incidents, and eventually two of them conflict — at which point behaviour becomes unpredictable and everyone blames the model. Keep them short, resolve conflicts explicitly, state precedence where two rules could both apply, and delete rules whose reason has gone. Length is not thoroughness; a page of consistent rules beats five pages of accreted ones.
Skills, for procedures A long, specific, repeatable procedure — how we run a quarterly review, how we format a client deliverable — is better as a Skill than as more lines in the instructions: it loads when relevant instead of competing for attention on every turn. Standing rules that apply to everything in the workspace stay in instructions.
An instruction says "always be helpful and thorough". Rewrite it usefully.
Replace it with the behaviours someone meant by it: "answer in at most 200 words unless asked for more; cite the source document and section for every factual claim; list any part of the question the Project documents cannot answer; end with the single next action the reader should take." Each of those is visible in the output, so you can tell whether it was followed and fix it when it was not — which the original never allowed.
Two instructions conflict: "answers must be under 200 words" and "always include the full regulatory citation with context". What do you do?
Resolve it in the configuration rather than leaving the model to arbitrate: state precedence explicitly — "the citation requirement takes priority; where a full citation makes the answer exceed 200 words, exceed it" — or restructure so both hold, e.g. a short answer plus a citations block that does not count toward the limit. Leaving the conflict in place produces output that inconsistently violates one rule or the other, and the inconsistency will be reported as a model problem.
Which single instruction most reduces hallucination in a knowledge-grounded Project?
The combined grounding and missing-information rule: answer only from the Project's documents, cite the document and section for every claim, and when the documents do not cover something, say so explicitly rather than inferring. It works on both halves of the problem — it makes every claim traceable so errors are findable, and it makes "I don't know" a legal output so the gap-filling reflex has somewhere else to go.

5.4 · Inform, maintain, and update configurations, knowledge sources, and instructions

The objective few candidates prepare for, and it carries real weight. Configuration is not a setup task; it is an asset with a decay rate.

The maintenance question the exam asks When a stem describes a configuration that used to work, the answer is almost never a prompt change or a model change. Something underneath moved: a document went stale, a rule outlived its reason, the process changed and the instructions did not. Look for the drift.
Trap — fixing the output instead of the configuration When a shared Project starts producing a recurring problem, correcting it in your own chat fixes it for you and for nobody else, and it hides the signal that the configuration needs work. The right move is to fix the configuration once and tell the users — which is also the difference between an Associate who has been certified and one who has just been using the product.
A Project that worked well for a year is now producing answers people describe as "subtly off". Where do you look, in order?
First the knowledge: what has been superseded, what got added by whom, and whether anything now contradicts something else in there. Second the instructions: which rules were bolted on during the year, and do any of them now conflict. Third the process itself: has the work changed so that the configuration is faithfully implementing last year's job. Only after those three does a model or prompt change make sense — "subtly off after a long period of working" is the signature of configuration drift, not of a capability problem.
You update a shared Project's instructions to fix a formatting problem. What else do you owe?
Tell the people who use it what changed and why, and record the change — that is the "inform" duty in the objective. Without it, colleagues see different output than yesterday with no explanation, some will work around it, and in three months nobody will know why the rule exists or whether it can be removed. Silent changes to shared configuration are how a well-maintained Project becomes an unmaintainable one.
Who should own a Project used by four teams?
One named individual, with a defined route for the other teams to request changes. Shared ownership across four teams means no one reviews it, everyone edits it, and the instructions accumulate four teams' special cases until they contradict. A single owner with a change request path keeps the configuration coherent while still serving everyone — and gives you someone to ask when behaviour changes.

Domain 6 · Governance, Risk, and Responsible Use 15% · ~9 items

Four objectives, third-heaviest domain. Expect scenarios where the technically capable answer is the wrong answer. The recurring test: can you find the control that lets legitimate work proceed safely, rather than either ignoring the risk or abandoning the work?

Real scenario
Larkfield Council: an officer, a personal account, and no policy yet

The situation. An officer wants to use a personal Claude account to speed up benefit entitlement decisions. The council has no AI policy. The work is legitimate, the backlog is real, and entitlement decisions have to be explainable on appeal.

The two answers the exam offers, and rejects. “Yes, get on with it” — a personal account puts residents’ personal data outside the council’s control, and no policy is not the same as permission. “No, refuse the use case entirely” — over-caution is scored as wrong here just as often, and this domain is full of options that sound responsible and are simply obstruction.

The shape of the right answer: the work proceeds, with the controls that make it defensible. An approved organisational account rather than a personal one. No residents’ personal data until that route is cleared — the officer can start on the policy-interpretation and drafting parts that need none. A named human decision-maker on every determination. The reasoning recorded, so the decision can be explained on appeal. And a disclosure line wherever policy requires one — noting that disclosure is transparency, not a control: saying “AI helped write this” does not make a wrong decision acceptable.

Takeaway · Find the control that lets legitimate work proceed safely. Refusing the whole use case is a wrong answer here as often as approving it unchanged, and disclosure is never a substitute for a human decision-maker.

6.1 · Identify appropriate and inappropriate use cases

AppropriateInappropriate
  • Drafting that a human edits and owns
  • Summarising and synthesising material you supply
  • Classification against defined categories, with sampling review
  • Explaining complex material to a named audience
  • Generating options for a person to choose between
  • Reviewing work against a checklist to surface candidates
  • Extraction from documents, verified against them
  • Final decisions about people — hiring, credit, discipline, benefits
  • Professional advice presented as qualified — legal, medical, tax, financial
  • Anything intended to deceive: fake reviews, impersonation, astroturfing
  • Content presented as human-authored where the audience is entitled to know
  • Processing sensitive data the workspace is not approved for
  • Autonomous action with material consequences and no human checkpoint
  • Circumventing a control your organisation deliberately put in place
Three questions that classify almost any case
  1. Who is accountable for the outcome? If the answer cannot be a person, it is inappropriate as designed.
  2. Would the affected person object to how this was produced? If yes, you have either a transparency duty or a use you should not make.
  3. Is there a control that makes this safe? Usually yes — review, redaction, a narrower scope, an approved workspace. Find it before concluding the work cannot happen.
Trap — the binary Most items in this objective are not "allowed vs forbidden" but "which control makes this appropriate". A rejected use case is usually a use case with a missing control. The two symmetric wrong answers are proceeding with no control and abandoning a legitimate task, and both appear regularly.
Marketing wants Claude to write product reviews to post under customer names. What is your answer?
No — that is fabricated testimony attributed to real or fictitious people, it deceives buyers, and in many jurisdictions it is unlawful as well as against acceptable use. There is no control that makes it acceptable, because the deception is the point of it. What you can offer instead is legitimate and close to what they want: draft outreach that asks real customers for reviews, summarise genuine feedback into themes for the product page, or draft clearly-marked marketing copy in the company's own voice.
HR wants help screening 300 applications. Appropriate or not?
Appropriate with controls, inappropriate as autonomous screening. Claude can extract stated qualifications and experience against the published criteria and produce a consistent structured summary per applicant — which, done well, is more consistent than 300 tired human skims. What it must not do is rank, reject, or shortlist as the operative decision. A named human decides, the criteria get a bias review, the reasons are recorded, and you check whether local law or company policy restricts automated processing in recruitment at all.
A colleague asks Claude to explain their MRI report because their appointment is weeks away. Where is the line?
Explaining terminology and general context is reasonable and genuinely helpful — what a term means, what a procedure involves, what questions to ask. Interpreting their results, offering a prognosis, or advising on treatment is clinical advice, and the harm is not hypothetical: a plausible-sounding misreading could lead someone to relax about something urgent or panic about something benign. The right answer is general explanation plus a clear statement that only their clinician can interpret the findings — and if the wait is the real problem, help them draft the question that gets the appointment brought forward.

6.2 · Apply data sensitivity, regulatory, and privacy considerations

The habit this objective certifies Before pasting or attaching anything, ask: what is in this, whose is it, and is this workspace approved for it? The most common real-world failure is not a malicious act but an unthinking paste of a file whose contents the person never actually looked at.

Data minimisation, concretely

  • Redact — remove the identifiers the task does not need. Most analysis does not need names.
  • Pseudonymise — "Customer A" preserves the ability to reason about the same person across a document without identifying them.
  • Aggregate — send the pattern, not the records, where the question is about the pattern.
  • Excerpt — the two relevant paragraphs, not the whole file. Also produces better answers.
  • Synthesise — for testing a prompt or a workflow, invented data of the same shape works and carries no risk at all.
Trap — instructions as a data control "Upload it but tell Claude not to store or use it" is the single most tempting wrong answer in this domain. Retention and training are governed by the product tier, the workspace configuration and the contract — not by a sentence in the prompt. The control is what you put in, plus using an approved environment. Note also that incognito chats reduce what is saved to history and memory but are not a clearance to process regulated data, and they are unavailable inside Projects.
You need sentiment themes from 5,000 survey responses that include free-text mentioning individuals by name. What do you do?
Strip the names before the data goes anywhere — the analysis is about themes, so identities are not needed, and removing them eliminates the risk rather than managing it. Pseudonymise if you need to track the same respondent across fields. Then confirm the workspace is approved for survey data at all, and check what respondents were told the data would be used for, because a purpose limitation in the privacy notice binds you regardless of technical controls.
A client contract says their data may only be processed within named systems, and Claude is not one of them. Your colleague says our internal policy permits it. Who is right?
The contract governs — a third party's data carries that third party's restrictions, and your internal policy cannot grant you permission over data you hold under someone else's terms. Either work without the client's data, or get the contract varied with the client's agreement through the proper route. This is a genuinely common real-world trap, because internal policy compliance feels like sufficient diligence.
Someone pastes a spreadsheet to ask a formula question, not realising it contains 2,000 customer records. What now?
Treat it as a data incident, not an embarrassment: report it through your organisation's incident process, because that judgement — whether it is notifiable, what remediation is needed — is not yours to make alone. Then reduce the exposure you can, and fix the cause, which is procedural rather than technical: people should check what a file contains before attaching it, and a formula question needs only a few synthetic rows of the same shape. Quietly deleting the chat and saying nothing is the wrong answer.

6.3 · Follow organizational AI policies and governance standards

This objective has an unusual property that the exam exploits: the correct answer often depends on a policy the stem does not state. When that is the case, the correct answer is to find out — not to substitute your own judgement, and not to assume the restrictive reading either.

What policy typically governsWhy you cannot infer it

Policy beats preference — including your own good judgement If policy prohibits something you consider low-risk, you follow the policy and, if you think it is wrong, raise it through the route that can change it. "It is obviously fine" is not an option the exam ever scores as correct, because the whole point of governance is that individual judgement is not the control.
When no policy exists A common and realistic stem. The answer is not "do whatever seems sensible" and not "stop all use". It is: act conservatively for now — no sensitive data, human review, keep records of what you did — and escalate to whoever should own the policy so a decision gets made properly. Proceeding quietly in a vacuum and waiting indefinitely for a policy are both wrong.
Your organisation has no AI policy and a manager asks you to run a client project through Claude. What do you do?
Neither refuse nor proceed silently. Establish what you can — the contractual position on the client's data and whether the workspace is an approved corporate one — and in the meantime work in the most conservative way that still delivers: no client-identifying data, human review of everything, a record of what was used and how. In parallel, escalate to legal, IT or risk so the policy question gets an owner and a real answer. That combination is what the exam consistently rewards: the work proceeds, the risk is bounded, and the gap gets closed by the people who should close it.
Policy requires disclosure of AI assistance in client deliverables. A colleague omits it because "it's only a first draft that we edited heavily". Your view?
The policy applies, and heavy editing does not remove the obligation — the disclosure exists so the client can make their own judgement, which is not ours to pre-empt. If the requirement is genuinely impractical for edited drafts, that is a legitimate argument to take to the policy owner, and until it changes, the deliverable carries the disclosure. Note the shape of the reasoning in the excuse: a plausible justification for a small deviation, which is how governance erodes.
Policy says only the corporate workspace may be used. Someone uses a personal account to finish urgent work. How serious is that?
Serious, and it needs reporting rather than overlooking. Corporate workspaces exist because of specific contractual terms about data handling, retention, training and access — a personal account has none of them, so company or client data has left the governed environment and the organisation cannot account for where it went. Urgency is a real pressure and it does not change the exposure. The right response is to report it, work out what data was involved, and fix the underlying problem that made the shortcut attractive.

6.4 · Understand the ethical implications of AI usage

Beyond rules, four themes the exam returns to. They tend to appear as scenarios where nothing is being broken and something is still wrong.

ThemeThe concernWhat you do about it
Transparency People are entitled to know when a decision affecting them, or content addressed to them, was AI-assisted Disclose where it matters to the reader or is required. Never present AI output as personally authored where authorship is part of what is being assessed or relied on
Fairness Systematic disadvantage to a group, from training data, from your inputs, or from criteria that proxy for protected characteristics Review the criteria and the inputs, not just the outputs. Test for disparate effect. Keep a human decision-maker on decisions about people
Accountability "The AI decided" is not an answer to anyone — not a customer, not a regulator, not a tribunal Name the person accountable for each decision. Keep the basis of the decision on record

The question that finds the ethical problem Who bears the cost if this is wrong, and did they get any say? When the person exposed to the error is not the person who chose the design — a customer, an applicant, a junior colleague — you have found the issue, and the fix is either a control or their involvement.
Trap — a disclaimer as a substitute for a control "Add a note saying this was AI-generated" is transparency, and transparency is not accuracy, fairness or accountability. A disclaimer on unreviewed clinical guidance does not make it safe; a disclaimer on a biased screening process does not make it fair. Disclose and control.
A performance-review process uses Claude to draft each review from manager notes. Managers approve them. What are the ethical considerations?
Several, none of which is a rule violation on its face. Fairness: are reviews drafted from thin notes now more uniform in language but less specific about actual contribution, and does that disadvantage people whose managers write less? Transparency: do employees know how their review was produced, given they are entitled to respond to it? Accountability: is approval genuine review, or a click at the end of a queue of thirty? And substance: a review that reads well from three bullet points may be filling gaps with plausible generic praise, which is unfair in both directions. The controls are managers adding specifics that only they know, employees being told the process, and the manager's ownership being real rather than nominal.
A support team's AI-drafted replies are sent under individual agents' names with no indication. Is that a problem?
It depends on what the signature is doing. A drafted reply that an agent reads, edits and stands behind is ordinary tool use and needs no disclosure — the agent is genuinely the author of the response. An unread draft sent automatically under a person's name misrepresents both the authorship and the attention the customer received, and it also means nobody checked it, which is a Domain 2 failure sitting inside an ethical one. Check policy too: some organisations and jurisdictions require disclosure of automated customer communication regardless.
An efficiency programme will use Claude to double each analyst's caseload. Analysts have not been consulted. What is your input?
Raise the consultation gap as a design problem, not just a courtesy one: the people doing the work know which cases are hard, where the current process protects against error, and what breaks at double volume — and the programme will be worse without that. Then look at where the cost of error lands. If the review time per case halves while accountability for mistakes stays with the analyst, the design has moved risk onto the people with least ability to refuse it. Neither opposing the efficiency goal nor accepting the target unexamined is the right answer.

Domain 7 · Troubleshooting and Optimization 10% · ~6 items

Three objectives, the smallest domain, and the one that most rewards a disciplined habit: diagnose before you change anything.

Real scenario
Northwind Retail: the descriptions have gone bland

The complaint. The first 200 product descriptions read well. The last 2,000 are interchangeable. Three changes were proposed in the first ten minutes: a stronger model, a longer prompt, more examples.

Diagnosis first. A sample of 30 bland outputs against 30 good ones showed two unrelated causes:

  • The brand-voice guide contains three sentences marked “always include”. In a 90-word description they consume most of the space, so there is nowhere for anything product-specific to go. The guide was doing the damage.
  • The bland items’ input contained only a title and a price. The good ones had a spec sheet attached. The model was not being lazy; it had nothing to work with.

Two causes, two fixes: loosen the mandatory phrasing to one sentence, and supply the spec sheet for items that have one. Neither was on the original list of three, and any one of those three would have been shipped, measured as “a bit better”, and left the real causes in place.

Takeaway · Diagnose before you change anything, and change one thing at a time. A quality complaint usually has more than one cause, and the most popular fixes — bigger model, longer prompt, more examples — are the exam’s favourite distractors precisely because they sound like progress.

7.1 · Identify, diagnose, and resolve issues with underperforming prompts or poor outputs

Diagnose in this order — the order is the answer to most items
  1. Input. Did Claude actually have what it needed? Was the document attached, current, readable, complete? Most "poor output" is missing input.
  2. Instruction. Was the task, audience, format and scope specified? Was there a missing-information rule?
  3. Structure. Was it too many tasks at once? Was the context diluted by a very long thread?
  4. Configuration. Is a stale document or a contradictory instruction in the Project shaping this?
  5. Capability. Only now: is the reasoning genuinely beyond this tier? Step up, or enable extended thinking.
Steps 1–4 are free and fix the large majority of cases. Step 5 costs money and is where untrained troubleshooters start.

A tier change is the right answer only when the input was complete, the instruction was specific, and the failure is in the reasoning itself — and a stem that mentions a missing document or a vague request has already told you it is not that.
Output about your product is confidently wrong on features. Someone proposes the top-tier model. Diagnose properly.
Check the input first: does Claude have your current product documentation at all? If not, this is not a capability failure — it is being asked about something it has never seen, and every tier will produce a plausible invention. Add the documentation to Project knowledge (or connect the live source), require citations, and add the missing-information rule. The top-tier model with no documentation gives you a more articulate wrong answer at higher cost, which is exactly the trap.
A prompt that worked reliably for months has started producing worse output, with no change to the prompt. Where do you look?
At everything except the prompt, since the prompt is the one thing that did not change. Candidates in order: the Project's knowledge (something added, something now superseded, something contradictory), the instructions (a rule bolted on for a one-off), the inputs (a source document changed shape or content upstream), and the work itself (the task has quietly evolved and the configuration has not). A changed model version is possible and worth confirming, but it is far down the list — configuration drift is the overwhelmingly common cause and the exam treats it as the default hypothesis.

7.2 · Adjust approach based on feedback and results

The objective is about running the loop on evidence rather than impressions — which requires that you have evidence at all.

  • Collect feedback specifically. "It's not great" is unusable. "It missed the exclusion clause in three of ten contracts" is a defect you can fix and re-measure.
  • Separate one-off from systematic. A single complaint may be a bad case; the same complaint three times is a defect in the design. Do not restructure a workflow on one data point, and do not dismiss the third report as bad luck.
  • Measure against a baseline. Better than what? If you did not record the starting error rate or handling time, you cannot demonstrate improvement — or notice regression.
  • Change one thing at a time, or you will not know what worked.
  • Watch for regression. A change that fixes one defect often reintroduces another. Keep a small standing set of cases you re-check after every change.
  • Close the loop with the people who reported it. Feedback that visibly changes nothing stops arriving, and then you are flying blind.
Keep a small evaluation set Ten to twenty real cases with known-good answers, re-run after every change to prompt, configuration or tier. It is the cheapest professional habit available, it turns "seems better" into a number, and it catches the regressions that otherwise surface in front of a client. Where a stem asks how to know whether a change helped, this is the answer.
Trap — reacting to the loudest single complaint One senior stakeholder's bad experience with one case is a data point, not a mandate to redesign. Log it, check whether it recurs, and look at the whole population — the risk is that you rebuild a workflow around a case that never happens again while the actual systematic defect stays in place.
Users say a summarisation workflow is "less useful than it was". You have no metrics. What do you do first?
Convert the impression into specifics before changing anything: ask for recent examples of both bad and acceptable outputs, and read them for a pattern — is it omission, wrong level, wrong format, or staleness? At the same time build the baseline you should already have had: a small set of real cases with known-good answers, so the next change can be measured. Changing the tier or rewriting the prompt on the strength of "less useful" is a guess, and if it happens to help you still will not know why.
You make three changes at once and quality improves. What have you learned?
That the combination helps, and nothing about which part did. That matters because one of the three may be doing nothing (permanent unnecessary cost or complexity) and one may be doing harm that the others mask. If the change is cheap and stable, banking it is defensible; if it involves ongoing cost — a higher tier, say — isolate the contributions against your evaluation set so you are not paying for a change that does not earn it.

7.3 · Optimize workflows for efficiency and effectiveness

Two words that pull in different directions, and the exam is careful about which one a stem is asking for. Efficiency is less time, cost or effort per unit. Effectiveness is a better outcome. Optimising one at the expense of the other is a failure, not a trade.

LeverImprovesWatch out for
Persist configuration in a ProjectBothAlmost always right. Needs an owner and a review cadence
Fix the output shapeBothFaster to produce, review and consume. Fields must stay stable across runs
Tier the work — cheap pass plus strong pass on the hard sliceBothNeeds a reliable way to identify the hard cases
Use the cheaper tier where quality holdsEfficiencyVerify quality holds before, not after. Measure it
Batch similar items in one passEfficiencyToo large a batch produces shallow averaged output
Decompose into checkpointed stagesEffectivenessMore steps; worth it when errors are expensive or hard to localise
Route review by risk, sample the restBothKeep a random sample of the unflagged population, or you cannot see your true error rate
Skip the review stepNeitherNot an optimisation. It moves cost onto whoever receives the error
Optimise the whole loop, not the model call Time-to-usable-output includes review and rework. A change that makes generation 30% faster but doubles review time is a loss. This is why a fixed, checkable output shape often beats a model upgrade as an optimisation: it cuts the expensive human minutes, not the cheap machine ones.
The best optimisation is usually removing a step Before making a step faster, ask whether it needs to exist. Reformatting by hand, re-explaining context every session, copying between systems, and reconciling three people's inconsistent output are all steps that a better design deletes rather than accelerates.
A workflow's generation is fast but each output takes 20 minutes to review. Where is the optimisation?
In the review, because that is where the time is. Attack it structurally: fix the output shape so a reviewer can scan rather than read, require a source citation per claim so verification is a lookup instead of a hunt, have the mechanically checkable parts checked mechanically, and mark the items the output itself is unsure about so attention goes where it is needed. Speeding up generation optimises the part that is already cheap.
Moving to a cheaper tier would halve cost. What must you establish first, and what do you keep watching?
Establish that quality holds on your evaluation set — run both tiers on the same real cases and compare against the criteria that matter, rather than assuming. Then keep watching, because the distribution of incoming work drifts: a tier that handles today's cases may not handle next quarter's, so keep the sampling review running and re-check the evaluation set periodically. A cost saving that quietly raises the escaped-error rate is not a saving, it is a transfer.

The distractor catalogue — how to eliminate two options before you decide

The Overview lists the eight patterns in summary form. This section is the working version: the elimination cues, and what the exam wants instead. Read an option and ask which pattern it is; two of four usually match one, and you are choosing between the remaining pair.

PatternElimination cue in the option textWhat survives instead
1 · Self-assessment as evidence "ask Claude to verify / rate its confidence / check its own work", "if it says it is confident" An independent check: the source document, the system of record, a qualified person
2 · Instruction as a control "tell Claude not to retain / not to use / to keep confidential" Change the input — redact, aggregate, excerpt — or use an approved environment
3 · Cosmetic fix "reword", "make it sound more authoritative", "add a disclaimer", "format it more professionally" Fix the defect: verify the fact, close the gap, name the audience, add the missing control
4 · Abandon the task "do not use Claude for this", "do it entirely manually", "wait until policy exists" The proportionate control that lets the legitimate work proceed
5 · Biggest model reflex "use the most capable model to be safe", "upgrade the tier" with no task-based reason Match the tier to the hardest step; diagnose input and instruction first
6 · Re-prompting harder "tell it to be accurate / thorough / careful", "emphasise the instruction" Supply the missing input, or decompose, or persist the rule in configuration
7 · Re-explaining every time "paste the guidelines into each new chat", "remind Claude at the start of every session" Project instructions and knowledge, owned and maintained
8 · Wrong escalation "hand it to engineering" for in-product configuration · "build the API integration yourself" as an Associate Associates own in-product configuration and judgement; APIs, architecture and agentic systems go to Architects and Developers
Three tie-breakers when two options both look defensible
  1. Which one consults something outside the model? That one, on any accuracy question.
  2. Which one is proportionate to the stated consequence? Match the control to the stakes in the stem — not to the maximum caution available.
  3. Which one fixes it for next time? On configuration and workflow questions, the answer that persists or maintains beats the answer that patches today's output.
The over-caution trap deserves its own warning Candidates who have studied risk over-correct and pick the most restrictive option every time. The exam scores over-caution as wrong: refusing legitimate work, demanding expert review of an internal meeting note, or abandoning a use case that a redaction would have made fine. Read what the stem actually says about consequence, and answer that.

How to read a stem

  1. Find the question. Read the last sentence first. Business stems carry a lot of scenery; the actual ask is usually one clause.
  2. Note the count. "Select two" changes everything about how you read the options.
  3. Identify the consequence. Internal or external? Regulated? About a person? Reversible? This single fact decides most Domain 2 and Domain 6 items.
  4. Identify the constraint. Volume, deadline, budget, confidentiality — whichever is stated is stated for a reason.
  5. Answer before reading the options where you can. It stops a fluent distractor from anchoring you.
  6. Eliminate by pattern. Two options will usually match the catalogue above.
  7. Choose the one that engages the stated constraint. If an option ignores the constraint the stem went to the trouble of giving you, it is wrong.

One-page cheat sheet

The whole hub, compressed. If you read one thing on the morning of the exam, read this.

Prompting

  • Five components: role/audience · context · task · constraints · output shape
  • The highest-value line: "if it is not stated, say not stated"
  • Examples beat adjectives
  • Decompose where you would want to inspect the middle
  • Iterate: name the defect, classify it, change one thing, re-measure, promote what worked
  • Analysis and research: constrain and ground. Brainstorming: widen first, judge second

Validation

  • Fluency is evidence about the writing, never about the facts
  • The check must be independent of the thing being checked
  • Verify: citations, figures, dates, names, quotes, causal claims, arithmetic
  • Count the inputs against the outputs — 8 in, 8 out
  • Self-critique and confidence ratings are triage at best
  • Re-runs locate unstable claims; agreement is not truth
  • Keep a random sample of the unflagged population

Human review is mandatory for

  • Legal, medical, financial, tax, safety advice
  • Decisions about people
  • Money and binding commitments
  • External publication under the organisation's name
  • Anything for a regulator, auditor or court
  • Irreversible actions
  • Match the reviewer's qualification to the risk

Surface and tier

  • Needed again → Project. Rules → instructions. Material → knowledge
  • Source changes → connector. Static → upload
  • Edited or reused → artifact. Read once → inline. Consumed by a system → structured
  • Many sources to reconcile → Research
  • Arithmetic over data → execute code
  • Tier = the hardest cognitive step, not the audience's seniority
  • High volume with a hard minority → tier the workflow

Governance

  • Ask before pasting: what is in this, whose is it, is this workspace approved
  • Minimise: redact, pseudonymise, aggregate, excerpt, synthesise
  • An instruction is not a data control
  • A third party's contract beats your internal policy
  • No policy? Act conservatively, keep records, escalate to an owner
  • A disclaimer is transparency, not a control
  • Ask who bears the cost if this is wrong, and whether they had a say

Troubleshooting order

  • 1 Input · 2 Instruction · 3 Structure · 4 Configuration · 5 Capability
  • Steps 1–4 are free and fix most cases
  • "Used to work" → configuration drift, not capability
  • Keep 10–20 real cases as an evaluation set
  • Change one thing; re-measure against a baseline
  • Optimise the whole loop — review time is where the minutes are
  • Skipping review is never an optimisation
