All 37 objectives, from first principles

This is written to be understood, not memorised. Each section gives you the mechanism (what is actually happening), the surface (the exact file, flag, field or parameter), the decision rule the exam grades on, the anti-patterns it plants as distractors, and drills. Sections marked priority map to objectives you scored 0% on.

How the Attempt-2 exam is shaped Items are long. A single question sets up a system — a pipeline, a review bot, a support orchestrator — and then asks one thing that requires you to hold two or three objectives at once: the topology and the context contract, or the tool distribution and the call ordering. That is why section-by-section recall is not enough, and why every section below ends by connecting itself to the others.
Version-sensitive surfaces CLI flag spellings, hook event names, frontmatter keys and supported JSON Schema keywords move between releases. Everything here reflects documented behaviour at the time of writing; re-check the exact spellings against the live docs close to your exam date. The decision rules are stable — those are what the exam is really testing.

F1 · The agentic loop, precisely

Everything in this blueprint is a variation on one loop. Claude Code is this loop. A subagent is this loop with a different system prompt and a smaller tool list. An Agent SDK program is this loop with your code in the middle. If you can say exactly where in the loop a described failure happened, most architecture questions answer themselves.

state: messages[]            // the ENTIRE conversation, resent every time
loop:
  response = POST /v1/messages { model, system, tools, messages, max_tokens }
  append response to messages
  switch response.stop_reason:
    "tool_use"   -> for each tool_use block: run it, collect a tool_result
                    append ONE user message containing every tool_result
                    continue loop
    "end_turn"   -> the model has finished speaking. TERMINAL for this turn.
    "max_tokens" -> output was CUT OFF mid-generation. Not a success.
    "refusal"    -> the model declined. TERMINAL. Route to a human.
    default      -> unknown: treat as terminal, escalate, never silently drop
  until turn budget / wall-clock budget / cost budget is exhausted

The three budgets, and why the exam cares

A loop that can only be stopped by the model finishing is a loop that can run forever. Production agent systems bound themselves three separate ways, and the exam expects you to name the right one for a described failure:

BudgetBounds whatSurfaceFailure it prevents
Turn budgetNumber of loop iterations--max-turns (CLI), your own counter (SDK)An agent ping-ponging between two tools forever
Wall-clock budgetElapsed real timeYour own deadline check inside the loopA single slow tool call blowing an SLA
Cost budgetTokens/spendAccumulated usage from each response, checked per iterationA runaway CI job billing thousands of dollars
Rule — a budget that is not handled is not a safeguard Hitting --max-turns stops the loop; it does not decide anything. Every budget exit must land in an explicit branch that records an outcome (escalate, fail the build, write a partial result with a reason code). "The loop ended" is not an outcome. This is the single most reliably-tested idea in both blueprints.

Stop reasons, complete

ValueMeaningCorrect handling
tool_useOne or more tool_use blocks; Claude is waitingRun every tool, return a tool_result for each tool_use_id, continue
end_turnClaude finished generatingTerminal for the turn. Not proof that anything happened in the world
max_tokensOutput truncated mid-generationNever parse as final. Continue generation, or re-scope the request (see S28)
stop_sequenceA custom stop sequence was emittedTerminal per your grammar
pause_turnA long-running server-side tool turn pausedSend the response back unchanged to continue the same turn
refusalClaude declined on safety groundsTerminal. Escalate; do not retry the identical prompt
model_context_window_exceededInput exceeded the windowCompact or split, then retry (see X21)

Tool-result protocol rules that get tested

  • Every tool_use must be answered by a tool_result with the matching tool_use_id, in the immediately following user message.
  • Within that message, tool_result blocks come first; free text after. Text first is a 400.
  • If the model emitted three parallel tool_use blocks, you must return three results in one message — not three messages.
  • A tool failure is a normal tool_result with "is_error": true and an instructive message, not a dropped turn.
  • Tool results are untrusted external content. They stay inside tool_result blocks and are never promoted into the system prompt.
An agent hit --max-turns in CI and the job went green. What is the defect?

The turn budget was treated as a stop condition rather than a decision point. Turn exhaustion means the agent did not finish; the exit code must reflect that. The fix is a branch on budget exhaustion that fails the job with a reason code and emits whatever partial findings exist, so the failure is visible and diagnosable rather than being laundered into a pass.

Why is end_turn not evidence that a task was completed?

end_turn reports that generation stopped, nothing more. It fires identically for "I have opened the PR, here is the link" and for a hallucinated version of the same sentence. Completion is a property of the world — a PR exists, a row was written, a file changed on disk — so a correct orchestrator verifies against the system of record before recording success.

F2 · What "context" actually is

The API is stateless. There is no server-side conversation. Every request carries the whole history, and "the agent remembers" is an illusion produced by resending. Four consequences drive a surprising number of exam items:

  1. Context is a budget you spend, not a place you store things. Every token of history is re-billed and re-read on every single turn. A 40-turn session is not 40 requests; it is 40 requests of monotonically increasing size.
  2. A subagent has no access to the coordinator's history unless you put it in the prompt. This is not a limitation to work around — it is the entire point of a subagent, and it is the source of objective O3.
  3. Anything not in the current request does not exist. "It knew that earlier" is never an explanation; either it is in messages, in system, in a tool result, or it is gone.
  4. Losing context is silent. Compaction, truncation and summarisation do not raise errors. The agent simply becomes confidently wrong about a constraint it agreed to nine turns ago.
Anti-pattern — "the subagent should just ask the coordinator" Round-tripping to the coordinator for missing context is the distractor in a whole family of questions. It doubles latency, burns the coordinator's own window with sub-conversations, and often is not even possible in the topology described. The correct answer is nearly always: the delegation prompt should have contained it.

F3 · The four enforcement surfaces

Given "how do we make sure X happens", there are exactly four places the requirement can live. The exam tests this ranking relentlessly, in both blueprints, in a dozen disguises.

SurfaceMechanismStrengthUse when
1. Code / configPermissions, hooks, backend validation, CI gatesGuaranteed Runs regardless of what the model decidesThe requirement is a must: security, spend, compliance, data integrity
2. SchemaJSON Schema on a tool, strict, enums, tool_choiceStructurally enforced Shape is guaranteed; truth is notYou need machine-parseable output, or a specific tool must be called
3. ContextCLAUDE.md, .claude/rules/, Skills, few-shot examplesStrong influence Shapes behaviour, cannot guarantee itConventions, house style, "how we do things here", domain knowledge
4. Prompt text"Please always remember to…"Weakest Fails exactly when things have already gone wrongAlmost never, as a control. Fine as an explanation
The rule that answers a third of the exam When two options both "work", the correct one moves the requirement down the list — from prompt to context, from context to schema, from schema to code. Distractors move it up: they add a probabilistic layer on top of a structural hole. Ask yourself: if the model ignored this entirely, what would happen? If the answer is "the bad thing happens", it is in the wrong surface.
Security says a directory must never be read. Where does that live?

Surface 1: a permissions.deny rule such as Read(./infra/secrets/**), deployed through managed settings so a local file cannot override it. A CLAUDE.md line is surface 3 and is advisory; a PostToolUse hook that alerts on the read is surface 1 but fires after the secret is already in context, which is too late for a confidentiality requirement.

Orchestration · Why multi-agent at all

Before any topology question, be clear about what a second agent actually buys you. There are exactly two legitimate reasons, and a long list of illegitimate ones.

Reason 1 · Context isolation real

A subagent starts with a clean window. It can read 40 files, form a conclusion, and return 200 tokens. The 40 files never touch the coordinator's context. This is the dominant reason in codebase work: you are trading a round trip for window headroom.

Reason 2 · Parallelism real

Four independent investigations run concurrently instead of serially. Only valid when the subtasks genuinely do not depend on each other's findings — otherwise you have parallelised guessing.

Non-reason · "Specialisation makes it smarter"

A subagent with a security-flavoured system prompt is not a security expert; it is the same model with a narrower brief. The gain is focus and recall on one concern (see C24) — real, but it is a prompting gain, not an intelligence gain.

Non-reason · "It mirrors our org chart"

Topology should follow data dependencies, not team structure. An agent per team is how you get four agents that each hold a third of the answer and no component that owns the whole.

The cost side, which distractors omit Every subagent is a fresh system prompt, a fresh tool-definition block, and a fresh delegation prompt — paid on every one of its turns. Multi-agent is a latency and coherence optimisation that usually costs more tokens, not fewer. If a question frames multi-agent as the cheap option, that framing is the trap.

Orchestration · Topologies and how to choose O10

The three shapes

COORDINATOR-WORKER (hub and spoke)          PARALLEL FAN-OUT / GATHER
        coordinator                                 coordinator
       /     |      \                              /    |    \
   worker worker  worker                       w1     w2     w3
       \     |      /                              \    |    /
        coordinator  (merges)                        synthesis

SEQUENTIAL PIPELINE
   stage1 -> stage2 -> stage3 -> stage4     (each stage's output is next stage's input)
TopologyChoose whenFails atSignature in a question
Coordinator-worker Subtasks are heterogeneous, need different tools, and one component must own the final answer Coordinator becomes a bottleneck and a single point of context pressure "…dispatches specialised agents and composes the customer-facing reply"
Parallel fan-out Subtasks are independent, homogeneous, and latency matters; coverage beats depth Contradictory findings with nothing to reconcile them; duplicated work "…research N sources concurrently and produce one report"
Sequential pipeline Each stage genuinely needs the previous stage's output; you want checkpointing Latency is the sum of all stages; one stage's failure stalls everything "…extract, then validate, then enrich, then load"
Hybrid (most real systems) A pipeline whose middle stage fans out, e.g. plan → parallel investigate → synthesise → act Complexity; needs explicit state at each boundary Any question mentioning both "concurrently" and "then"
Decision rule — read the dependency graph, not the prose Write down which subtask needs which other subtask's output. Independent nodes go parallel. Dependent nodes go sequential. A node that needs everyone's output is a synthesis stage. The topology is then forced — it is not a style choice, and any option that picks a topology contradicting the dependency graph is wrong regardless of how well it is argued.

Coverage, latency, reliability — the stated trade-off

The objective names three properties, and questions usually pin two and ask you to optimise the third:

  • Coverage ↑ with more parallel workers and broader tool access; ↓ when one agent must do everything within one window.
  • Latency ↓ with parallelism and with multiple tool calls per turn; ↑ with every additional sequential hop, including every subagent round trip.
  • Reliability ↑ with checkpointing, structured returns and a single owner of the merged result; ↓ with peer-to-peer chatter and implicit state.
Anti-pattern — subagents calling subagents Letting workers invoke each other directly abandons hub-and-spoke: no component owns the merged outcome, failures become untraceable, and coordination paths grow combinatorially. When an option offers peer-to-peer delegation as a fix for a missing-context problem, the real fix is a better delegation package (O3).
Four investigations, three of which need the first one's output. Topology?

Hybrid: run investigation one alone, then fan out the remaining three in parallel with its result packed into each delegation prompt, then synthesise. Answering "all four in parallel" parallelises three agents that will guess; answering "all four sequentially" pays three unnecessary round trips.

Orchestration · Multiple tool calls in one turn O1

Distinct from multi-agent parallelism and frequently confused with it. This is one agent, in one response, emitting several tool_use blocks that your executor runs concurrently.

// One assistant response, three tool_use blocks:
{ "stop_reason": "tool_use",
  "content": [
    { "type": "tool_use", "id": "tu_1", "name": "get_employee",  "input": {...} },
    { "type": "tool_use", "id": "tu_2", "name": "get_policy",    "input": {...} },
    { "type": "tool_use", "id": "tu_3", "name": "get_inventory", "input": {...} } ] }

// ONE user message answering all three — order of blocks does not matter,
// completeness does:
{ "role": "user", "content": [
    { "type": "tool_result", "tool_use_id": "tu_1", "content": "..." },
    { "type": "tool_result", "tool_use_id": "tu_2", "content": "..." },
    { "type": "tool_result", "tool_use_id": "tu_3", "content": "..." } ] }

What you control

  • The model decides whether to batch calls; it does so when the calls are visibly independent. Tool descriptions that state independence ("does not require any other lookup first") make batching more likely.
  • You must execute them concurrently to get the benefit. Running three parallel tool_use blocks serially in your executor produces the token pattern of parallelism with the latency of sequence — a favourite distractor.
  • To forbid batching, set disable_parallel_tool_use: true inside tool_choice. You do this when calls have side effects that must be ordered, or when a downstream system cannot tolerate concurrency.
Rule — parallel only where there is no data dependency get_order and get_policy can go together. lookup_order and process_return(order_id) cannot, because the second consumes the first's output. Forcing parallelism across a dependency makes the model invent the missing input — which is exactly the failure in M37.
Latency did not improve after the model started batching. Why?

Almost always the executor. The three tools were dispatched in a for loop and awaited one at a time. Batching by the model only removes round trips to the API; the wall-clock win requires your side to fan the calls out concurrently and join.

Orchestration · The delegation package 67% O3

A subagent starts with an empty context and sees exactly three things: its system prompt, its tool definitions, and the delegation prompt you hand it. Anything else it needs, it must be told. The objective is explicit that it must complete its task without returning to the coordinator for missing context.

The five-part package

PartContainsFailure if omitted
1. ObjectiveThe outcome required, in one sentence, stated as a goal not a procedureThe agent optimises for the wrong thing, or stops early
2. Accumulated findingsWhat is already known and must not be re-derived — facts, decisions, prior stage outputDuplicated work; contradictory conclusions; wasted turns
3. Structured dataIDs, records, parameters the task operates on, in machine form, not paraphrasedThe agent invents plausible values (the classic hallucination path)
4. Source metadataWhere each fact came from: file path and line, document ID, tool that produced it, timestampSynthesis cannot cite, cannot resolve conflicts, cannot express confidence
5. Constraints & output contractAuthority limits, exclusions, and the exact shape to returnOut-of-scope actions; output the synthesis stage cannot parse
# Delegation prompt — logistics subagent
## Objective
Determine whether order SO-88213 can still be rerouted, and to where.

## Established facts (do not re-derive)
- Customer verified at 09:14Z via verify_identity (tool: identity.verify, conf 0.99)
- Order SO-88213 placed 2026-08-19, seller SLR-4417, status IN_TRANSIT
- Customer's new address: 14 Bridge St, Bristol BS1 4ND  (source: chat turn 6)
- Carrier: NW-Express, tracking NWX-99120  (source: get_order tool result)

## Constraints
- You may call get_tracking, get_carrier_policy. You may NOT contact the seller.
- Reroute fees above $15 require coordinator approval; report, do not commit.

## Return exactly
{ "reroutable": bool, "reason": str, "fee_usd": number|null,
  "sources": [{"claim": str, "tool": str, "ref": str}] }
Rule — the delegation prompt is a closure, not a pointer Pack the values, not references to where the values live. "Use the address the customer gave earlier" is a pointer into a conversation the subagent cannot see. "14 Bridge St, Bristol BS1 4ND" is a value. Every exam item in this family turns on that distinction.
Anti-patterns
  • Passing the coordinator's entire transcript — this destroys the isolation you delegated for, and re-imports all the noise.
  • Paraphrasing structured data into prose ("the order from a few days ago").
  • Omitting source metadata because "the finding is what matters" — then synthesis cannot tell a documented fact from an inferred one.
  • Relying on a shared system prompt to carry per-task facts. The system prompt is for the role; the delegation prompt is for the task.
A subagent returned a confident answer built on an invented order ID. Root cause?

Part 3 of the package was missing. The task referred to "the customer's order" without supplying the identifier, and the model produced a well-formed value because the schema demanded one. Two fixes stack: pack the real ID into the delegation prompt, and make the field nullable so absence is expressible (S26).

Orchestration · Goal-oriented vs procedural delegation O4

Two ways to write the objective line of a delegation package, and the exam wants you to know that the answer is not "always goal-oriented".

Goal-oriented

Determine whether this PR introduces
a security regression. You decide what
to read and in what order.

Gains: adapts to what it finds, handles cases you did not anticipate, needs fewer revisions as the codebase changes.
Costs: variable token use, variable path, harder to predict or reproduce.

Procedural

1. Read auth/middleware.ts
2. Grep for `verifyToken(`
3. Check each call site for the
   audience claim. Report per site.

Gains: deterministic, auditable, cheap, easy to test.
Costs: blind to anything outside the script; goes stale as the code moves; cannot react to discoveries.

Decision rule Use goal-oriented when the search space is unknown and adaptation is the point — investigation, research, diagnosis, review. Use procedural when the steps are genuinely fixed and compliance matters — a release checklist, a migration, an audited process. The exam's phrase "adaptive behaviour while maintaining coordinator visibility and control" describes the combination: a goal-oriented brief plus a structured output contract and explicit constraints. Control comes from the return schema and the tool allowlist, not from scripting the steps.
The pattern the exam rewards goal + constraints + tool allowlist + output schema. That gives the model latitude in how, while the coordinator retains certainty about what comes back and what could be touched. Answers that achieve control by enumerating steps are trading away the reason you delegated.

Orchestration · Constraining a subagent invocation O5

Three independent levers, tested separately and together.

1 · Tool restriction

In Claude Code, a subagent is a markdown file with frontmatter. The tools: key is an allowlist; omit it and the subagent inherits the full tool set, which is almost always wrong.

---
name: security-reviewer
description: Reviews a diff for security regressions. Use for auth, crypto,
             input-handling and secrets changes. Read-only.
tools: Read, Grep, Glob
model: sonnet
---
You are a security reviewer. You never modify files. For each finding, report
the file, the line, the vulnerability class, and the exploit path. If you cannot
demonstrate an exploit path, report it as an observation, not a finding.

2 · Context scoping

What the agent can see: the delegation prompt (O3), plus any directories added to its working scope. Narrow scope is not only a safety property — it materially improves tool selection, because the model is choosing among fewer plausible actions.

3 · System prompt / role

The markdown body is the subagent's system prompt. It defines the role and the standing rules, never the per-task facts. Role in the body; task in the delegation prompt. Mixing them is why subagents "remember" the previous task.

Rule — the three levers answer three different questions tools: answers "what may it do". Context scoping answers "what may it see". The system prompt answers "what is it for". A question that describes an agent doing something out-of-role is a tools: problem; one describing an agent that lacks a fact is a delegation-prompt problem; one describing an agent with the wrong judgement is a system-prompt problem.

Orchestration · Diagnosing subagent spawn failures O6

Given "the subagent did not run" or "ran but did nothing useful", there are four distinct causes with four distinct fingerprints.

CauseFingerprintFix
Not discoverableThe agent is never selected; the coordinator does the work itselfFile is in the wrong directory, or description does not say when to use it. Descriptions are the routing signal
Missing tool permissionSpawns, then fails or stalls on its first action; errors mentioning a tool it was not grantedAdd the tool to the subagent's tools: allowlist and ensure the parent session permits it
Wrong AgentDefinition parametersSpawns with the wrong role, model, or an empty prompt; behaves like a generic assistantCheck description, prompt, tools, model are all populated and spelled as the SDK expects
Absent coordinator wiringThe agent exists and is correct, but nothing ever invokes itThe coordinator's own prompt/plan must actually delegate; a defined agent is not a called agent
The permission subtlety A subagent cannot be granted a capability the parent session does not have. Adding Bash to a subagent's tools: does not help if the session's permission settings deny it. Two layers must agree, and questions like to break exactly one of them.

Orchestration · Dynamic task decomposition 0% — priority O7

You scored 100% on this in Attempt 1 and 0% in Attempt 2, which usually means the second exam tested the harder half: not "should plans adapt" (obviously yes) but "what does an adaptive decomposition actually look like, and when is a fixed sequence still correct".

The mechanism

A static decomposition computes the full subtask list once, from the initial request, and executes it. A dynamic decomposition computes an initial subtask list, executes some of it, and then re-plans from what came back. The re-planning step is the whole objective.

STATIC                                  DYNAMIC
plan = decompose(request)               plan  = decompose(request)      # initial, partial
for task in plan:                       done  = []
    run(task)                           while plan.has_ready_tasks():
merge(results)                              batch   = plan.ready_tasks()     # independent -> parallel
                                            results = run_parallel(batch)
                                            done   += results
                                            plan    = replan(plan, done)     # <-- the objective
                                        merge(done)

What replan is allowed to do

  • Add subtasks that only became knowable after a finding ("the audit log points at a second service — investigate it too").
  • Drop subtasks that a finding made moot ("the config is not deployed anywhere; skip the three downstream checks").
  • Re-scope a subtask with newly-available parameters (turning "find the offending migration" into "verify migration 0421").
  • Re-order when a dependency is discovered that was not visible at plan time.
Decision rule — dynamic when discovery changes the shape of the work Ask: can the result of subtask A change which subtasks exist? If yes, a fixed sequence is wrong by construction — it will either do work that is now pointless or miss work that has become necessary. If no — the steps are known in advance and invariant — a fixed sequence is better: cheaper, deterministic, testable, auditable.
Keeping control while being dynamic Dynamic does not mean unbounded. Every production version of this pattern bounds it:
  • a depth or iteration cap on re-planning rounds, so discovery cannot recurse forever;
  • a persisted plan object (task list with statuses) so the current plan is inspectable and resumable — this is also O9;
  • a rule for what may be added: new tasks must be in-scope for the original objective, not adjacent curiosities;
  • convergence: each round must close more tasks than it opens, or the loop is diverging and should escalate.
Anti-patterns the distractors use
  • "Generate a longer plan up front to cover more cases." A longer static plan is still static; it just wastes more when reality differs.
  • "Let each subagent decide what to do next and spawn its own follow-ups." That is not dynamic decomposition, it is unbounded recursion with no owner of the plan.
  • "Re-run the whole decomposition from scratch after every finding." Throws away completed work and loses the finding trail; re-plan is an update, not a restart.
  • "Ask the model each round whether it should continue." Self-assessment is not a termination condition; use the task graph and the caps.
An incident agent runs the same five diagnostics on every incident and misses novel causes. Fix?

Make the decomposition dynamic: run the cheap, always-relevant diagnostics first as an initial batch, then re-plan from their output — a spike in one dependency's error rate should generate the subtask "investigate that dependency", which did not exist at plan time. Keep a persisted task list, cap the re-planning rounds, and escalate if the round count is hit with the incident still open.

When is a fixed sequence the right answer despite this objective?

When the steps are invariant and the value is in compliance and repeatability: a release runbook, a data migration, a regulated onboarding flow. There, adaptation is a defect — you want the same steps in the same order every time, with a hook or gate enforcing it. Choosing "dynamic" reflexively is itself a trap.

Orchestration · Subagent output schemas O18

What comes back from a worker determines what synthesis can do with it. The objective names three content types deliberately, because the right format differs for each.

ContentFormatWhy
Structured data — findings, counts, statuses, IDsJSON with a fixed schema; enums for categoriesMust be merged, filtered, sorted and counted by code without parsing prose
Prose summary — reasoning, nuance, caveatsA bounded free-text field inside the structureSome judgement genuinely does not fit an enum; boxing it keeps it from contaminating the machine-readable part
Citation metadata — provenancePer-claim, not per-report: {claim, source, ref, confidence}Synthesis must attribute individual claims, resolve conflicts, and drop unsupported ones
{
  "agent": "security-reviewer",
  "status": "complete",                       // complete | partial | failed
  "findings": [                               // structured, mergeable
    { "id": "SEC-1", "severity": "high", "class": "missing_authz",
      "file": "src/api/orders.ts", "line": 142,
      "claim": "Handler reads :orgId from the path without checking membership",
      "evidence": [{ "source": "src/api/orders.ts", "ref": "L138-L151" }],
      "confidence": "established" }           // established | probable | contested
  ],
  "summary": "Two authz gaps, both on the orders router...",   // bounded prose
  "coverage": { "files_examined": 14, "files_skipped": 2,
                "skipped_reason": "generated code" },
  "unresolved": ["Could not determine whether middleware runs on this route"]
}
Rule — unresolved and coverage are not optional extras A worker that returns only findings is indistinguishable from a worker that found nothing because it looked in the wrong place. Reporting what was not examined, and what could not be settled, is what lets the coordinator decide whether to re-plan (O7) or escalate.

Orchestration · The synthesis agent and uncertainty O19

The synthesis stage is where multi-agent systems most often destroy their own value: three workers report three different things, and the synthesiser produces one confident paragraph that mentions none of the disagreement.

Rule — synthesis preserves the epistemic status of every claim A claim supported by two independent sources, a claim supported by one, and a claim two sources contradict are three different things. Collapsing them into uniform prose is a loss of information that no downstream reader can recover. Correct synthesis output distinguishes them explicitly.

What a synthesis prompt must specify

  • Conflict handling: when sources disagree, report both positions with their sources — never silently pick the more confident-sounding one.
  • Confidence propagation: a conclusion is at most as strong as its weakest supporting claim. Two "probable" inputs do not make an "established" output.
  • Attribution: every claim in the final report traces to a worker and a source.
  • Gap reporting: what no worker covered must appear in the output as a gap, not as silence.
  • No new facts: synthesis may not introduce claims absent from worker output. This is the single most valuable line in a synthesis system prompt.
Anti-pattern — "take the majority view" Three agents that read the same stale document agree with each other and are all wrong. Agreement between workers is only evidence if their sources were independent — which is exactly why per-claim source metadata (O18) has to survive the trip.
Two workers disagree on whether a rate limit applies. What should synthesis emit?

A contested finding naming both positions, both sources, and what would settle it — not an averaged answer and not a silent pick. If the decision downstream is expensive, the correct system behaviour is to route the contested item to a human (X22) rather than to resolve it by fiat.

Orchestration · Pipeline state and resumption O9

Any pipeline long enough to be useful is long enough to be interrupted — a deploy, an eviction, a rate limit, a crash. The objective is explicit about the two requirements: resume without repeating completed work and without losing prior findings.

What must be persisted, and where

ArtefactWhy it must survive
Task graph with per-task status (pending | running | done | failed)Tells the resumer what to skip and what to retry. Also the object O7's re-planner mutates
Per-task output, keyed by task IDThe findings themselves. Losing these is what forces repeated work
Input fingerprint (commit SHA, document hash, file mtimes)Lets you tell "already done" from "done against different inputs" — the basis of targeted re-analysis
Run metadata (prompt version, schema version, model)A resume that silently changes model or prompt version produces incomparable halves of one result
Rule — durable, out-of-process, and idempotent In-process state does not survive SIGKILL. Persist to a store that outlives the worker, make each task idempotent so a retry is harmless, and write the checkpoint after the task's effects are durable — not before, or you will skip work that never actually happened.
Targeted re-analysis — the efficient resume On resume, do not re-run everything and do not blindly trust every checkpoint. Compare the input fingerprint: tasks whose inputs are unchanged keep their cached output; tasks whose inputs changed are re-run; tasks that never ran are run. That is the same idea as X2 at pipeline scale.

Claude Code · context: fork 0% — priority O14

A Skill or slash command normally executes in the current session: it reads the conversation so far, and everything it does — every file it reads, every tool result it collects, every intermediate step — is appended to that same conversation and stays there for the rest of the session.

The context: fork frontmatter option changes that. The invocation runs in an isolated subagent context: a fresh window seeded with what the command needs, doing its work out of sight of the main thread, and returning only its result. The session gets the answer without inheriting the working-out.

---
name: audit-dependencies
description: Audit every dependency for known advisories and licence conflicts.
context: fork
allowed-tools: Read, Grep, Glob, Bash(npm audit:*)
---
Read package.json and the lockfile, run the audit, cross-check licences,
and return ONLY: a table of {package, version, advisory, severity, licence}
plus a one-paragraph risk summary. Do not include intermediate output.

Why it exists — the two failures it prevents

Context pollution

A dependency audit reads a 6,000-line lockfile and 40 advisory records. Without a fork, all of that sits in the main conversation forever, crowding out the work the developer was actually doing and pushing the session toward compaction.

Cross-contamination of state

The skill's exploratory reasoning — files it opened and rejected, hypotheses it discarded — becomes part of the session's history and influences later, unrelated answers. Forking keeps the skill's reasoning out of the session's reasoning.

Decision rule — fork when the work is wide and the result is narrow Fork if the command reads a lot, explores, or runs a long procedure, and its useful output is a small summary. Do not fork when the command's whole purpose is to operate on the live conversation — a command that reformats the answer just given, or that continues an in-flight edit, needs the session context that a fork deliberately withholds.
SituationFork?Reason
Codebase-wide audit invoked mid-taskYesWide read, narrow answer; protects the session window
Generate a release changelog from git historyYesLarge input, self-contained, no need for session state
Multi-step research skill run repeatedly in one sessionYesWithout forking, run 3 inherits runs 1 and 2 — the exact cross-contamination the objective names
"Explain the change you just made"NoThe answer is the session context; a fork cannot see it
"Fix the failing test we have been debugging"NoDepends on accumulated debugging state
What forking is not
  • It is not a permission boundary. Restricting capability is allowed-tools / settings, not context.
  • It is not parallelism. It is isolation; the fork still runs as part of the invocation.
  • It does not make output smaller by itself. You still specify the return contract in the body — a fork that returns everything it read has isolated nothing useful.
  • It is not free: the forked context must be seeded, so anything it needs from the session has to be passed in — the same closure rule as O3.
A skill invoked three times in one session gives worse answers each time. Diagnosis?

Cross-contamination: each invocation inherits the previous ones' exploration, so by the third run the context is dominated by two runs' worth of irrelevant intermediate state. Adding context: fork makes each invocation start clean and return only its result — which is precisely the case the objective is written around.

Claude Code · Choosing a review architecture 0% — priority O8

Three architectures, chosen on three inputs: scope, risk/reversibility, and whether a human must approve before anything changes.

ArchitectureShapeChoose when
Direct execution One pass: read, decide, act, report Scope is small and well understood; changes are cheap to revert; no approval gate is required. Adding ceremony here just costs turns
Plan mode Investigate and produce a plan; stop; a human approves; then execute The approach is uncertain or the change is expensive/irreversible or a stakeholder must sign off before code moves. The stop is the feature
Multi-phase workflow Distinct phases with their own prompts, tools and outputs — e.g. survey → specialised reviews (parallel) → synthesis → report Scope is large, concerns are separable, and one pass would trade recall between them (see C24). Also when phases need different tool permissions
Decision rule — three questions, answered in this order
  1. Must a human approve before any change? Yes → plan mode. This dominates: it is a process requirement, not an efficiency preference.
  2. Is the work too broad or too multi-concern for one focused pass? Yes → multi-phase.
  3. Otherwise → direct execution. Simplest thing that satisfies the constraints.
Why plan mode is not "read-only mode" Its value is the approval boundary: investigation happens, a reviewable artefact is produced, and execution is gated on a human decision. Read-only tool restrictions are how you implement it; the boundary is what you are being tested on. A question mentioning "architectural uncertainty", "stakeholder review", "irreversible", or "before we touch anything" is signalling plan mode.
Anti-patterns
  • Plan mode for a two-line, trivially revertible fix — pure ceremony, and the plan costs more than the fix.
  • Direct execution for a schema migration because "the agent is usually right" — reversibility, not accuracy, is the criterion.
  • Multi-phase for a single-concern review — you pay N times the tokens to split a concern that was never competing with anything.
  • Treating multi-phase as a substitute for approval. Phases are about coverage; the human gate is about authority. A question can require both.
A 40-file refactor across payments, with the team lead wanting to see the approach first. Architecture?

Plan mode, and then a multi-phase execution. The approval requirement forces the plan gate; the breadth and the risk profile of payments make a single execution pass a poor idea afterwards. An option offering only one of the two is incomplete — this is the shape of question that makes the A2 exam feel like it tests three things at once.

Claude Code · Designing a review configuration 0% — priority O13

The objective names three requirements, and a correct answer satisfies all three: load the correct project standards, restrict unnecessary tool access, and produce structured output suitable for automated downstream processing. Distractors satisfy one or two.

1 · Load the correct standards

  • Project-wide review criteria in CLAUDE.md or a dedicated review Skill — never pasted into a CI prompt string where it drifts from the repo.
  • Area-specific standards via .claude/rules/ with paths:, so a review touching src/payments/** automatically loads the payments rules and nothing else.
  • Accepted patterns and known exceptions travel with the standards (see C30) — otherwise the reviewer re-reports them every run.

2 · Restrict tool access

A reviewer needs to read. Granting write or arbitrary shell is not just a safety issue: it widens the decision space and degrades tool selection.

--allowedTools "Read,Grep,Glob,Bash(git diff:*),Bash(git log:*)"

Note the scoped Bash: the review needs the diff, not a shell. Bash(git diff:*) permits the command family it needs and nothing else.

3 · Structured output for downstream processing

"Post the review as a comment" is a human deliverable. "Fail the build on any high-severity finding in changed files" needs machine-readable output: a finding list with severity, file, line and class — so a script can filter, threshold and route without parsing prose.

claude -p "$(cat .github/review-prompt.md)" \
  --output-format json \
  --allowedTools "Read,Grep,Glob,Bash(git diff:*)" \
  --permission-mode plan \
  --max-turns 25 \
  > review.json

jq -e '[.findings[] | select(.severity=="high")] | length == 0' review.json
Rule — the review's output contract is part of the configuration If a downstream system consumes the review, the schema is not a nicety, it is the interface. Structure it with a tool schema or --output-format json; do not ask for "a JSON-formatted comment" in prose and hope. This is S25 applied to review.
Anti-pattern — one giant review prompt in the workflow YAML Standards embedded in CI config drift away from the repo they govern, cannot be scoped by path, and are invisible to developers running the same review locally. Keep the standards in the repo's configuration surfaces; keep the workflow file to invocation and gating.

Claude Code · Specialised review passes O24

Claude Code · Test generation quality 0% — priority O15

Ask for tests with no further input and you get assertions that restate the implementation: mocks that verify the mock, snapshots that lock in current behaviour, and coverage that rises while confidence does not. The objective names three fixes, and they are additive.

1 · Existing test files as context

The single highest-leverage input. Real test files carry the framework, the assertion style, the setup and teardown idiom, the naming convention, and the implicit standard of what this team considers worth testing. Two or three representative files teach all of that at once — far more effectively than a paragraph describing them.

2 · Fixture conventions

State where fixtures live, how they are built, and which are shared. Without this you get a bespoke inline fixture in every test, duplicated setup, and tests that break together when the shape changes.

# In CLAUDE.md or .claude/rules/tests.md (paths: ["**/*.test.ts"])
- Factories live in `test/factories/`; use `makeOrder({...overrides})`.

3 · Criteria separating meaningful from trivial

Rule — the funnel: Glob → Grep → Read, and Bash only for actions Each step narrows before the expensive one. Systematic exploration under a context budget

  1. Map before you read. Glob for structure; read the manifest, the entry point, the README. Establish the shape of the repo in a few hundred tokens.
  2. Search for anchors, not for understanding. Grep the symbol, the route, the error string. Collect file/line anchors.
  3. Read narrowly around the anchors — a range, not a file, when the file is large.
  4. Write down what you learned in a durable place — a scratchpad file, a structured state object — before context pressure eats it (X20).
  5. Delegate the wide passes. When a question needs 30 files scanned, that is a subagent's job; the coordinator wants the conclusion, not the 30 files (O10).
Anti-pattern — "read the whole directory to understand the module" This is the single most common context-exhaustion path, and it is the wrong answer even when the module is small, because it does not scale to the next question. Grep for the specific thing; read the specific place.

Anti-pattern — "increase the context window" A bigger window postpones every one of these failures without fixing any of them, degrades attention over long inputs, and costs more per turn. When it appears as an option in a context-management question, it is the distractor essentially every time.

Context · Session resumption 100% O2

Resumption is restoring an agent to a working state without paying for the work again. Two mechanisms, named in the objective.

Targeted re-analysis of changed files

On resume, the world may have moved. Rather than re-analysing everything or blindly trusting everything, compare a fingerprint — commit SHA, content hash, mtime — per artefact:

for file in previously_analysed:
    if hash(file) == recorded_hash: keep cached finding      # no cost
    else:                           re-analyse(file)         # targeted
for file in newly_added:            analyse(file)

Context injection

Seed the resumed session with the structured state object (X21) and the scratchpad contents, so it starts holding the conclusions rather than re-deriving them. In Claude Code the session mechanics are --continue (most recent session) and --resume <id> (a specific one); a SessionStart hook is the deterministic place to inject standing context on every start.

Rule — resumption must be explicit about staleness The dangerous resume is the one that restores confident conclusions about files that have since changed. Fingerprints are not an optimisation; they are what makes the restored state true.

Structured output · Extraction schema design 67% O26

The core insight: a schema that cannot express absence forces fabrication. A required, non-nullable field leaves the model no legal way to say "not in this document", so it produces a well-formed invention.

DeviceExpressesForm
Nullable value"The field applies but is absent or unreadable here""type": ["string", "null"], key still required
Optional key"The field may not apply to this document type at all"Omit from required
Enum + escape members"Classify, and be able to say the list does not fit"Enum plus "other" and "unclear"
Field descriptionThe semantics of null and the normalisation ruleProse inside description
Required-but-nullable is the preferred form Keep the key required and make the value nullable. Consumers then always find the field and only test for null, and you can measure a per-field null rate — which is your early warning that a layout has changed. An omitted key forces every consumer to distinguish "absent" from "missing key", and it is invisible in metrics.
"other" and "unclear" are not the same escape hatch "other" means "a real type that your list does not contain" — a rising rate tells you to extend the enum. "unclear" means "I cannot determine it from this document" — a rising rate tells you about scan quality or ambiguity. They diagnose different problems and drive different fixes, so a schema with only one of them collapses two signals into one.

Structured output · Truncation: split and merge O28

stop_reason: "max_tokens" on a structured response means the JSON is cut off mid-value. It is not a success, and it is not a parsing problem.

Rule — re-scope, do not inflate Raising max_tokens buys headroom until the next larger input, degrades quality across a very long generation, and costs more per call. The correct fix is to split the task into smaller scoped calls and merge the resulting structures: review 10 files per call rather than 120, extract per section rather than per document, then combine in your code where the merge is deterministic and testable.

Splitting also buys parallelism (each scoped call is independent, so they fan out — O10) and better attribution (each finding is tied to the scope that produced it). The merge belongs in code, not in another model call, because de-duplication and ordering are deterministic operations.

  - Secrets written to logs or committed files

DO NOT report:
  - Style, formatting or naming (handled by the linter)
  - Anything in **/generated/** or test fixtures
  - Theoretical issues without a concrete exploit path in this codebase
  - Dependency CVEs (a separate pass owns these)

If a finding does not clearly fall inside the inclusion list, omit it.
Rule — exclusions are as load-bearing as inclusions An inclusion list alone leaves the boundary fuzzy at the edges. Naming what is out — with the reason, so the rule generalises — is what raises precision. Note the last line: an explicit tie-breaker for the ambiguous case, which is what stops the model resolving uncertainty by reporting.

Tools · Distributing tools across agents 0% — priority O33

The objective states both the mechanism and the two reasons: assign each subagent only the tools required for its designated role, to reduce decision complexity and prevent out-of-role tool invocations. Most candidates read this as a security control. It is primarily a reliability control.

Why fewer tools produce better behaviour

  • Selection accuracy falls as the catalogue grows, and it falls fastest where tools are semantically similar. Four overlapping lookup tools in one agent is a mis-selection generator.
  • Every tool definition is tokens on every turn. Thirty-one tools handed to every subagent is thirty-one schemas re-sent on every request, for tools most of them will never call.
  • Out-of-role calls are usually plausible, which is what makes them dangerous: a returns agent with a refund tool will eventually issue a refund, because in some situation that looks like the helpful thing to do.

The distribution method

  1. Write down each agent's role in one sentence. If you cannot, the decomposition is wrong, not the tool list.
  2. List the actions that role must perform to satisfy its output contract — no more.
  3. Map actions to the minimum tools, preferring one consolidated tool with an action/system enum over several near-duplicates.
  4. Give write/irreversible tools to exactly one agent — usually the coordinator, or a dedicated executor gated behind approval. Investigators are read-only.
  5. Check the negative case: for each agent, name a tool it must not have and the bad outcome if it did. If you cannot name one, you have not scoped it.
AgentToolsDeliberately absent
CoordinatorTask/delegation, session state, escalationDomain tools — it delegates rather than acts, so it cannot silently do a worker's job badly
Security reviewerRead, Grep, GlobEdit, Write, Bash — a reviewer that can edit will "helpfully" fix things unreviewed
Test authorRead, Grep, Glob, Write, Bash(npm test:*)Unscoped Bash, deploy tools
Synthesis agentNoneEverything. It reasons over worker output only; a tool here lets it introduce facts no worker found (O19)
The rule that decides these items Tool access follows the output contract, not the topic. "It might be useful" is not a justification — it is the definition of the failure mode. The giveaway phrase in a question is an agent doing something reasonable but out of role; the fix is its tools: allowlist, not a stronger system prompt telling it not to.
Anti-patterns
  • Handing every subagent the full catalogue "so any agent can handle any request" — that is a single agent with extra latency.
  • Controlling role boundaries in the system prompt instead of the allowlist: surface 4 where surface 1 is available (F3).
  • Giving the synthesis agent tools so it can "verify" — verification is a worker's job with its own contract; synthesis that can fetch will invent.
  • Forgetting the parent: a subagent cannot exceed the session's own permissions (O6).

MCP · Resources versus tools O34

ToolsResources
SemanticsModel-invoked actions — do something, possibly with effectsAddressable content the client can attach directly

Cost profileA schema in every request; a turn per callNo per-turn schema cost; no exploratory round trips

Rule — expose content as resources to kill exploratory tool calls The failure this objective targets: an agent burning three turns on list_tables → describe_table → get_schema just to learn a shape. Exposing the schema as a resource makes it attachable in one step, with no model decision and no round trips. Resources are a context-efficiency mechanism as much as an API design one.
The design heuristic If the answer to "which one?" depends on a parameter the model must choose → tool. If the content can be addressed by a stable name or URI and simply needs to be present → resource. Servers that expose everything as tools force the model to rediscover their contents on every session.

Authentication by environment expansion

    "github": {
      "command": "npx",

      "env": { "GITHUB_TOKEN": "${GITHUB_TOKEN}" }

The file is committed; the secrets are not. ${VAR} expands from the environment at load, and ${VAR:-default} supplies a fallback. Committing a literal token and relying on the repository being private is the wrong answer even when the repository really is private — it puts a credential in version history, shares it with everyone who clones, and cannot be rotated per user.

Verifying discovery

A server that starts is not a server whose tools are usable. Verify that the tools actually appear — list the server's tools, confirm the namespaced names (mcp__<server>__<tool>) are present, and confirm any permission rules reference those exact names. Silent discovery failure is the usual cause of "the agent ignores our MCP server".

MCP · Writing tool descriptions O36

The description is the routing signal. Four components, and questions about mis-selection are nearly always missing the second one.

  1. Purpose / positive scope — what it does and when to use it.
  2. Negative scope, naming the alternative — "Do not use for X; use other_tool for that." This is what separates semantically similar tools.
  3. Input format specification — exact formats, units, allowed values, with an example value per parameter.
  4. Relationship and prerequisites — "Requires an order_id obtained from lookup_order."
search_tickets:
  "Full-text search across SUPPORT tickets by keyword, requester or date range.
   Use when you do not yet know the ticket ID.
   Do NOT use to fetch a known ticket — use get_ticket(ticket_id) for that.
   Do NOT use for engineering issues — use search_issues.
   query: free text, e.g. 'refund declined'.  since: ISO 8601 date, e.g. '2026-08-01'.
   Returns at most 25 summaries; call get_ticket for full bodies."
Rule — disambiguation lives in the descriptions, not the system prompt A routing paragraph in the system prompt is read once per turn and competes with everything else there. The description is attached to the decision itself. When a question offers "add a decision tree to the system prompt" against "rewrite the two descriptions with explicit negative scope", the second is the answer.

Tools · tool_choice and multi-tool sequencing 0% twice — top priority O37

You scored 0% on this objective on both attempts. It is the highest-value section on this page. It has two halves and questions usually test them together.

Half one · tool_choice

ValueGuaranteesUse when
{"type": "auto"} (default)Nothing — the model may call a tool or reply in textConversational turns where a text answer is legitimate
{"type": "any"}Some tool is called — never which oneA tool call is required but several are legitimate

{"type": "none"}No tool is called at allThe final summarising turn, after the data is gathered
The mis-selection trap, stated plainly any does not fix "the model keeps choosing the wrong tool". It guarantees a call, not a correct call — it can even make mis-selection worse by removing the option of not calling anything. Mis-selection is a tool-design problem: fix the descriptions (M36) and the distribution (M33).
The forced-tool side effect that surprises people When you force a specific tool, the assistant turn is effectively prefilled with that tool call, so no natural-language text is emitted before it. If a product requires a greeting before a forced identity check, the greeting cannot come from that turn — emit it from your orchestrator, or use auto and request the tool in the user message. Reported as a bug, this is expected behaviour.

Half two · Sequencing dependent tools

The failure: a tool needs a value that only another tool can produce, and nothing enforces the order, so the model calls the dependent tool with an invented input.

process_return(order_id)   requires   order_id  <-  lookup_order(email)

Model calls process_return("ORD-00000")   ->  silent failure or wrong order

Three layers, weakest to strongest — and the exam wants the strongest:

LayerMechanismStrength
Prompt rule"Always look up the order first"Advisory — fails under pressure
Tool description"Requires an order_id obtained from lookup_order"Better — attached to the decision, still advisory
Backend preconditionValidate in the tool, return a structured PRECONDITION_FAILED naming the remediation toolEnforced — the sequence cannot be skipped, and the error teaches the fix
{ "is_error": true,
  "error": { "code": "PRECONDITION_FAILED",
             "message": "order_id 'ORD-00000' does not exist.",
             "retryable": true,
             "remediation": "Call lookup_order(email) to obtain a valid order_id,
                             then retry process_return." } }
Rule — sequencing is enforced by the callee, taught by the description, never assumed from the prompt And note the combination the exam likes: a structured, actionable error is what turns a hard precondition into something the agent can recover from in one turn instead of failing the session. That makes this objective overlap with error design and with O1 — never parallelise a dependency.
A three-step workflow keeps skipping step one under load. Fix?

Validate the precondition in step two's backend and return PRECONDITION_FAILED naming step one as the remediation. Add the prerequisite to step two's tool description so the model usually gets it right, and make sure step two is not batched in parallel with step one. A stronger prompt instruction is the distractor.

Classification must always happen and must be one of nine categories. Configuration?

tool_choice: {"type":"tool","name":"classify_intent"} with the nine categories as an enum in the input schema and strict validation on. any would force a call without pinning which tool; prompt instructions guarantee neither the call nor the category set.

Exam-day playbook

  1. Read the last sentence of the stem first. A2 items are long and describe more system than the question needs. Find out what is being asked, then re-read the scenario for the two or three facts that bear on it.
  2. Name the objectives in play. Most items span two or three. "This is topology plus context contract" immediately kills options that only address one.
  3. Apply the surface ladder (F3). Prefer the option that moves the requirement into code, config, or schema.
  4. Check the dependency graph before endorsing any parallelism, batching or ordering.
  5. Ask what happens if the model ignores the instruction. If the answer is "the bad thing happens", that option is wrong.
  6. Prefer the option that makes failure visible over the one that makes it less likely. Escalation with a reason code beats a lower probability of error.
  7. Watch for "and". When an item requires approval and breadth, or isolation and a return contract, the correct option does both. Partial options are the commonest near-miss.
  8. Do not reward effort. Bigger windows, more retries, more examples, stronger wording — all are the distractor family. Structural fixes win.
  9. Two minutes per item. Flag and move. A long scenario you cannot decompose in two minutes will not improve on minute four.
